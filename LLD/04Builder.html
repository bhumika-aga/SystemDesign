Builder Pattern

For objects with lots of optional fields. Instead of a giant constructor, you set fields one step at a time on a builder, then call build() to get the finished object. You already use one: StringBuilder.

00 · The problem

Too many optional fields

A student has a roll number (mandatory) and lots of optional fields. Real classes can have 50 or 100. How should the constructor look? 

public class Student {
    int rollNumber;          // mandatory
    int age;                 // optional
    String name;             // optional
    String fatherName;       // optional
    String motherName;       // optional
    List<String> subjects;   // optional
    String mobileNumber;     // optional
}

Problem 1: one huge constructor

public Student(int rollNumber, int age, String name,
               String fatherName, String motherName,
               List<String> subjects, String mobileNumber) { … }
// callers must pass every value, even the ones they don't have

Problem 2: an explosion of small constructors

public Student(int rollNumber, int age) { … }
public Student(int rollNumber, int age, String name) { … }
public Student(int rollNumber, String fatherName,
               String motherName) { … }
// … one more for every combination someone needs

Problem 3: some combinations are impossible

With four or five fields this is already messy. With 100 fields it's unmanageable. That's the problem the builder pattern solves.

01 · The idea

Create the object step by step

Builder is a creational pattern that creates an object step by step.

Like you're five

A house isn't made in one go. First the walls, then the roof, then the door, then the windows. Halfway through it's not a house yet, just "a house being built". When everything is done, you say "build!" and you get the house.

  • Each step is a method: addWall(), addRoof(), …
  • After each step the object is still in an intermediate form: the builder. So every step method returns the builder itself.
  • A final build() method returns the real object (the House).
02 · You already use it

StringBuilder is a builder

String s = new StringBuilder()
        .append("Hello")         // returns StringBuilder
        .append(", ")            // returns StringBuilder
        .append("world")         // returns StringBuilder
        .toString();             // returns the real object: a String
Builder idea StringBuilder
Step methods append, insert, delete, deleteCharAt…
Steps return The builder itself (StringBuilder)
Final method toString() (plays the role of build())
Final object A new String
03 · Builder for Student

Three layers: product, builder, director

Layer 1: the product takes a builder

No long parameter list, no pile of small constructors: the constructor receives a builder and copies its values. 

public class Student {
    int rollNumber;
    int age;
    String name;
    String fatherName;
    String motherName;
    List<String> subjects;

    public Student(StudentBuilder builder) {
        this.rollNumber = builder.rollNumber;
        this.age        = builder.age;
        this.name       = builder.name;
        this.fatherName = builder.fatherName;
        this.motherName = builder.motherName;
        this.subjects   = builder.subjects;
    }
}

Layer 2: the builder holds the same fields

It's abstract (or an interface), so there can be several concrete builders. 

public abstract class StudentBuilder {
    int rollNumber;
    int age;
    String name;
    String fatherName;
    String motherName;
    List<String> subjects;

    public StudentBuilder setRollNumber(int rollNumber) {
        this.rollNumber = rollNumber;
        return this;                   // still a builder
    }
    public StudentBuilder setAge(int age) {
        this.age = age;
        return this;
    }
    public StudentBuilder setName(String name) {
        this.name = name;
        return this;
    }
    // setFatherName, setMotherName: same shape

    abstract public StudentBuilder setSubjects();

    public Student build() {
        return new Student(this);      // the real object
    }
}

The concrete builders differ only in the subjects:

public class EngineeringStudentBuilder extends StudentBuilder {
    @Override
    public StudentBuilder setSubjects() {
        List<String> subs = new ArrayList<>();
        subs.add("DSA");
        subs.add("OS");
        subs.add("Computer Architecture");
        this.subjects = subs;
        return this;
    }
}

public class MBAStudentBuilder extends StudentBuilder {
    @Override
    public StudentBuilder setSubjects() {
        List<String> subs = new ArrayList<>();
        subs.add("Micro Economics");
        subs.add("Business Studies");
        subs.add("Operations Management");
        this.subjects = subs;
        return this;
    }
}

trade-off Every field is written twice, in Student and in StudentBuilder. Builders mean more lines of code and some duplication.

04 · Layer 3

The director knows the recipe

The director holds a builder and calls its steps in the right order, then build(). For a house it knows "walls before roof". For students it knows which fields each kind needs. 

public class Director {
    StudentBuilder studentBuilder;

    Director(StudentBuilder studentBuilder) {
        this.studentBuilder = studentBuilder;
    }

    public Student createStudent() {
        if (studentBuilder instanceof EngineeringStudentBuilder) {
            return createEngineeringStudent();
        } else if (studentBuilder instanceof MBAStudentBuilder) {
            return createMBAStudent();
        }
        return null;
    }

    private Student createEngineeringStudent() {
        return studentBuilder.setRollNumber(1).setAge(22)
                .setName("Asha").setSubjects().build();
    }

    private Student createMBAStudent() {
        return studentBuilder.setRollNumber(2).setAge(24)
                .setName("Asha").setFatherName("MyFatherName")
                .setMotherName("MyMotherName").setSubjects().build();
    }
}

The client just picks a builder and asks for a student:

public class Client {
    public static void main(String args[]) {
        Director d1 = new Director(new EngineeringStudentBuilder());
        Director d2 = new Director(new MBAStudentBuilder());

        Student engineer = d1.createStudent();
        Student mba      = d2.createStudent();
    }
}

The client code is tiny: "make me a student". The director decides which steps to run for that builder.

05 · A common confusion

Builder vs decorator

Builder Decorator
Category Creational: creating an object Structural: composing objects into bigger structures
Pizza Builder per recipe, director calls addCrust → addCheese → build Base pizza wrapped in Cheese, wrapped in Mushroom
New combination Lecture: needs a new builder class Just wrap one more layer at run time

The lecture's conclusion: builder can't handle dynamic combinations; decorator can.

nuance That limit comes from writing one builder per recipe. A single PizzaBuilder with addCheese() and addMushroom() can build any combination at run time. The clearer difference is purpose: a builder assembles data once into a finished object, while decorators add behaviour (like each topping adding to cost()) by wrapping an existing object, and you can keep wrapping it later.

Beyond the course good to know as an engineer

Good to know as an engineer

The builder you'll see most: Effective Java's

Joshua Bloch's Effective Java (Item 2) popularised a simpler builder with no director: a static nested class, required fields in its constructor, optional fields as chained setters, and a build() that validates. 

public final class Student {
    private final int rollNumber;          // final: immutable
    private final String name;
    private final int age;

    private Student(Builder b) {
        rollNumber = b.rollNumber; name = b.name; age = b.age;
    }

    public static class Builder {
        private final int rollNumber;      // required
        private String name;               // optional
        private int age;

        public Builder(int roll) { this.rollNumber = roll; }
        public Builder name(String v) { name = v; return this; }
        public Builder age(int v)     { age = v;  return this; }

        public Student build() {
            if (age < 0) throw new IllegalStateException("age");
            return new Student(this);
        }
    }
}

Student s = new Student.Builder(42).name("Asha").age(20).build();
  • Required fields can't be forgotten: they go in the builder's constructor. In the lecture's version, the mandatory roll number could be skipped.
  • Immutable result: fields are final and there are no setters on Student.
  • Reads like named parameters: .name("Asha") is clearer than the fourth String in a constructor.

Why not just use setters?

The "JavaBeans" style (new Student() followed by setters) works, but the object is half-built and inconsistent between calls, can't be immutable, and can't validate all fields together. Bloch's verdict: builders are easier to read than telescoping constructors and safer than JavaBeans.

GoF director vs no director

In the original Gang of Four pattern, the director owns the construction sequence, so the same steps can produce different representations. It's worth having when the order matters and is reused (documents, house plans, SQL queries). For plain data objects, skip it. The lecture's instanceof checks inside the director are also a smell: every new builder means editing the director (open/closed, lecture 1).

Builders in the wild

  • StringBuilder, Stream.builder(), HttpRequest.newBuilder(), Locale.Builder, Guava's ImmutableList.builder().
  • Lombok @Builder generates a Bloch builder for you. It doesn't handle inheritance well; use @SuperBuilder for class hierarchies.
  • Don't use a builder for small objects. A point with two coordinates is fine with a constructor.
Check yourself

Revision questions

Try answering out loud before opening each one.

What three problems do many optional fields cause?

A huge constructor parameter list, an explosion of small constructors, and combinations that can't be written because two constructors would have the same signature.

Why does Student(int, String fatherName, String name) clash with Student(int, String fatherName, String motherName)?

Both have the signature (int, String, String). Java ignores parameter names when telling overloads apart, so it's a compile error.

What do the step methods of a builder return, and why?

The builder itself, because the object is still in its intermediate form. That's what lets you chain calls.

How does StringBuilder map onto the builder pattern?

append/insert/delete are the steps and return StringBuilder; toString() is the final build step and returns a String.

What are the three layers in the lecture's design?

The product (Student, constructed from a builder), the builder (abstract StudentBuilder plus Engineering/MBA builders), and the director (calls the steps in order, then build()).

What's one downside of the builder pattern?

More code and duplication: every field exists in both the product and the builder.

Builder vs decorator in one line?

Builder is creational: it assembles an object step by step. Decorator is structural: it wraps an existing object to add behaviour, and layers can be stacked at run time.

How does the Effective Java builder make the mandatory field impossible to forget?

The required field is a parameter of the builder's own constructor, so you can't create a builder without it.
