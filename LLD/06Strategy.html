Strategy Pattern

When several child classes need the same behaviour that the parent doesn't have, inheritance forces you to copy code. Strategy pulls that behaviour out into its own small classes, and each object simply holds the one it needs.

00 · Before we start

Design patterns and two arrows

Design patterns are proven ways of structuring object-oriented code so software stays manageable, scalable and reusable as it grows. Strong low-level design depends on knowing them, and Strategy is the first one this course covers.

01 · The problem duplicate code

Siblings sharing code the parent doesn't have

A base Vehicle has a drive() with the normal drive capability. Its children are passenger, off-road and sports vehicles. 

public class Vehicle {
    public void drive() {
        System.out.println("normal drive capability");
    }
}

public class PassengerVehicle extends Vehicle { }   // reuses parent

public class OffRoadVehicle extends Vehicle {
    @Override
    public void drive() {
        System.out.println("sports drive capability");
    }
}

public class SportsVehicle extends Vehicle {
    @Override
    public void drive() {                      // ✕ same code again
        System.out.println("sports drive capability");
    }
}
  • When a child uses the parent's code, inheritance works fine.
  • When siblings at the same level need the same code that isn't in the parent, it gets duplicated, and nothing is reused.
  • It gets worse as the system grows: more children, and more features (drive, display, fuel capacity, seating…), each duplicated wherever two siblings agree. That design doesn't scale.
02 · Strategy pattern

Move the behaviour out, then hold it

Like you're five

Instead of building a different toy car for every way of driving, you build one car with a slot. Pop in the "normal" chip or the "sports" chip, and the same car drives differently.

  1. Create an interface for the behaviour: DriveStrategy with drive().
  2. Write each variant once as a concrete class: NormalDriveStrategy, SportsDriveStrategy, and later XyzDriveStrategy.
  3. Vehicle has-a DriveStrategy and delegates drive() to it.
  4. The vehicle doesn't create the strategy itself (that would hard-wire one). Each child passes it in through the constructor: constructor injection.
03 · The code

Strategy, as written in the lecture

public interface DriveStrategy {
    public void drive();
}

public class NormalDriveStrategy implements DriveStrategy {
    @Override
    public void drive() {
        System.out.println("Normal drive capability");
    }
}

public class SportsDriveStrategy implements DriveStrategy {
    @Override
    public void drive() {
        System.out.println("Sports drive capability");
    }
}
public class Vehicle {
    DriveStrategy driveObject;

    // this is known as constructor injection
    Vehicle(DriveStrategy driveObj) {
        this.driveObject = driveObj;
    }

    public void drive() {
        driveObject.drive();          // delegate to the strategy
    }
}

public class SportsVehicle extends Vehicle {
    SportsVehicle() { super(new SportsDriveStrategy()); }
}
public class OffRoadVehicle extends Vehicle {
    OffRoadVehicle() { super(new SportsDriveStrategy()); }
}
public class GoodsVehicle extends Vehicle {
    GoodsVehicle() { super(new NormalDriveStrategy()); }
}
public class Main {
    public static void main(String args[]) {
        Vehicle vehicle = new SportsVehicle();
        vehicle.drive();
    }
}
// output: Sports drive capability

new SportsVehicle() passes a SportsDriveStrategy up to Vehicle. When drive() is called, the vehicle hands the work to that strategy.

When to use it

The lecture's rule of thumb

Use Strategy when, in a parent-child hierarchy, several children need the same code that isn't in the base class. Otherwise, every new feature adds more duplicated code.

Plain inheritance Strategy
Special drive code Copied into each child that needs it Written once in SportsDriveStrategy
New behaviour Override in yet more children Add one new strategy class
Relationship Vehicle is-a sporty thing Vehicle has-a drive strategy
Scales? duplication grows reuse grows
Beyond the course good to know as an engineer

Good to know as an engineer

The textbook definition

Gang of Four: define a family of algorithms, encapsulate each one, and make them interchangeable. Strategy lets the algorithm vary independently of the clients that use it. It's the classic case of "favour composition over inheritance", and it follows open/closed (lecture 1): new behaviour is a new class, and Vehicle never changes. (Small correction: the Gang of Four catalogue has 23 patterns, not "25 or more".)

Swap strategies at run time

The lecture fixes each vehicle's strategy in its constructor. A setter lets you change behaviour while the program runs, which constructor-only injection can't: 

public void setDriveStrategy(DriveStrategy s) {
    this.driveObject = s;
}

Vehicle car = new GoodsVehicle();
car.setDriveStrategy(new SportsDriveStrategy());   // sport mode on

You use strategies every day

  • Comparator is a sorting strategy: list.sort(…) stays the same, and the comparator you pass decides the order.
  • Payment methods (card, UPI, wallet), compression formats, route planners (fastest, shortest, no tolls) and pricing rules are all common strategy setups.

Modern Java: a lambda is a strategy

A strategy interface with one method is a functional interface, so you often don't need a class per strategy at all: 

DriveStrategy sports = () -> System.out.println("Sports drive");
Vehicle v = new Vehicle(sports);

staff.sort(Comparator.comparing(Employee::salary).reversed());

Strategy vs State (they look identical)

Same structure, different intent. In Strategy the client chooses the algorithm and strategies don't know about each other. In State, the object's behaviour changes as its internal state changes, and the states themselves trigger transitions (a vending machine moving from "idle" to "has coin"). State comes later in this course.

Don't overuse it

If there's only one behaviour and no realistic second one, a plain method is simpler. Introduce a strategy when you actually have, or clearly expect, interchangeable variants.

Check yourself

Revision questions

Try answering out loud before opening each one.

What's the difference between an is-a and a has-a relationship?

is-a is inheritance (SportsVehicle is a Vehicle). has-a is composition: one object holds another (Vehicle has a DriveStrategy).

When does plain inheritance lead to duplicate code?

When sibling classes need the same behaviour that isn't in the parent, so each sibling overrides with the same code.

What are the parts of the strategy solution?

A DriveStrategy interface, concrete strategies (Normal, Sports, Xyz), and a Vehicle that holds a DriveStrategy and delegates drive() to it.

Why doesn't Vehicle just do new NormalDriveStrategy() itself?

That hard-wires one behaviour. Constructor injection lets each child (or caller) choose the strategy.

What does new SportsVehicle().drive() print, and why?

"Sports drive capability". SportsVehicle passes a SportsDriveStrategy to the Vehicle constructor, and Vehicle.drive() delegates to it.

How do you add a brand-new drive behaviour?

Write a new class implementing DriveStrategy and pass it in. No existing class changes (open/closed).

Strategy vs State in one line?

Strategy: the client picks an interchangeable algorithm. State: behaviour changes as the object's internal state changes, with states driving the transitions.
