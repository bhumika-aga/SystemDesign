SOLID Principles

Five rules of thumb for object-oriented code that's easy to change. You probably follow some already without knowing the names, but interviewers ask for them by name. Each one below comes with the lecture's Java example: the version that breaks the rule, and the fix.

Why bother

What SOLID buys you

  • Avoids duplicate code.
  • Code is easy to maintain and easy to understand.
  • Software is flexible, and complexity is reduced.

Design patterns (the rest of this LLD course) are largely these five principles applied to recurring problems.

S · Single responsibility principle

"A class should have only one reason to change"

One class, one responsibility. If several unrelated kinds of change would each force you to edit the same class, it's doing too much.

Breaks the rule

class Marker { String name; String color; int year; int price; } class Invoice { private Marker marker; private int quantity; // reason 1: pricing (GST, discount…) public int calculateTotal() { return marker.price * quantity; } // reason 2: print format public void printInvoice() { /* print */ } // reason 3: storage public void saveToDB() { /* save */ } }

Invoice has three reasons to change: the price logic (add GST or a discount), the printing logic, and the saving logic (DB or file).

Follows the rule

class Invoice { // marker, quantity public int calculateTotal() { … } } class InvoicePrinter { // holds an Invoice public void print() { … } } class InvoiceDao { // holds an Invoice public void saveToDB() { … } }

A pricing change now only touches Invoice, and the other classes are unaffected. That's easier to maintain and easier to understand.

O · Open/closed principle

"Open for extension, closed for modification"

Code that's already tested and live shouldn't be edited to add features. Add new code that extends it instead.

Breaks the rule

class InvoiceDao { public void saveToDB() { … } // tested, live in production // ✕ new method edited into a tested class: risk of bugs public void saveToFile() { … } }

Follows the rule

interface InvoiceDao { void save(Invoice invoice); } class DatabaseInvoiceDao implements InvoiceDao { public void save(Invoice i) { /* save to DB */ } } class FileInvoiceDao implements InvoiceDao { public void save(Invoice i) { /* save to file */ } } // tomorrow: class MongoInvoiceDao implements InvoiceDao { … } // ← extension, no modification
L · Liskov substitution principle ★ the tricky one

"A subtype must be usable wherever its parent is"

If class B is a subtype of class A, you should be able to replace an A object with a B object without breaking the program's behaviour. The output may differ, but nothing should break.

Rule of thumb: a subclass should extend the parent's capabilities (add features), never narrow them down (take features away).

interface Bike { void turnOnEngine(); void accelerate(); } class MotorCycle implements Bike { boolean isEngineOn; int speed; public void turnOnEngine() { isEngineOn = true; } public void accelerate() { speed = speed + 10; } } class Bicycle implements Bike { public void turnOnEngine() { // ✕ narrows the parent throw new AssertionError("there is no engine"); } public void accelerate() { /* do something */ } }

Code that takes a Bike and calls turnOnEngine() works with MotorCycle but crashes with Bicycle. The subtype isn't substitutable, so LSP is broken. The solution is the next lecture (LLD 2).

I · Interface segregation principle

"Don't force classes to implement methods they don't need"

Split large interfaces into small, focused ones, so no client has to implement functions it doesn't use.

Breaks the rule

interface RestaurantEmployee { void washDishes(); void serveCustomers(); void cookFood(); } class Waiter implements RestaurantEmployee { public void washDishes() { /* not my job ✕ */ } public void serveCustomers() { System.out.println("serving the customer"); } public void cookFood() { /* not my job ✕ */ } }

Follows the rule

interface WaiterInterface { void serveCustomers(); void takeOrder(); } interface ChefInterface { void cookFood(); void decideMenu(); } // (and e.g. a HelperInterface { void washDishes(); }) class Waiter implements WaiterInterface { public void serveCustomers() { System.out.println("serving the customer"); } public void takeOrder() { System.out.println("taking orders"); } }
D · Dependency inversion principle

"Depend on interfaces, not concrete classes"

Breaks the rule

class MacBook { private final WiredKeyboard keyboard; // ✕ concrete classes private final WiredMouse mouse; public MacBook() { keyboard = new WiredKeyboard(); // stuck with wired forever mouse = new WiredMouse(); } }

Follows the rule

class MacBook { private final Keyboard keyboard; // interfaces private final Mouse mouse; // constructor injection public MacBook(Keyboard keyboard, Mouse mouse) { this.keyboard = keyboard; this.mouse = mouse; } } // any combination works new MacBook(new WiredKeyboard(), new BluetoothMouse());

Now MacBook works with wired, Bluetooth, or any mix, without changing its code.

Good to know as an engineer

Sharper wording for each principle

  • S: Robert C. Martin's later phrasing is "a module should be responsible to one actor": one group of people who request changes. Pricing rules come from finance, print layouts from design, storage from the platform team. "Does one thing" is a looser reading.
  • O: usually achieved with polymorphism: an interface plus new implementations (exactly the Strategy pattern, LLD 6). It doesn't forbid fixing bugs in existing code.
  • L: a subtype must not demand more from callers or promise less back. The textbook example is Square extends Rectangle: setting a square's width also changes its height, which breaks code that expects to set them independently.
  • I: a sign you need it is UnsupportedOperationException or empty method bodies in an implementation.
  • D: the full statement: high-level modules shouldn't depend on low-level modules; both should depend on abstractions, and the abstraction belongs with the high-level code.

Dependency inversion vs dependency injection

They're related but different. Inversion is the design principle: depend on an interface. Injection is a technique for supplying the actual object from outside, like the constructor in the MacBook example. Frameworks like Spring automate injection.

Don't overdo it

An interface for every class and a class for every method makes code harder to follow. Apply SOLID where change is likely. YAGNI ("you aren't gonna need it") and KISS are the counterweights.

History

The principles come from Robert C. Martin ("Uncle Bob"), notably his 2000 paper Design Principles and Design Patterns. The SOLID acronym was coined a little later (often credited to Michael Feathers). Liskov substitution is named after Barbara Liskov's 1987 work on subtyping.

Check yourself

Revision questions

Try answering out loud before opening each one.

What does each letter of SOLID stand for?

Single responsibility, Open/closed, Liskov substitution, Interface segregation, Dependency inversion.

Why does the original Invoice class break SRP?

It has three reasons to change: price calculation, printing and saving.

How do you add "save to file" without breaking open/closed?

Make InvoiceDao an interface and add a new FileInvoiceDao class, instead of editing the tested database class.

State Liskov substitution in one sentence.

If B is a subtype of A, any A can be replaced by a B without breaking the program's behaviour, so subclasses extend capabilities and never narrow them.

Why does Bicycle break LSP?

It implements Bike but throws on turnOnEngine(), so code written for any Bike crashes when given a Bicycle.

What's wrong with one RestaurantEmployee interface?

It forces Waiter to implement washDishes() and cookFood(), which it doesn't need. Split it into smaller interfaces.

How does the fixed MacBook follow dependency inversion?

It holds Keyboard and Mouse interfaces, injected through the constructor, so any wired or Bluetooth combination works without code changes.
