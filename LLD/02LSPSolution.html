Liskov Substitution: the fix

Lecture 1 showed how a child class can break Liskov. This one shows how to prevent it: keep only truly common methods in the parent, and move the special ones into a new in-between class. Then the compiler catches the mistake before it can crash in production.

00 · Recap

Swap the child, nothing breaks

If a parent has children C1, C2 and C3, code written as Parent obj = new C1() must keep working when you change it to new C2() or new C3().

Like you're five

A remote control works with any TV of the right brand. If one "TV" turned out to be a painting, pressing "on" would do nothing, or worse. A child class must really be able to do everything the parent promises.

The lecture's diagnosis: the break happens when a child removes a capability the parent has, instead of adding to it.

01 · The setup

Vehicle, MotorCycle, Car: all fine

public class Vehicle {
    public Integer getNumberOfWheels() { return 2; }   // default
    public Boolean hasEngine()         { return true; }
}

public class MotorCycle extends Vehicle { }  // 2 wheels, engine: as-is

public class Car extends Vehicle {
    @Override
    public Integer getNumberOfWheels() { return 4; }
}

The client puts both into one list and loops over them:

List<Vehicle> vehicleList = new ArrayList<>();
vehicleList.add(new MotorCycle());
vehicleList.add(new Car());

for (Vehicle vehicle : vehicleList) {
    System.out.println(vehicle.hasEngine().toString());
}
// true
// true

MotorCycle uses the parent's hasEngine(), and so does Car. Both print true.

02 · The problem LSP broken

Add Bicycle, and the loop crashes

A bicycle has no engine, so it overrides hasEngine() and returns null (allowed, since the return type is the object Boolean). 

public class Bicycle extends Vehicle {
    @Override
    public Boolean hasEngine() { return null; }  // ✕ capability gone
}

vehicleList.add(new Bicycle());
// loop: null.toString()
// → Exception in thread "main" java.lang.NullPointerException

Bicycle reduced the parent's capability instead of extending it. The tempting patch is to guard every call: 

if (!(vehicle instanceof Bicycle)) {   // ✕ repeated at 100 call sites
    System.out.println(vehicle.hasEngine().toString());
}

If hasEngine() is called in 100 places, that's 100 if/else checks, and every future engine-less vehicle means editing all of them again.

03 · The solution

Generic in the parent, specific one level down

Put only the methods that are common to every child in the parent. Move the specific ones into a new subclass, and inherit from it only where they apply. 

public class Vehicle {                      // generic only
    public Integer getNumberOfWheels() { return 2; }
}

public class EngineVehicle extends Vehicle { // specific
    public boolean hasEngine() { return true; }
}

public class MotorCycle extends EngineVehicle { }
public class Car extends EngineVehicle {
    @Override
    public Integer getNumberOfWheels() { return 4; }
}

public class Bicycle extends Vehicle { }    // no engine method at all

Bicycle doesn't need to override anything: it inherits getNumberOfWheels() and simply never sees hasEngine().

04 · Client code

Three clients, and none can crash

Client 1: list of Vehicle, generic method

List<Vehicle> vehicleList = new ArrayList<>();
vehicleList.add(new MotorCycle());
vehicleList.add(new Car());
vehicleList.add(new Bicycle());

for (Vehicle vehicle : vehicleList) {
    System.out.println(vehicle.getNumberOfWheels().toString());
}   // ✓ 2, 4, 2

Through a Vehicle reference you can only call what Vehicle declares, and every child has it.

Client 2: list of Vehicle, engine method

for (Vehicle vehicle : vehicleList) {
    System.out.println(vehicle.hasEngine());   // ✕ compile error
}

Vehicle doesn't know about hasEngine(), so this won't compile, even before a Bicycle is added.

Client 3: list of EngineVehicle

List<EngineVehicle> vehicleList = new ArrayList<>();
vehicleList.add(new MotorCycle());   // ✓
vehicleList.add(new Car());          // ✓
vehicleList.add(new Bicycle());      // ✕ compile error

for (EngineVehicle vehicle : vehicleList) {
    System.out.println(vehicle.hasEngine());   // safe
}

Bicycle isn't an EngineVehicle, so it can't get into the list in the first place.

Takeaway

Move the failure from run time to compile time

Before After
Where's hasEngine()? Vehicle (every child) EngineVehicle only
Bicycle's parent Vehicle, overrides with null Vehicle, overrides nothing
Mistake found run time · NPE compile time
Client code instanceof checks everywhere No checks needed

As the lecture puts it, this is just using inheritance properly: a class belongs under a parent only if it can honour everything that parent offers.

Beyond the course good to know as an engineer

Good to know as an engineer

The precise rules (what "substitutable" means)

Liskov's behavioural subtyping is usually written as a few checkable rules. A subclass must:

  • Not strengthen preconditions: accept at least everything the parent accepts. (No "throws if the list is empty" when the parent handled empty lists.)
  • Not weaken postconditions: deliver at least what the parent promised. Returning null where callers expect a real Boolean is exactly this break.
  • Keep invariants: whatever is always true of the parent (say, "balance never negative") stays true.
  • Respect the history constraint: not allow state changes the parent forbids, for example making an immutable point mutable through a new setter.
  • Not throw new kinds of exceptions that callers of the parent wouldn't expect.

Java's compiler already checks the signature side: an override may return a narrower type (covariant return) and may not declare broader checked exceptions. The behavioural rules above are only enforced by design and tests.

A subtle point about this example

What actually broke the contract was return null. A Bicycle returning false would have answered the question honestly and the loop wouldn't crash. The split is still the better design when a method makes no sense for some children: in lecture 1, Bicycle.turnOnEngine() can't do anything truthful, so the method shouldn't be on its parent at all.

Other ways to fix it

  • Small capability interfaces instead of a deeper class tree: interface Motorized { boolean hasEngine(); } that only Car and MotorCycle implement. This is interface segregation (lecture 1) solving an LSP problem, and it scales better when capabilities overlap (electric, engine, pedals…).
  • Composition over inheritance: give Vehicle an optional Engine field instead of encoding "has an engine" in the class tree.
  • Ask "is-a" about behaviour, not real-world category. A square is a rectangle in maths, but a Square extends Rectangle breaks code that sets width and height independently.

Java's own famous example

Collections.unmodifiableList(…) and List.of(…) return a List whose add() throws UnsupportedOperationException. The Javadoc marks those methods as "optional operations", so it's technically within the contract, but callers who expect any List to be addable get a runtime surprise. It's the trade-off Java chose to avoid separate read-only and mutable interfaces.

How to catch LSP breaks in practice

Run the parent's tests against every subclass (a shared "contract test"). Treat empty overrides, instanceof checks in client code and UnsupportedOperationException as warning signs.

Check yourself

Revision questions

Try answering out loud before opening each one.

Why does adding Bicycle crash the original loop?

Bicycle overrides hasEngine() to return null, and the loop calls hasEngine().toString(), which throws a NullPointerException.

Why is "add an instanceof check" a bad fix?

Every call site needs the check (the lecture's "100 places"), and every new engine-less vehicle means editing all of them again.

What's the lecture's rule for deciding what goes in the parent?

Only generic methods that every child supports. Specific methods go into a new subclass that only the relevant children extend.

Draw the fixed hierarchy.

Vehicle (getNumberOfWheels) → EngineVehicle (hasEngine) → Car, MotorCycle. Bicycle extends Vehicle directly.

Why can't client 2 call hasEngine() on a List<Vehicle>?

Vehicle no longer declares hasEngine(), so it's a compile-time error. The unsafe call can't be written.

What happens if you add a Bicycle to a List<EngineVehicle>?

Compile-time error, because Bicycle isn't an EngineVehicle.

Name two of the formal LSP rules.

Any two of: don't strengthen preconditions, don't weaken postconditions, preserve invariants, respect the history constraint, don't throw unexpected new exceptions.
