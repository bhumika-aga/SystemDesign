Factory & Abstract Factory

Two patterns about who creates objects. Instead of every class deciding "if this, make a Circle; if that, make a Square", one factory owns that decision. Abstract factory adds a second layer: first pick the right factory, then let it pick the object.

00 · The problem

Creating objects "if this, then that"

Use a factory when you create an object based on a condition: condition 1 → object 1, condition 2 → object 2.

Like you're five

You don't build your own toy car. You tell the toy shop "a red car, please" and it hands you one. The shop knows how to make each toy; you only say which one you want.

Without a factory, every class that needs a shape repeats the same conditions. Add a new shape and you edit all of them. The factory avoids that duplication and is the single source of truth for "which object do I build?"

Both patterns are creational design patterns: they're about how objects get created.

01 · Factory pattern

One class decides which object to build

  • Product interface: Shape, with one method draw().
  • Concrete products: Circle, Square, Rectangle, each implementing draw().
  • Factory: ShapeFactory.getShape(input) looks at the input and returns the matching object.
02 · Factory in code

ShapeFactory, as shown in the lecture

public interface Shape {
    void draw();
}

public class Circle implements Shape {
    @Override
    public void draw() { System.out.println("circle"); }
}

public class Rectangle implements Shape {
    @Override
    public void draw() { System.out.println("rectangle"); }
}
// Square is the same shape of class
public class ShapeFactory {

    Shape getShape(String input) {
        switch (input) {
            case "CIRCLE":
                return new Circle();
            case "RECTANGLE":
                return new Rectangle();
            default:
                return null;
        }
    }
}
public class MainClass {
    public static void main(String args[]) {
        ShapeFactory shapeFactoryObj = new ShapeFactory();
        Shape shapeObj = shapeFactoryObj.getShape("CIRCLE");
        shapeObj.draw();
    }
}
// output: circle

The caller never writes new Circle(). It asks the factory, and gets back a Shape.

03 · Abstract factory pattern

A factory of factories

When products fall into groups, give each group its own factory, then add one more factory on top that picks the right group.

The lecture's example: four cars implementing a Vehicle interface with an average() method (fuel average).

Group Class Example
Luxury LuxuryVehicle1 Mercedes
Luxury LuxuryVehicle2 BMW
Ordinary OrdinaryVehicle1 Swift
Ordinary OrdinaryVehicle2 Hyundai

You could put all four cars into one big factory. But when products can be logically grouped, each group gets its own factory with the same kind of switch logic, and a top-level factory chooses between them.

04 · Abstract factory in code

Two layers of the same idea

The lecture draws this one on the whiteboard. Here it is as Java, using the whiteboard's names. 

public interface Vehicle { int average(); }

public class LuxuryVehicle1 implements Vehicle {   // Mercedes
    public int average() { return 10; }
}
// LuxuryVehicle2 (BMW), OrdinaryVehicle1 (Swift),
// OrdinaryVehicle2 (Hyundai) look the same
public interface VehicleFactory {
    Vehicle getVehicle(String type);
}

public class LuxuryFactory implements VehicleFactory {
    public Vehicle getVehicle(String type) {
        switch (type) {
            case "MERCEDES": return new LuxuryVehicle1();
            case "BMW":      return new LuxuryVehicle2();
            default:         return null;
        }
    }
}

public class OrdinaryFactory implements VehicleFactory {
    public Vehicle getVehicle(String type) {
        switch (type) {
            case "SWIFT":   return new OrdinaryVehicle1();
            case "HYUNDAI": return new OrdinaryVehicle2();
            default:        return null;
        }
    }
}
// layer 1: the factory of factories
public class VehicleFactoryProducer {
    VehicleFactory getVehicleFactory(String group) {
        switch (group) {
            case "LUXURY":   return new LuxuryFactory();
            case "ORDINARY": return new OrdinaryFactory();
            default:         return null;
        }
    }
}

VehicleFactory f = new VehicleFactoryProducer()
        .getVehicleFactory("LUXURY");
Vehicle car = f.getVehicle("BMW");      // LuxuryVehicle2

Good to know as an engineer

What it is One class with a switch Subclasses override a create method One object creates a family of related products
Mechanism Conditional Inheritance Composition: you pass a factory object around

The lecture's "factory pattern" is the simple factory idiom. It isn't one of the 23 Gang of Four patterns, but it's the one you'll see most. GoF Factory Method looks like this: 

abstract class Dialog {
    abstract Button createButton();    // the factory method
    void render() { createButton().paint(); }
}
class WindowsDialog extends Dialog {
    Button createButton() { return new WindowsButton(); }
}

The textbook abstract factory is about families

"Factory of factories" is a popular way to explain it, but the GoF definition is a factory that creates several related products that must match. The classic example is a UI toolkit: 

interface GUIFactory {
    Button   createButton();
    Checkbox createCheckbox();
}
class MacFactory implements GUIFactory { … } // Mac button, checkbox
class WinFactory implements GUIFactory { … } // Windows ones

Hand the app one GUIFactory and every widget it builds is guaranteed to come from the same family. You never get a Mac button next to a Windows checkbox. In the lecture's terms, a true luxury factory would make the matching car and interior and tyres.

Making the lecture's code production-ready

  • Don't return null for unknown input. Throw IllegalArgumentException instead, otherwise the caller crashes later with a NullPointerException (the same trap as lecture 2).
  • Use an enum (ShapeType.CIRCLE) instead of strings, so typos become compile errors.
  • Adding a shape means editing the switch, which bends open/closed. For large or plugin-style sets, use a registry such as Map<ShapeType, Supplier<Shape>>.
  • Factories often return shared or cached instances instead of always calling new. Callers don't need to know which.

Where you've already used factories

  • Calendar.getInstance() returns a Gregorian, Buddhist or Japanese calendar depending on locale.
  • NumberFormat.getInstance(), Charset.forName("UTF-8") and List.of(…) are all factory methods.
  • DocumentBuilderFactory.newInstance() picks an XML parser implementation at run time. It's often called an abstract factory, though it only makes one kind of product.
  • Spring's BeanFactory and ApplicationContext are, at heart, very large factories.
Check yourself

Revision questions

Try answering out loud before opening each one.

When does the lecture say to use a factory?

When you create objects based on a condition (condition 1 → object 1, condition 2 → object 2), especially when that logic would otherwise be repeated in many places.

What does ShapeFactory.getShape("CIRCLE") return, and what type does the caller see?

A new Circle object, typed as the Shape interface.

What problem does the factory solve?

Duplicated creation logic. The conditions live in one place (the single source of truth) instead of being copied wherever an object is needed.

Describe the two layers of the abstract factory example.

Layer 1 (factory of factories) returns a LuxuryFactory or OrdinaryFactory. Layer 2: that factory returns the concrete car (Mercedes/BMW or Swift/Hyundai).

Simple factory vs GoF Factory Method?

A simple factory is one class with a switch. Factory Method uses inheritance: a base class declares a create method, and subclasses decide which product to instantiate.

What's the GoF definition of Abstract Factory?

An interface for creating families of related or dependent objects without naming their concrete classes, for example a GUIFactory that makes matching buttons and checkboxes.

Why is returning null from a factory a bad idea?

The caller may not check, and it crashes later with a NullPointerException far from the cause. Throw an exception for unknown input instead.
