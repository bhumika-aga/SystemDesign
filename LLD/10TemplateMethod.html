Template Method Pattern

The parent class fixes the steps and their order; each child fills in how to do each step. It's just an abstract class used deliberately, and it's one of the most common patterns in real codebases.

00 · When to use it

Two hints that you need it

A behavioural pattern. Reach for it when both are true:

  1. You want all classes to follow specific steps, in a specific order, to process a task.
  2. You also need the flexibility for each class to have its own logic in those steps.
Like you're five

Every sandwich is made the same way: bread, filling, bread, cut. That order is the template. One kid picks cheese, another picks jam, but nobody puts the filling on top of the second slice.

01 · The example

Two payment flows, the same four steps

A payments app has a pay to friend flow and a pay to merchant flow (an online purchase). Both must follow the same steps in order:

  1. Validate the request
  2. Debit the money from the sender
  3. Calculate the platform's fees
  4. Credit the money to the receiver
Pay to friend Pay to merchant
Sender pays 100 rupees 100 rupees
Platform fee 0% 2% (2 rupees)
Receiver gets 100 rupees (full amount) 98 rupees (the remainder)

Same steps, but the logic inside some steps (validation, fees, credit) differs per flow.

02 · The problem no guaranteed order

An interface can't enforce the order

public interface Payment {
    void sendMoney();
}
// PayToFriendFlow and PayToMerchantFlow each override sendMoney()
// and each decides the order of steps itself; nothing checks it
03 · The solution

An abstract class with a final template method

public abstract class PaymentFlow {

    public abstract void validateRequest();
    public abstract void calculateFees();
    public abstract void debitAmount();
    public abstract void creditAmount();

    // this is the template method, which defines the order of steps
    public final void sendMoney() {
        validateRequest();      // step 1
        debitAmount();          // step 2
        calculateFees();        // step 3
        creditAmount();         // step 4
    }
}
public class PayToFriend extends PaymentFlow {
    @Override
    public void validateRequest() {
        System.out.println("Validate logic of PayToFriend");
    }
    @Override
    public void debitAmount() {
        System.out.println("Debit the Amount logic of PayToFriend");
    }
    @Override
    public void calculateFees() {
        System.out.println("0% fees charged");
    }
    @Override
    public void creditAmount() {
        System.out.println("Credit the full amount");
    }
}

public class PayToMerchantFlow extends PaymentFlow {
    // validateRequest(), debitAmount(): merchant-specific logic
    @Override
    public void calculateFees() {
        System.out.println("2% fees charged");
    }
    @Override
    public void creditAmount() {
        System.out.println("Credit the remaining amount");
    }
}
  • sendMoney() is final: no child can override it, so every flow follows the same order.
  • The steps are abstract: each child must supply its own logic.
  • Logic that's common to every flow can go in the parent as a normal (concrete) method that children reuse.
04 · How a call runs

The parent drives, the child fills in

PaymentFlow obj = new PayToFriend();
obj.sendMoney();

// Validate logic of PayToFriend
// Debit the Amount logic of PayToFriend
// 0% fees charged
// Credit the full amount

PayToFriend doesn't define sendMoney(), so the parent's version runs. Each step it calls is dispatched to the object's own override. The order comes from the parent, and the details come from the child.

Nothing new in Java here: an abstract class can mix concrete and abstract methods. The pattern is the way of thinking: make the task method final, list the steps inside it, and leave only the steps abstract.

Beyond the course good to know as an engineer

Good to know as an engineer

The textbook definition

Gang of Four: define the skeleton of an algorithm in an operation, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps without changing the algorithm's structure.

Hooks: optional steps

Not every step has to be abstract. A hook is a step with a default (often empty) body that children may override: 

public abstract class PaymentFlow {
    public final void sendMoney() {
        validateRequest();
        debitAmount();
        calculateFees();
        creditAmount();
        if (shouldNotify()) sendReceipt();   // hook decides
    }
    protected boolean shouldNotify() { return true; }   // hook
    protected void sendReceipt() { /* default: email */ }
}

Make step methods protected rather than public, so callers can only use the template method and can't run steps out of order.

The Hollywood principle

"Don't call us, we'll call you." The parent calls the child's methods, never the other way round. That inversion of control is how frameworks work: you fill in hooks, and the framework decides when they run.

You've used it already

  • HttpServlet.service() receives every request and dispatches to your doGet() / doPost().
  • AbstractList: implement just get(int) and size(), and it builds iterator(), indexOf(), equals() and more on top.
  • JUnit's lifecycle (@BeforeEach → test → @AfterEach), Spring's JdbcTemplate, and Android's onCreate → onStart → onResume.

Template Method vs Strategy

Template Method Strategy (lecture 6)
Mechanism Inheritance: subclass overrides steps Composition: object holds a strategy
What varies Individual steps of one algorithm The whole algorithm
Chosen At compile time (which subclass) Can be swapped at run time

Downside of inheritance: Java allows only one superclass, and deep template hierarchies get rigid. If the steps vary independently, a set of strategies can be more flexible.

Check yourself

Revision questions

Try answering out loud before opening each one.

What are the two hints that you need the template method pattern?

All classes must follow specific steps in a set order to process a task, and each class needs its own logic within those steps.

What are the four steps of sendMoney() in the lecture?

Validate request, debit amount, calculate fees, credit amount.

Why doesn't a Payment interface solve this?

Each implementation writes its own sendMoney(), so nothing guarantees the steps run, or run in the right order.

Why is sendMoney() declared final?

So no subclass can override it and change the order of steps.

What differs between PayToFriend and PayToMerchantFlow?

Their step logic: friend charges 0% and credits the full amount; merchant charges 2% and credits the remainder.

What's a hook method?

An optional step with a default implementation that subclasses may override, for example shouldNotify().

Template Method vs Strategy?

Template Method uses inheritance to vary steps of a fixed algorithm. Strategy uses composition to swap the whole algorithm, even at run time.
