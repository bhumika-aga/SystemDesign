Recap

Why we need write strategies

Cache-aside and read-through (Part 1) only handle reads. Writes went straight to the database and left the cache holding stale data (DB = 11, cache still says 10). A write strategy decides what happens to the cache when data changes.

Remember the pattern for this whole lecture: write strategies are paired with a read strategy. On their own, most of them are useless.

Strategy 3

Write-around

  • Writes go directly to the database. The cache's copy is not updated.
  • Instead, the cached entry is invalidated: marked dirty (a dirty flag set to true).
  • On the next read, the app sees the dirty flag and treats it as a cache miss. It reads the fresh value from the database and refreshes the cache.

Pros

  • Good for read-heavy apps. It must be used with cache-aside or read-through; alone it does nothing.
  • Fixes the inconsistency between cache and database from Part 1.

Cons

  • New data always misses first: a POST never puts anything in the cache.
  • If the database is down, writes fail. Writes depend entirely on the database, so they aren't fault tolerant.
Strategy 4

Write-through

The write passes through the cache. First write into the cache, then, synchronously, into the database. Both must succeed. If the database write fails, roll back the cache write. If the cache write fails, fail the operation.

Pros

  • Cache and database always stay consistent.
  • Cache hit chance increases a lot: even brand-new data goes into the cache on write, so the "new data always misses first" problem is gone.

Cons

  • Alone it's not useful; it only adds latency (two writes instead of one). Always pair it with read-through or cache-aside, so something actually reads the cache.
  • Needs two-phase commit to keep both writes all-or-nothing (lecture 20).
  • If the database is down, writes fail, so it's still not fault tolerant.
Strategy 5 ★ the fault-tolerance one

Write-back (write-behind)

Write into the cache first, then write to the database asynchronously. The app pushes a message onto a queue and replies to the client right away. A worker reads the queue and writes into the database later.

  • Now writes don't depend on the database. If it's down for 2 hours but cached data lives for 24, writes and reads keep working from the cache. When the database comes back, the queue catches it up. This is the fault tolerance promised in Part 1.

Pros

  • Good for write-heavy apps.
  • Lower write latency: writing to a cache is faster than to a database, and nobody waits for the database.
  • Cache hit chance increases a lot: the cache always has the latest data.
  • Much better performance with read-through or cache-aside on top, so reads come from the cache too.
  • Writes keep working even when the database is down.

Con

  • If the data expires from the cache before the queue has written it to the database, it's in neither place. See the next section.
Picture it

A busy café cashier jots each order on a notepad (the cache) and drops a copy in a tray (the queue). The kitchen manager (the database) types the tray into the official ledger whenever they get a moment. Customers never wait for the ledger.

Write-back's catch

When the cache forgets before the database remembers

  1. Write 10: it's in the cache (TTL 3 h) and queued for the database.
  2. The database goes down for 5 hours. The queue waits and retries.
  3. At 3 hours, the TTL expires and 10 is removed from the cache.
  4. Now 10 is in neither the cache nor the database. Anything that reads or builds on it breaks.

The lecture's fix: keep the cache's TTL comfortably longer than any likely database outage, e.g. 2 days.

Both parts together

All five strategies at a glance

Strategy On read / write Best for Main weakness
Cache-aside Read: the app loads on a miss Read-heavy Stale without a write strategy; first read misses
Read-through Read: the cache library loads on a miss Read-heavy Same, and the cached data must match the table
Write-around Write: DB only, mark the cache dirty Read-heavy (paired) Write fails if the DB is down; new data misses
Write-through Write: cache then DB, synchronously Consistency + high hit rate Slower writes; needs 2PC; write fails if the DB is down
Write-back Write: cache now, DB later via a queue Write-heavy, fault tolerant Data gap if the cache expires before the DB write

Only write-back keeps writes working while the database is down. Write-around and write-through both fail writes when it is.

Beyond the course good to know as an engineer

Good to know as an engineer

Write-around in practice: just delete the key

The "dirty flag" is usually implemented by deleting the cache key after the database write. The next read misses and reloads. This cache-aside + delete-on-write pairing is the most common setup in real systems. Add a TTL as a safety net (see Part 1's race condition).

Write-through without real two-phase commit

  • Caches like Redis can't join a database transaction, so true 2PC across them is rare (lecture 20 covers 2PC itself).
  • Most systems write the database first (the source of truth), then update or delete the cache. If the cache step fails, a TTL or a retry repairs it. Writing the cache first risks showing data the database later rejects.
  • Managed read-through + write-through caches exist: e.g. Amazon DAX in front of DynamoDB handles both for you.

Write-back's other risks

  • Crash before flush: if writes sit only in cache memory, a cache crash loses them. The lecture's design pushes each write to a durable queue (e.g. Kafka, lecture 15), which closes that hole.
  • Ordering: two quick updates to the same key must reach the database in order, or the older one wins. Partition the queue by key, or attach version numbers.
  • Other readers of the database (reports, other services) see old data until the queue catches up.
  • Bonus: write-back can coalesce writes. A view counter bumped 1,000 times a second can be flushed to the database once a second. That's why likes, views and game scores often use it.

The missing topic: eviction policies

The lecture's outline promised eviction policies, but the video ends before them. A cache has limited memory, so when it's full, something must go:

Policy Evicts Good when
LRU (least recently used) The item untouched for the longest time Recent data is likely to be used again (the common default)
LFU (least frequently used) The item used the fewest times Some items stay popular for a long time; resists one-off scans
FIFO (first in, first out) The oldest inserted item Simple; age matters more than use
TTL-based Items closest to expiring Data has a natural lifetime

Redis controls this with maxmemory-policy: e.g. allkeys-lru, allkeys-lfu, volatile-ttl, or noeviction (refuse new writes when full). Note that Redis's LRU and LFU are approximate: they sample a few keys rather than tracking every one exactly. A write-back cache must never evict entries that haven't been flushed to the database yet.

Check yourself

Revision questions

Try answering out loud before opening each one.

How does write-around keep the cache from going stale?

It writes only to the database and invalidates (marks dirty) the cached entry. The next read treats it as a miss and reloads the fresh value.

Two weaknesses of write-around?

New data always misses on its first read, and writes fail when the database is down.

Describe write-through and its main pro.

Write into the cache, then synchronously into the database. Both succeed or both roll back. The cache and database stay consistent, and even new data hits the cache.

Why is write-through "useless alone"?

It just adds a second write (more latency). It only pays off when a read strategy actually serves reads from the cache.

Why does write-through need two-phase commit?

So the cache and database writes are all-or-nothing. Otherwise the cache could hold a value the database never stored.

How does write-back give fault tolerance?

Writes land in the cache plus a queue and return immediately. If the database is down, the system keeps working from the cache, and the queue writes to the database once it's back.

What goes wrong if the cache TTL is 3 h and the DB is down for 5 h?

After 3 h the value expires from the cache, but it hasn't reached the database yet, so it's in neither. The fix is a TTL longer than any expected outage (e.g. 2 days).

Which strategy keeps writes working when the database is down?

Only write-back.

LRU vs LFU?

LRU evicts what hasn't been used for the longest time. LFU evicts what has been used the fewest times.
