Idempotent POST APIs

Networks time out and users double-click, so the same request often arrives twice. For "add to cart" or "pay ₹10" that means two items or two payments. An idempotency handler makes retries safe: however many times a request arrives, it takes effect only once.

Idempotency vs concurrency

Concurrency

Many users, one resource. Example: on BookMyShow, many people try to book the same seat at once. Who gets it? That's a concurrency problem, covered in later lectures (24–28).

Idempotency

One client, the same request repeated. Example: "add to cart" sent twice because of a retry. It should add the item once. That's this lecture.

Definition

What idempotency means

Idempotency lets a client safely retry an operation as many times as it likes, without worrying about side effects. The first request does the work, and every repeat changes nothing.

Picture it

A lift button. Press it once and the lift is called. Press it ten more times and it doesn't send ten lifts. That's idempotent. A vending machine coin slot is not: insert the coin twice and you've paid twice.

Example: "add item to cart" creates a row saying Shreyansh added this item. If the request is retried, it must not create a second row. However many retries, the database holds exactly one.

HTTP methods

GET, PUT and DELETE already are. POST isn't.

Method Repeat it 5 times… Idempotent?
GET Just reads data. No change to the DB, however many times. yes, by nature
PUT "Update name SJ → Shreyansh". The first call changes it, and repeats find it already "Shreyansh". Same final state. yes, by nature
DELETE Deleting something already deleted leaves it deleted. yes, by nature
POST "SJ pays Hardik ₹10". Each call creates a new payment: −₹10, −₹10, −₹10… no, we must make it so

POST creates a new resource every time, so duplicates cause real damage: multiple payments, or the same item added to the cart several times. Only POST APIs need an idempotency handler.

The two ways duplicates arrive

Sequential and parallel duplicates

1 · Sequential: timeout, then retry

The client sends POST "add item to cart". The server starts processing but takes too long, so the client times out. The server finishes anyway and the item is added. The client thinks it failed and retries, sending a duplicate request.

2 · Parallel: two copies at the same moment

Two identical POSTs arrive at the same time (two browser tabs, a double tap), maybe even on different machines. Only one must be processed.

The approach

The idempotency key

Attach a unique ID to each operation, usually a UUID (universally unique identifier). Retries reuse the same ID, so the server can recognise "I've seen this one before."

Picture it

A cheque number. If the bank sees cheque #4417 twice, it knows the second one is a copy and doesn't pay it again, however many times it's presented.

The two agreements with the client

  1. The client generates the idempotency key. Usually a UUID from a library, sometimes combined with the operation name or a timestamp for extra uniqueness.
  2. Each different operation gets a new key. A retry of the same operation reuses its key. A genuinely new "add to cart" gets a fresh one.

The key's lifecycle

Status Meaning
created (or acquired) A request with this key has started but isn't finished yet.
consumed (or claimed) The operation succeeded and the resource exists. The key can't be reused.
The flow ★ draw this in the interview

Handling every request, step by step

  1. The client generates an idempotency key, say IK1.
  2. The client puts it in the request header and calls the server: POST /cart/items with header IK1.
  3. The server validates: is there a key in the header? No → HTTP 400 (validation error).
  4. The server reads the key from the DB.
  5. Not found (first time): insert IK1 | created.
    Found (a duplicate): check its status.
    • consumed: the original already finished, so return HTTP 200. The request succeeded earlier and nothing new is created.
    • created: the original is still running, so return HTTP 409 Conflict, meaning "already in progress, retry later".
  6. If the operation succeeds (item added), change the key's status to consumed and return HTTP 201 Created.
Response When
201 Created First request with this key, operation succeeded, resource created.
200 OK Duplicate. The original already completed, so no new resource.
409 Conflict Duplicate while the original is still processing. Retry later.
400 Bad Request No idempotency key in the header.

In the timeout-and-retry case, the server finished the original (status consumed) even though the client never saw the 201. The retry carries the same IK1, finds it consumed, and gets 200. No second item is added.

Follow-up 1

Two duplicates at the exact same moment

With two parallel requests carrying the same key, both can read the DB before either has inserted. Both see "not found", both insert, both do the work, and you get two items and two 201s.

  • The critical section is steps 4–5: read the key, and insert it if missing.
  • Protect it with mutual exclusion, for example a mutex, semaphore or synchronized block: acquire the lock, do the check and insert, then release.
  • Request 1 gets in first and inserts IK1 | created, then continues. Request 2 waits, then finds the key: 409 if R1 is still working, 200 if it's done.
Follow-up 2

Duplicates landing on different servers and databases

If the two copies go to different servers in different clusters, each with its own database, the DBs only sync with each other slowly (the lecture says it can take minutes). Neither server can trust its local DB to know about the other's key.

The lecture's answer: keep the keys and the lock in a cache, because cache synchronisation is far faster than DB synchronisation (near real time, in milliseconds).

Beyond the course good to know as an engineer

Good to know as an engineer

Use an atomic "insert if absent", not just an in-process lock

A mutex or synchronized block only protects requests on one server. With many servers, make the check and insert a single atomic operation in the shared store:

  • SQL: a UNIQUE constraint on the key column, then INSERT … ON CONFLICT DO NOTHING. If 0 rows were inserted, it's a duplicate.
  • Redis: SET ik:IK1 created NX EX 86400. NX means "only if it doesn't exist", which is the lock and the insert in one step.

On the lecture's cache answer: caches in different regions also replicate asynchronously. In practice, send every key to one authoritative store (one primary Redis or DB for that key, often chosen by hashing the key) rather than relying on fast replication.

Replay the original response

Store the original response (status and body) alongside the key. A duplicate then gets back exactly what the first request got: the same order ID, the same 201. Stripe does this: a retry with the same key returns the saved result instead of charging again.

Same key, different body is a client bug

Also store a hash of the request body. If a request reuses a key with a different payload, reject it. The IETF draft for the Idempotency-Key header suggests 422 for that case, and 409 while the original is still being processed, which matches the lecture.

Keys expire

Keys shouldn't live forever. Stripe keeps them for at least 24 hours. After pruning, the same key is treated as a new request. Give your keys a TTL that covers any realistic retry window.

What if the operation fails?

Decide what a failure does to the key. Usually, delete the created entry (or mark it failed) on a retryable error, so the client can retry with the same key. For a permanent error, store the error response so retries get the same answer.

Idempotent consumers

The same idea protects message consumers. Queues deliver at least once (lecture 5), so a consumer records each processed message ID and skips repeats. It's also why SAGA steps and outbox relays must be idempotent (lecture 4).

Check yourself

Revision questions

Try answering out loud before opening each one.

Idempotency vs concurrency?

Concurrency is many users competing for one resource, like a movie seat. Idempotency is the same client sending the same request more than once, which should take effect once.

Which HTTP methods are idempotent by nature, and why isn't POST?

GET, PUT and DELETE: repeating them leaves the same state. POST creates a new resource every call, so duplicates create duplicate payments or items.

Two ways duplicates happen?

Sequential: the client times out and retries, though the server already finished. Parallel: two identical requests arrive at the same moment.

The two agreements with the client?

The client generates the idempotency key (a UUID), and every different operation gets a new key. Retries reuse the same key.

Walk through the server's response codes.

No key in the header gives 400. Key not in the DB: insert it as created, do the work, mark it consumed, and return 201. Key found and consumed gives 200. Key found and still created gives 409 Conflict.

How do you stop two parallel duplicates both getting through?

Make "read the key, insert if missing" a critical section with mutual exclusion (a lock or mutex). In a multi-server system, make it an atomic insert-if-absent in a shared store.

Duplicates hit different clusters with separate DBs. Then what?

The lecture's answer: keep the keys and lock in a cache, which syncs much faster than DBs. In practice, route each key to one authoritative store.
