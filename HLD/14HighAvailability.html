High Availability

If your only database dies, your whole product dies with it. High availability means designing so that any one failure, even a whole data centre, doesn't take you down. The two classic patterns are active–passive and active–active.

The question ★ asked in many disguises

One question, many names

It's partly theoretical, but many practical questions are built on it. It can be asked as:

  • "Design a high availability architecture."
  • "Design a data resiliency architecture." Resiliency means the ability to come back from a failure.
  • "Design an architecture with 99.999% availability", the famous five nines. That's only about 5 minutes of downtime a year.
  • "Design an architecture with no single point of failure."
  • "What's the difference between active–passive and active–active?"

They're all the same goal: stay up even when something fails, and recover on your own.

The starting point

Single node: one database for everything

  • The client (mobile, laptop or desktop) goes through a load balancer to the application layer (microservices X, Y, Z, possibly several machines each), which all use one primary DB.
  • If that DB goes down, requests still reach the apps, but every read and write fails. The whole product is down.
  • That's not five nines, it is a single point of failure, and it can't recover on its own. Fixing it might take hours or even days.
Picture it

A shop with one cash register. However many staff you hire, if that one register breaks, nobody can pay until it's repaired.

The fix is multi-node: more than one copy, in more than one data centre. There are two flavours: active–passive and active–active.

Multi-node · pattern 1

Active–passive

Two data centres with identical application setups, say DC1 in Mumbai and DC2 in Pune. But only one database is the primary (also called the live or read/write DB). The other is a replica, and its data centre is the DR (disaster recovery) data centre.

  • A request lands in DC1: the apps read and write the primary DB right there.
  • A request lands in DC2: its apps send writes across to the primary in DC1.
  • Data is copied one way: primary → replica.
  • Improvement: DC2's apps can serve reads from the local replica (hence the name read-only DB). Only writes have to cross to DC1.

Why not let both databases take writes?

Traditional relational databases (Oracle, MySQL, PostgreSQL) are not multi-master in their standard setup. They write to one primary only, so you must pick which one is live.

Picture it

A head office (Mumbai) keeps the official ledger. A branch office (Pune) serves customers and can look things up in its photocopy of the ledger. But to record a new sale, it phones head office, because only head office writes in the real ledger.

Why it's resilient

Failover: when the primary dies

  1. The primary DB in DC1 goes down.
  2. Route DC1's traffic to the DR data centre.
  3. Promote DC2's replica to primary (read/write). It now takes all the traffic.
  4. When the old DB comes back, it becomes the replica / read-only DB.

So even with one database down, you keep serving users. No single point of failure, and the system recovers.

The costs

Disadvantages of active–passive

Problem Why
Extra latency A write arriving in Pune must travel to Mumbai's primary. If it takes 1 s via Mumbai, the same request might take about 2 s via Pune (the lecture's illustrative numbers).
A failover gap Switching traffic and promoting the replica takes time, say 10–15 minutes by hand. During that window, writes fail.
Wasted capacity The replica sits mostly idle. It handles reads at best, never writes.
Write bottleneck Every write in the system lands on one primary. A write-heavy app won't scale much this way.
Multi-node · pattern 2

Active–active

Use a database that supports multi-master: more than one live DB, all accepting writes at the same time. Cassandra and most NoSQL databases do this. Now both data centres are fully live.

  • Each DC's apps talk only to their own DB, for reads and writes. No cross-country hop.
  • Sync is bi-directional (active–passive is one-way).
  • Advantage: all resources are fully used, so you can handle much more traffic, including write-heavy loads. If one DC fails, the other already serves everything, with no promotion step.
Picture it

Two equal branch offices, each with its own ledger that it writes in directly. At the end of each day they exchange notes so both ledgers match. Faster for customers, but if both offices edit the same account on the same day, someone has to decide which edit wins.

The hard part

Keeping two live databases in sync

  • Write conflicts: the same row is changed in DC1 and DC2 at the same moment, and both try to replicate to each other. Which value wins? You need conflict resolution.
  • Stale reads: a write lands in DC1, but a read hits DC2 before the sync arrives, so it returns old data.

The lecturer stresses that this sync "looks easy but is where all the complexity lives". Conflict resolution gets its own later lectures.

Beyond the course good to know as an engineer

Good to know as an engineer

RPO and RTO: the two numbers every HA design is judged on

Term Question it answers Example
RPO (recovery point objective) How much data can we lose? "At most the last 5 seconds of writes"
RTO (recovery time objective) How long can we be down? "Back up within 2 minutes"
  • Asynchronous replication (the usual for cross-region) is fast but means RPO > 0. Writes that hadn't reached the replica are lost on failover.
  • Synchronous replication waits for the replica on every write. RPO = 0, but every write pays the cross-DC latency.

Automate failover, and guard against split-brain

  • Manual failover (the lecture's 10–15 minutes) is slow. Managed setups do it automatically: Amazon RDS Multi-AZ typically fails over in 60–120 seconds, and its newer Multi-AZ clusters in under 35 seconds. Tools like Patroni do the same for self-run PostgreSQL.
  • The danger is split-brain: a network blip makes the standby think the primary died, so both act as primary. Real systems use a quorum (a majority vote, as in lecture 2's consensus notes) and fencing to make sure the old primary is really stopped before promoting the new one.

Hot, warm and cold standby

Hot: a running replica, always in sync, so failover takes seconds to minutes. Warm: running but scaled down or slightly behind. Cold: backups only, to restore from, which takes hours. Cost goes down as RTO goes up.

Resolving active–active conflicts

  • Last-write-wins with timestamps: simple, but clock skew can silently drop data (lecture 9's notes).
  • Vector clocks to detect conflicts and let the app merge them (lecture 9), or CRDTs that merge automatically.
  • Avoid conflicts entirely by giving each record a home region. An Indian user's data is always written in Mumbai, a US user's in Virginia, and other regions only read it.

The lecture's "not multi-master" claim, updated

That's true of the standard single-primary setups. MySQL's Group Replication has a multi-primary mode (writes on any member, with conflict detection that rolls back one of two clashing transactions), and there are multi-master add-ons for PostgreSQL and Oracle. They exist, but they're complex and less common than single-primary with replicas.

Availability maths

  • In series (A needs B): multiply. 99.9% × 99.9% ≈ 99.8%.
  • In parallel (either can serve): two independent 99.9% sites give 1 − 0.001² = 99.9999% in theory. That's the whole point of a second data centre, though real failures are rarely fully independent.
  • Five nines (99.999%) allows about 5.26 minutes of downtime a year. A single manual failover can blow that budget.

Test it

An untested DR site is a hope, not a plan. Teams run regular failover drills ("game days") and chaos engineering, deliberately killing a node or a whole region to prove recovery works.

Check yourself

Revision questions

Try answering out loud before opening each one.

Name three other ways this question gets asked.

Design a data resiliency architecture, design for 99.999% (five nines) availability, design with no single point of failure. Or: active–passive vs active–active.

What's wrong with the single-node design?

The one DB is a single point of failure. If it goes down, all reads and writes fail, and recovery can take hours or days.

In active–passive, what happens to a write that lands in the DR data centre?

Its apps send the write across to the primary DB in the main data centre. Reads can be served from the local read-only replica.

Why can't Oracle, MySQL or PostgreSQL just write to both?

In their standard setups they're not multi-master: they accept writes on one primary only.

Walk through active–passive failover.

The primary fails, traffic is routed to the DR data centre, and its replica is promoted to read/write primary. When the old DB returns, it becomes the replica.

Four disadvantages of active–passive?

Extra latency for cross-DC writes, a failover gap during which writes fail, an idle replica, and a write bottleneck on the single primary.

What makes active–active hard?

Bi-directional sync: the same row written in two places at once (a conflict), and reads in one DC before another DC's write has synced (stale reads).

RPO vs RTO?

RPO is how much data you can afford to lose. RTO is how long you can afford to be down.
