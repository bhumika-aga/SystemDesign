Zero to a Million Users

You start with one computer doing everything. As users arrive, it breaks in a new place each time, and you fix that place. The lecture walks through nine fixes, in order. Each one solves the last step's problem and exposes the next.

Step 1 of 9

Single server

Everything lives on one machine: your code, your database, your files. This is how every college project starts, and it's fine when you have zero users.

Picture it

A tiny food stall with one person. They take orders, cook, and keep the groceries under the counter. It works for ten customers a day. At a thousand, the cook, the counter and the storage all get overwhelmed together, and if that one person falls sick the stall closes.

How it works

  1. The user types your domain name. DNS (the internet's phone book) turns it into your server's IP address. DNS is usually a paid third-party service, not something you run.
  2. The client sends an HTTP request (for example GET /tickets) to that IP.
  3. The server runs the business logic, reads or writes the database on the same box, and sends back HTML or JSON.

Why it stops working

  • Single point of failure. One crash, reboot or deploy takes the whole product offline.
  • Everything fights for the same CPU, RAM and disk. A heavy database query slows down every API call.
  • You can't scale the parts separately. If only the database needs more memory, you still have to upgrade the whole machine.
What breaks next → the app and the database need to stop sharing one machine.
Step 2 of 9

Separate the application server and the DB server

Put the application on one machine and the database on another. The lecture names these two layers the mid tier (business logic) and the data tier (storage).

Picture it

The stall moves its groceries into a separate storeroom next door with its own keeper. The cook has more space to cook, and the storeroom can grow without touching the kitchen.

Why this helps

  • Independent scaling. The app tier is CPU-heavy (running code). The data tier is memory- and disk-heavy (indexes, storage). Now you size each machine for its own job.
  • No resource fights. A slow query no longer starves the web process of CPU.
  • Security. The DB machine can sit on a private network with no public access. Only the app server can reach it.

Why it stops working

There is still exactly one application server. It can only handle so many requests per second. If it can do about 1,000 requests a minute, request number 1,001 gets slow or is dropped. And if it crashes, the site is down.

What breaks next → one application server is both a capacity limit and a single point of failure.
Step 3 of 9

Load balancer + multiple app servers

Run several copies of the application (App server 1, 2 … N) and put a load balancer in front. The client only ever talks to the load balancer, and the load balancer decides which app server gets each request.

Picture it

The stall becomes a restaurant with several cooks. A host stands at the door and sends each new customer to whichever cook is free. Customers never walk into the kitchen. If one cook goes home sick, the host stops sending people to them, and the restaurant stays open.

What the lecture stresses

  • Distributing traffic. As the name says, the load balancer spreads requests evenly so no single server is overloaded.
  • Security and privacy. The load balancer faces the internet. The app servers have private IPs, so a client (or an attacker) cannot call them directly. That adds a layer of protection.
  • Failover. If App server 1 dies, the load balancer routes its traffic to the others and the system stays up. If traffic grows, add App server N+1 and register it with the load balancer.
Beyond the lecture
  • Make the web tier stateless. If server 1 keeps a user's login session in its own memory, that user breaks when the next request lands on server 2. The fix is to store session data in a shared store (Redis or a NoSQL DB). Then any server can handle any request, and you can add or remove servers freely. The other option, "sticky sessions" that pin a user to one server, works against the whole point.
  • Health checks. The load balancer pings each server (for example GET /health every few seconds) and stops routing to one that fails.
  • Algorithms. Round robin, weighted round robin, least connections, IP hash. These are covered in HLD lecture 17 (Load Balancer and Different Algorithms).
  • The load balancer itself can fail. Real setups run a pair (active–passive) or use a managed cloud load balancer that is redundant internally.
What breaks next → the app tier now scales, but every server still hits one database. If it dies, everything dies.
Step 4 of 9 circled on the whiteboard: master–slave

Database replication

Keep several copies of the database. One master takes every write (create, update, delete). One or more slaves (also called replicas) hold copies and serve the reads. There can be many slaves.

Picture it

A teacher keeps the official register and is the only one allowed to write in it. Every evening, photocopies go to several assistants. When students ask "am I marked present?", any assistant can answer from their copy. If one assistant is absent, others answer. If the teacher is absent, one assistant is promoted to keep the official register.

Why this split works

Most apps read far more than they write. Think of how many times you scroll a feed compared to how often you post. With one master and many slaves, you can add read capacity just by adding slaves.

Failure cases the lecture walks through

  • A slave dies. Reads go to the other slaves. If it was the only slave, the master serves reads temporarily. A new slave is started to replace it.
  • The master dies. A slave is promoted to become the new master and starts taking writes. A fresh slave is then added.
  • This is the same idea as step 3. There, one app server failing didn't take the system down. Here, one DB node failing doesn't either.
Beyond the lecture
  • Replication lag. Copying to slaves is usually asynchronous, so a slave can be a few milliseconds (sometimes seconds) behind. A user who updates their profile and immediately reloads might read the old value from a slave. A common fix, called read-your-writes, sends that user's reads to the master for a short time after they write.
  • Sync vs async. Synchronous replication waits for the slave to confirm each write. That's safer but slower. Async is faster, but a master crash can lose the last few writes that hadn't reached a slave yet. That's why promoting a slave sometimes needs a data-recovery step.
  • Newer docs say primary / replica instead of master / slave. Same idea.
What breaks next → the system survives failures, but every read still goes to a database, which is slow.
Step 5 of 9 ★ important

Cache

A DB call is a network hop plus disk work, which makes it expensive. The lecture says to treat database operations as very, very expensive. A cache (for example Redis) keeps recently used data in memory so most requests never reach the DB.

Picture it

The chef keeps today's most-used ingredients on the counter within arm's reach, instead of walking to the storeroom for every order. Each item gets a "use by" label (the TTL). When the label expires, it goes in the bin, and the next time someone needs it the chef fetches a fresh one from the storeroom.

The read flow, step by step

  1. A request arrives at an app server.
  2. The app asks the cache first.
  3. Cache hit: the data is there, so return it immediately. No DB call.
  4. Cache miss: the data isn't there, so read it from the DB, write it into the cache, then return it.
  5. The next request for the same data is a hit. Performance goes up and DB calls are saved.

TTL (Time To Live)

Every cached item gets an expiry, set by the application. It could be 24 hours, 48 hours or 7 days, depending on how fresh the data needs to be. After the TTL passes, the item is removed. The next request misses, fetches fresh data from the DB and stores it again with a new TTL. Without a TTL, the cache would serve stale data forever.

Beyond the lecture
  • This pattern is called cache-aside (or lazy loading): the app manages the cache itself. Other strategies such as read-through, write-through, write-around and write-back are covered in HLD lectures 18–19.
  • When to cache: data that is read often and changes rarely (product details, user profiles, config). Don't use a cache as the only copy of important data, because memory is lost on restart.
  • Consistency: when the DB row changes, delete or update the cached copy. Otherwise users see old data until the TTL runs out.
  • Eviction: memory is limited. When it's full, something has to go. LRU (least recently used) is the usual choice; LFU and FIFO also exist.
  • A single cache node is a single point of failure. Run several cache nodes, and over-provision memory a little.
What breaks next → dynamic data is fast now, but users far from your server still wait for images, CSS and videos to cross the planet.
Step 6 of 9 ★★ very important

CDN: Content Delivery Network

A CDN is a network of servers spread across the world, called edge nodes or PoPs. They cache your static files close to users. The lecture's key line: a CDN does caching, but not everything that caches is a CDN. Redis caches too, but it isn't a CDN. A CDN also adds geographic spread and security.

Picture it

One big warehouse in India, with customers in the USA, France and Japan. Shipping every order from India is slow. So you open small corner shops in each country, stocked with the popular items that rarely change. Customers buy from the shop down the road. If the shop doesn't have something, it asks a nearby shop, and only then orders from the warehouse, keeping a copy for the next customer.

The problem: distance is latency

The lecture puts the data centre in India and has users in several countries. The farther the user, the longer each request–response round trip takes:

The user near the data centre gets a fast response, but you have users all over the world. That's the latency problem a CDN solves.

How a request flows

  1. The client requests a static file, for example https://cdn.site.com/logo.png. The CDN's routing sends it to the nearest node.
  2. Hit: the node has the file, so it returns it immediately.
  3. Miss: the node asks a neighbouring CDN node. If that one has it, it's copied over.
  4. If no node has it, the request goes to the origin server. The file comes back, the CDN stores it (with a TTL), and returns it.
  5. Later users in that region get it straight from the edge.

What goes on a CDN

Static content that changes rarely: HTML pages, CSS, JavaScript, images, video. Personalised, fast-changing API responses usually stay on your servers and the Redis cache.

Where it sits

The client goes to the CDN before it even reaches the load balancer. Static assets come from the CDN, and only dynamic requests travel on to the load balancer and app servers.

Three benefits the lecture lists

  • Performance: lower latency, because content is served from nearby.
  • Security: clients don't hit your origin directly. CDNs absorb DDoS attacks, because the flood is spread across hundreds of edge nodes. They can also detect bots and block them before they reach the origin.
  • Cost: the origin handles far less traffic, so you need fewer servers.
Beyond the lecture
  • Invalidation: to push a new CSS file before the TTL runs out, either call the CDN's purge API or, more often, version the URL (app.v42.css). A new URL is a guaranteed cache miss.
  • Cost: you pay per GB served. Don't put rarely accessed files on a CDN.
  • Fallback: if the CDN has an outage, clients should be able to fetch from the origin.
  • Well-tuned CDNs commonly reach 90%+ hit ratios on static content. Examples: Cloudflare, Akamai, AWS CloudFront, Fastly.
What breaks next → static files are close to users, but all the dynamic work still happens in one data centre. If India goes down, everyone goes down.
Step 7 of 9

Multiple data centres

Copy the whole stack (app servers, cache, master and slave DBs) into several data centres, for example India and the US. A geo-routing load balancer sends each user to their nearest data centre.

Picture it

The restaurant opens a full branch in another country, with its own cooks, counter and storeroom. Customers go to the branch nearest them. If one branch floods, the head office sends everyone to the other branch until it reopens. Every night the branches swap their record books so both know the same things.

How it works

  • Geo-routing: the load balancer (in practice usually GeoDNS) looks at where the request comes from and routes it to the closest data centre. Indian users go to India, American users go to the US.
  • Inside each data centre nothing changes: the load balancer feeds the app servers, the app servers talk to the cache, writes go to the master and reads go to the slaves.
  • Failover: if the India data centre goes down, the load balancer sends all traffic to the US data centre.
  • For that to work, the US data centre must already have India's data. That's why the databases replicate between regions.
Beyond the lecture
  • Capacity: each data centre must be able to take the other's traffic during failover, or the surviving one gets overwhelmed.
  • Data sync is the hard part. Cross-region replication is slow (hundreds of ms), so it's usually async. You have to decide what happens when both regions accept writes for the same record. HLD lecture 14 (Active–Passive and Active–Active) covers this in depth.
  • Deployments: keep every data centre on the same version with automated deployment tools, or users see different behaviour depending on location.
What breaks next → slow side-jobs (emails, notifications, webhooks) still hold up the user's request.
Step 8 of 9 ★★ very important

Message queue

A queue sits between the part of the system that creates work (the producer) and the part that does the work (the consumer or subscriber). The producer drops a message in and moves on immediately. This brings asynchronous processing into the system. Popular choices: RabbitMQ and Kafka.

Picture it

A waiter doesn't stand at the stove waiting for the dish. They clip the order ticket to the kitchen rail and go serve the next table. Cooks pull tickets off the rail when they're free. If a dish goes wrong, the ticket goes back on the rail to be cooked again.

Why it matters: the lecture's example

A user places an order. After saving it you need to send a notification, send an email and call a partner's webhook. These are heavy, slow operations. If the request thread does them one after another while the user waits, the thread is blocked and the user stares at a spinner. The lecture calls that a very bad design.

Instead, the app saves the order, pushes a message like {"event":"order_placed","id":123} to the queue, and responds to the user immediately. A subscriber reads the message and sends the email in the background.

  • Faster responses: the request doesn't wait for side-jobs.
  • Retries: if the consumer fails, the message can be requeued and tried again. Nothing is lost.
  • Decoupling: producers and consumers scale independently. If the queue grows, add more workers.
  • Buffering spikes: a sudden burst of orders piles up in the queue instead of crashing the workers.

RabbitMQ terminology

In RabbitMQ the producer doesn't write to a queue directly. It sends to an exchange, and the exchange decides which queue or queues get the message.

  • Routing key: a label the producer attaches to each message, like an address on an envelope.
  • Binding: the link between an exchange and a queue. Each binding has a binding key, which says what that queue wants to receive.
  • Exchange: compares the message's routing key with each binding key and delivers to the queues that match. Subscribers of those queues then get the message.

Exchange types

1 · Direct

routing key == binding key

Exact match only. A message with key email goes only to the queue bound with email. It's like a letter addressed to one flat number.

in lecture

2 · Fanout

ignore the key → every queue

A copy goes to every bound queue (Q1, Q2, Q3 …). The routing key is ignored. It's like a school-wide announcement. Use it for broadcasts, for example "price changed" to all services.

in lecture

3 · Topic

wildcard pattern match

Keys are dot-separated words. Bindings can use wildcards: * matches exactly one word and # matches zero or more. order.*.india matches order.placed.india. So topic is a wildcard comparison, while direct is an exact comparison.

in lecture

4 · Headers

match on message headers

Routes on header values (for example format=pdf) instead of the routing key. Rarely used.

from RabbitMQ docs
Beyond the lecture
  • RabbitMQ vs Kafka in one line each. RabbitMQ is a smart broker: it routes via exchanges, pushes messages to consumers and deletes them once acknowledged. Kafka is a distributed, append-only log: messages go to topics split into partitions, consumers pull and track their own position (offset), and messages are kept for days so they can be replayed.
  • Acknowledgements: a consumer confirms (acks) a message only after it has finished processing it. If it crashes before acking, the broker redelivers the message. That means a message can arrive twice, so consumers should be idempotent (see HLD lecture 13).
  • Messages that keep failing go to a dead-letter queue so they don't loop forever.
  • Full design of a queue system: HLD lecture 15 (Distributed Messaging Queue).
What breaks next → data keeps growing. Eventually one master DB can't hold it all or handle all the writes.
Step 9 of 9 ★★ very important

Database scaling

There are two ways to give the database more power: make the machine bigger (vertical) or add more machines (horizontal). Horizontal scaling for databases is implemented with sharding.

Picture it

A phone book gets too thick to hold. Vertical: buy a bigger table to rest it on, which only works up to a point. Horizontal: split it into two books, A–P and Q–Z. Each book is light, and you know which one to open by looking at the first letter of the name.

Vertical scaling (scale up)

  • Increase the capacity of existing DB servers: more CPU and more RAM.
  • It's simple, because no code changes. But there is always a limit: at some point you can't buy a bigger CPU. It also gets very expensive, and it's still one machine that can fail.

Horizontal scaling (scale out)

  • Add more database nodes, each holding part of the data.
  • It's harder to manage, but it has no fixed ceiling. The lecture's conclusion: vertical has limits, horizontal keeps scaling. Horizontal is implemented with sharding.

Sharding: horizontal vs vertical

Horizontal sharding (row-wise). Take a table with 1,000 rows and split the rows across tables on different machines. Every shard has the same columns but different rows.

You write a sharding logic (based on a sharding key) that decides which shard a row belongs to, and the app routes each query to that shard. Common strategies:

  • Range-based: A–P and Q–Z, or IDs 1–500 and 501–1000. Easy to understand, but ranges fill up unevenly.
  • Hash-based: shard = hash(user_id) % N. Spreads data evenly, but changing N moves almost every row.
  • Directory-based: a lookup table maps each key to its shard. Flexible, but the lookup table is one more thing that can fail.

Vertical sharding (column-wise). Split a table by columns. A table with columns C1–C10 becomes one table with C1–C5 and another with C6–C10, each keeping all the rows.

Generally horizontal sharding is preferred, but it depends on the requirement. Sometimes a vertical split is all you need.

Drawbacks of sharding

  • Uneven data and resharding. Suppose most users' names start with A–P. Shard ST1 fills up fast while ST2 sits half empty. Now ST1 has to be split again into ST1(1) and ST1(2), and those may split again. The shards grow into a tree, and data has to be moved each time.
  • Joins become hard. If ST1 and ST2 live on different machines, a SQL JOIN across them is slow or impossible. You end up fetching from both shards and joining in application code, or denormalising (duplicating data) so a query only needs one shard.
  • Hotspots, also called the celebrity problem. One key gets huge traffic, for example a celebrity's profile. The shard holding it melts while the others sit idle. (Web addition.)

The fix for the resharding problem is consistent hashing. When a shard is added or removed, only a small part of the data moves instead of almost all of it. It's a big topic, covered in the next lecture (HLD 6).

Beyond the lecture
  • Choosing the sharding key is the most important decision. Pick a key that spreads data and traffic evenly, and that most queries include (for example user_id).
  • Celebrity fixes: give hot keys their own dedicated shard, or split one hot key into sub-keys (celebId_0 … celebId_9) spread across shards.
  • Sharding and replication are used together: each shard is itself a master with its own slaves.
  • Transactions that span shards need distributed-transaction techniques such as 2PC or SAGA (HLD lectures 20–21).

The full picture

This is the architecture you end up with: CDN at the edge, geo load balancer, data centres with app servers, cache, queue and workers, replicated (and eventually sharded) databases.

Also worth knowing for interviews (not covered in the video)
  • Logging, metrics and automation: at scale, you need centralised logs, dashboards (CPU, latency, error rate, DAU) and CI/CD. Without them you can't see problems before users do.

Beyond the course good to know as an engineer

Good to know as an engineer

The nine steps get you to a million users. These are the practices that keep that system healthy day to day.

SLI, SLO, SLA: defining "fast enough" and "up enough"

Term Meaning Example
SLI (indicator) What you measure % of requests answered in under 300 ms
SLO (objective) Your internal target 99.9% of requests under 300 ms over 30 days
SLA (agreement) A promise to customers, with penalties 99.5% uptime or we refund 10%

The gap between 100% and the SLO is your error budget. While budget remains, ship fast. When it runs out, slow down and fix reliability. Measure p99 latency (the slowest 1%), not the average, because averages hide the users having a bad time.

Cache stampede (thundering herd)

Picture it

The shop's only bread tray empties, and every customer walks into the bakery kitchen at the same moment to ask for more. The fix is for one person to fetch a fresh tray while everyone else waits a second, or takes yesterday's loaf.

  • Request coalescing ("single flight"): only one request rebuilds the value, and the rest wait for it.
  • Stale-while-revalidate: keep serving the old value while one background refresh runs.
  • TTL jitter: add randomness to expiry times so keys don't all expire at the same second.
  • Early refresh: refresh a hot key shortly before it expires.

Autoscaling, backpressure and graceful degradation

  • Autoscaling: add or remove app servers automatically based on CPU, request rate or queue length (for example Kubernetes HPA or AWS Auto Scaling). Scale out early, scale in slowly.
  • Backpressure and load shedding: when overloaded, reject quickly with 429 or 503 instead of queueing forever. A fast "try again" beats a 30-second timeout.
  • Graceful degradation: decide in advance what to switch off under stress. Drop recommendations, reviews or animations, but keep search and checkout working.

Releasing safely

Strategy How Rollback
Rolling Replace servers a few at a time. Roll forward or back gradually.
Blue-green Run the new version (green) alongside the old (blue), then switch the load balancer over in one step. Instant: switch back to blue.
Canary Send 1–5% of traffic to the new version, watch error rates, then widen. Route the canary share back.

A canary is the same idea as the Strangler pattern's traffic split (lecture 4), applied to every release.

Observability: the three pillars

  • Metrics: numbers over time (QPS, error rate, p99, CPU). Prometheus and Grafana.
  • Logs: structured events per request, centralised (ELK, Loki).
  • Traces: one request followed across services (OpenTelemetry). See lecture 3's notes.
Check yourself

Revision questions

Try answering out loud before opening each one.

Why do app servers get private IPs behind the load balancer?

So the internet can't call them directly. Only the load balancer is public. That's an extra security layer, and it guarantees that every request goes through the load balancer's traffic distribution and health checks.

In master–slave replication, what happens when the master fails?

A slave is promoted to master and starts accepting writes, and a new slave is added to replace it. With async replication, the most recent writes may need recovering because the slave might have lagged behind.

Walk through a cache miss.

The app checks the cache and doesn't find the data. It reads from the DB, writes the result into the cache with a TTL, and returns it to the client. The next request for the same data is a cache hit.

"A CDN does caching, but not everything that caches is a CDN." Explain.

Redis caches data inside your data centre. A CDN is a geographically distributed network that caches static content near users. It also adds DDoS protection, bot filtering and lower origin load. Caching is one feature of a CDN, not the whole definition.

Where does the CDN sit in the request path?

Before the load balancer. The client fetches static files from the nearest CDN node. On a miss, the node asks a neighbouring node, then the origin. Only dynamic requests go to the load balancer.

Why use a message queue for sending emails after an order?

Sending email is slow. Doing it inside the request thread blocks the thread and delays the user. With a queue, the app publishes a message and responds right away. A consumer sends the email asynchronously, and on failure the message is requeued and retried.

Direct vs fanout vs topic exchange?

Direct: exact match of routing key and binding key. Fanout: copy to every bound queue, key ignored. Topic: wildcard pattern match on dot-separated keys (* = one word, # = zero or more words).

Horizontal vs vertical sharding, and which is usually preferred?

Horizontal splits rows across shards (same columns, different rows). Vertical splits columns (all rows, different columns). Horizontal is generally preferred for scaling, but the right choice depends on the requirement.

Name three drawbacks of sharding.

Uneven distribution that forces resharding, cross-shard joins becoming hard (so you denormalise), and hotspot or celebrity keys. Consistent hashing reduces how much data moves when shards change.
