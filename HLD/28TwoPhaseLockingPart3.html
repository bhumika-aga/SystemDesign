Two-Phase Locking · Cascading Aborts

Basic 2PL's second big problem: a transaction releases a lock before it commits, someone else reads that unfinished value, and then the first transaction aborts. Now the second must abort too, and possibly a third. The fix, strong strict 2PL (rigorous 2PL), holds every lock until the very end. It's the version real databases use.

The problem ★ why basic 2PL is avoided

A cascading abort, step by step

  1. A = 10, B = 5. Both transactions begin.
  2. T1 takes X(A) and X(B) (growing), then updates A to 11.
  3. T1 unlocks A, so its shrinking phase starts, but it hasn't committed.
  4. T2 immediately takes X(A) and works with A = 11. That's a dirty read (lecture 24).
  5. T1 aborts, and A is rolled back to 10.
  6. T2 built on a value that no longer exists, so T2 must abort too. That's a cascading abort, and anything that read from T2 would follow.
The fix

Strong strict 2PL (rigorous 2PL)

  • The growing phase works as usual: acquire locks gradually.
  • After that, no new or upgraded locks, and nothing is released until the end. Shared and exclusive locks are freed together, only at commit or abort.
  • So no one can ever read a value that might still be rolled back. No dirty reads, no cascading aborts.

Cons

  • Less concurrency than basic 2PL, because locks are held longer.
  • Deadlock is still possible, usually handled with a wait-for graph (lecture 27).

Why it's the one widely used

  • Cascading aborts are very expensive, since they throw away lots of work.
  • Deadlocks are rarer and cheap to detect and resolve with a wait-for graph.

One example, three ways · 1

Transfer ₹10 from A to B while someone adds A + B

T1 moves ₹10 from A to B. T2 computes A + B. Initially A = 100 and B = 100, so the correct total is always 200.

The lecture's "basic 2PL" run

Time Transaction 1 Transaction 2
t1–t3 X(A) · A = 100 − 10 · write A = 90
t4 unlock(A)
t5–t7 S(A) · read A = 90 · unlock(A)
t8–t10 S(B) · read B = 100 · unlock(B) · commit → 190 ✕
t11–t13 X(B) · B = 110 · unlock(B) · commit

T2 reports 190 instead of 200: it saw A after the transfer but B before it. No deadlock and no abort, just a wrong answer.

A correction: this run is not actually two-phase. T1 takes X(B) after releasing A, which the 2PL rule forbids (Part 1). Under real basic 2PL, T1 must lock B before unlocking A, so T2 would wait for B and read 110, giving 200. Basic 2PL's genuine problems are deadlocks and cascading aborts, not wrong totals.

One example, three ways · 2

Conservative 2PL: grab everything first

Time Transaction 1 Transaction 2
t1–t2 X(A), X(B) at the start
t3–t5 A = 90 · B = 110 · write both
t6 unlock(A)
t7–t9 S(A) ✓ · S(B) waiting…
t10 unlock(B) S(B) ✓
t11+ commit read A, B → 90 + 110 = 200 ✓ · unlock · commit

Correct, and no deadlock is possible. But T1 releases A before committing, so if T1 had aborted after t6, T2 would have read dirty data. A cascading abort is still possible.

One example, three ways · 3

Rigorous 2PL: hold everything until commit

Time Transaction 1 Transaction 2
t1–t3 X(A) · A = 90 · write A S(A) waiting…
t4–t5 X(B) · B = 110 · write B waiting…
t6 commit → all locks released
t7–t10 S(A) ✓ · read 90 · S(B) · read 110
t11 commit (releases its locks) → 200 ✓

T1 takes its locks gradually (A, then B) but keeps them all until commit. T2 can't see anything until T1 is final, so there are no dirty reads and no cascading aborts.

Beyond the course good to know as an engineer

Good to know as an engineer

Strict vs rigorous: two slightly different things

  • Strict 2PL: hold exclusive (write) locks until commit/abort. Shared (read) locks may be released earlier. That alone already prevents cascading aborts.
  • Rigorous / strong strict 2PL: hold all locks, shared and exclusive, until the end. It's what the lecture describes, and it's simpler to reason about because transactions are serialised in commit order.

The textbook ladder of "safe" schedules

Property Rule What it rules out
Recoverable If T2 read T1's write, T1 must commit before T2 does Committing on top of data that later vanishes
Cascadeless Only read values whose writer has already committed Cascading aborts
Strict Don't read or overwrite uncommitted values Dirty reads and dirty writes

Each row is a stricter subset of the one above. Strict 2PL produces strict schedules.

You already use this

  • In databases, a written row stays exclusively locked until commit at every isolation level (lecture 24). That's the strict part of strict 2PL, and it's why dirty reads are blocked from read committed upward.
  • At the serializable level, lock-based engines (SQL Server, MySQL InnoDB for locking reads) also keep read and range locks until commit. That's rigorous 2PL.
  • MVCC engines (PostgreSQL, Oracle) avoid dirty reads differently: readers see the last committed version, so a cascading abort can't happen in the first place.

The whole 2PL series in one line

Basic 2PL guarantees serializable results but can deadlock (lecture 26) and cascade aborts (this lecture). Conservative fixes deadlock, and rigorous fixes cascading aborts. Industry picks rigorous 2PL plus wait-for-graph deadlock detection (lecture 27).

Check yourself

Revision questions

Try answering out loud before opening each one.

What is a cascading abort?

T1 releases a lock before committing, T2 reads T1's uncommitted value, T1 aborts, and T2 must abort too because it used data that never really existed. This can chain further.

Which part of basic 2PL makes it possible?

Releasing locks during the shrinking phase before the transaction has committed.

How does strong strict (rigorous) 2PL prevent it?

It holds every lock until commit or abort, then releases them all at once, so no one can read uncommitted data.

Two downsides of rigorous 2PL?

Less concurrency, and deadlock is still possible.

Why is rigorous preferred over conservative?

Cascading aborts are very expensive, while deadlocks can be detected and resolved cheaply with a wait-for graph. Conservative also needs every lock known up front and cuts concurrency.

Basic, conservative, rigorous: which avoids what?

Basic: neither problem. Conservative: avoids deadlock (cascading abort is still possible). Rigorous: avoids cascading abort (deadlock is still possible).

Why did the lecture's "basic" transfer example produce 190?

T2 read A after the transfer and B before it. That happened only because T1 took a lock on B after releasing A, which breaks the two-phase rule. Proper 2PL would have given 200.
