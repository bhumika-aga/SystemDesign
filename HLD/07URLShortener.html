The question very common in product companies

What we're building

LinkedIn does this automatically: paste a long YouTube playlist link into a post and it becomes https://lnkd.in/dJkgzKxf. Both links open the same page. TinyURL is the classic public example.

Picture it

A cloakroom. You hand over your big coat (the long URL) and get a small numbered ticket (the short code). Show the ticket later and you get the same coat back. The whole design is about making sure no two coats ever get the same ticket number, even with many cloakroom attendants working at once.

Two APIs

  • POST a long URL. The service generates a short code, stores short → long in a table, and returns the short URL.
  • GET the short URL. The service looks up the code in the table and redirects the browser to the long URL.
short_url long_url
dJkgzKx https://www.youtube.com/playlist?list=PL6W8uoQQ2c61X…
00000g8 https://example.com/some/very/long/path?with=params
Requirement analysis

How short can the code be?

The interviewer says "as short as possible". That isn't a number. You work it out from traffic and the characters allowed.

Step 1: how many URLs must we support?

traffic = 10 million new URLs / day (given by interviewer)
per year = 10 M × 365 = 3,650 M
lifetime = 100 years (we don't want to run out)
total = 3,650 M × 100 = 365,000 M = 365 billion URLs

Step 2: which characters?

Usually 0–9 (10) + a–z (26) + A–Z (26) = 62 characters. Each position of the code can be any of 62, so a code of length L gives 62L combinations.

Length Combinations Enough for 365 B?
1 62 no
2 62² = 3,844 no
6 62⁶ ≈ 56 billion no
7 62⁷ ≈ 3.5 trillion yes

So the answer is 7 characters. Using a calculator for these powers is fine in an interview.

Generating the code · option 1

Why not just hash the long URL?

The obvious idea is to run the long URL through MD5 or SHA-1. The problem is that their output is far longer than 7 characters.

  • MD5 gives 128 bits = 16 bytes. One hex digit is 4 bits (a nibble), so that's 32 hex characters.
  • SHA-1 gives 160 bits = 20 bytes = 40 hex characters.

We need 7, so we'd have to trim to the first 7 characters and throw the rest away. Two different URLs can easily share the same first 7 characters, which is a collision: two long URLs mapped to one short code.

URL A → MD5 → 9e107d9d372bb6826bd81d3542a419d6 → keep 7 → 9e107d9 URL B → MD5 → 9e107d9f81c0a52d7e6f02b8c1d34a77 → keep 7 → 9e107d9 ✕ collision

Hash strings above are illustrative.

With billions of URLs, collisions would be frequent. That's why the lecture rejects hash functions.

Beyond the lecture

Some designs keep hashing but handle collisions: check the DB, and if the code is taken, append a salt to the URL and hash again. It works, but every write needs a DB lookup and may need retries. That gets slow at scale, which is why the ID-based approach below is preferred.

Generating the code · option 2 ★ the chosen approach

Base-62 encoding of a unique number

Give each URL a unique integer ID, then write that integer in base 62 using our 62 characters. A different ID always gives a different code, so there are no collisions by construction.

Picture it

We normally count with 10 symbols (0–9), so after 9 comes "10". Base 62 counts with 62 symbols: 0–9, then a–z, then A–Z. After 9 comes a, after z comes A, and only after Z do you roll over to "10". Big numbers get very short.

Digit values

0–9 → 0–9 · a → 10, b → 11, c → 12 … g → 16 … z → 35 · A → 36 … Z → 61

Worked example: 1000 in base 62

1000 ÷ 62 = 16 remainder 8
16 ÷ 62 = 0 remainder 16
read remainders bottom → top: 16, 8 → g, 8 → "g8"

This leaves two problems, and the lecture solves both:

  1. We need an ID generator that produces unique numbers across many servers (next section).
  2. The length varies. 1000 gave only 2 characters, but we want exactly 7 (section 6).
The real interview question ★★ "unique ID in a distributed system"

Generating unique IDs across many servers

At 10 million URLs a day, one database with an auto-increment column won't do. Its capacity is limited, and it's a single point of failure. With many servers, they must never hand out the same number. The lecture compares three approaches.

Approach 1: ticket server

A centralised auto-increment service that all app servers call. It's simple, and IDs are unique. But it's the same problem again: if the ticket server goes down, nobody can create a short URL. It's a single point of failure and also a bottleneck. Not much use at scale.

Approach 2: Snowflake (Twitter)

Each server builds IDs itself from the time, its own machine ID and a sequence number. Nobody needs to coordinate, because two machines can't share a machine ID and one machine never repeats a (timestamp, sequence) pair.

1unused
41 bits · timestampms since a custom epoch (~69 years)
10 · machineup to 1,024
12 · sequence4,096 / ms

The lecture: easy to implement because it depends on the timestamp, not on a central server. If two requests arrive in the same millisecond on different machines, the machine ID differs. On the same machine, the sequence number differs, and it resets once it hits its limit. (Exact bit sizes: see "Beyond the lecture".)

Approach 3: ZooKeeper ranges (the lecturer's preference)

  • Apache ZooKeeper is a coordination service. It helps distributed applications coordinate with each other reliably. It is not itself an ID generator. We put the range logic on top of it.
  • The total ID space is 0 to 3.5 trillion (62⁷). ZooKeeper splits it into ranges, for example 0–1M, 1M–2M, 2M–3M and so on.
  • Each server (worker) is allotted a range and uses only numbers inside it. Two servers can never collide.
  • When a server uses up its range, it asks ZooKeeper for the next unused range, say 13M–14M.
  • If a server dies halfway through its million, those unused numbers are lost. That's fine: we have 3.5 trillion and only need 365 billion.
Approach Unique? Single point of failure? Notes
One DB auto-increment Yes yes Doesn't scale. With multiple DBs you need synchronisation.
Ticket server Yes yes Central bottleneck.
Snowflake Yes no Time-ordered IDs. Depends on machine clocks.
ZooKeeper ranges Yes no Servers work independently inside their range. Some numbers are wasted, which is fine.
Beyond the lecture
  • Snowflake's real layout is 1 unused + 41 timestamp + 10 machine + 12 sequence = 64 bits. 41 bits of milliseconds is about 69 years. 12 bits allows 4,096 IDs per millisecond per machine. The 10 machine bits are often split into 5 datacenter + 5 worker.
  • A Snowflake ID is a 64-bit number (up to about 9.2 × 10¹⁸), which gives about 11 base-62 characters. It's bigger than the 7-character space, so for a 7-char shortener the range approach fits better.
  • Sequential IDs make short codes guessable (00000g8, 00000g9…). If that matters, shuffle the ID with a reversible bit permutation before encoding.
Fixing the length

Padding to exactly 7 characters

ID 16 in base 62 is just g, one character. Pad it to 7, for example 000000g (or with a padding symbol, the way base-64 uses ==).

Can a code ever exceed 7 characters? No. We only use IDs from 0 up to 62⁷ − 1 (about 3.5 trillion), which is ZZZZZZZ in base 62. Any ID in that range encodes to ≤ 7 characters: exactly 7 means use it as is, fewer means pad it.

Putting it together

Final design

  • Load balancer in front of multiple shortener servers, possibly across several data centres.
  • ZooKeeper hands each server its ID range.
  • DB: a relational DB is enough. It's one simple table (id, short_url, long_url).
  • Cache for popular short codes, since reads are far more common than writes.
  • No CDN is needed. The lecture notes the interesting part for interviewers is code generation, not the boxes.
Beyond the lecture
  • 301 vs 302 redirect: 301 (permanent) is cached by browsers, so repeat clicks skip your server. That's faster and cheaper, but you lose click analytics. 302 (temporary) sends every click through your server, so you can count clicks, countries and devices. Pick based on whether analytics matter.
  • Optional features to mention: custom aliases, expiry dates, and rate limiting on the POST API to stop abuse.
Beyond the course good to know as an engineer

Good to know as an engineer

Two more building blocks worth knowing, plus the problems a real shortener fights every day.

Key Generation Service (KGS)

An alternative to computing a code at write time: pre-generate unused 7-character codes in bulk and store them in a keys table.

  • Each app server grabs a batch of unused keys (say 1,000) into memory and marks them used in the table. Writes then need no computation or collision check at all.
  • If a server crashes, its unused batch is lost. That's the same trade-off as ZooKeeper ranges, and fine with trillions available.
  • Handing out batches must be atomic (a DB transaction or row lock) so two servers never get the same batch.

Bloom filter: a fast "definitely not" check

Picture it

A guest list where, for each name, you tick 3 boxes on a big grid. To check a name, look at its 3 boxes. If any box is empty, the person definitely isn't on the list. If all are ticked, they're probably on it, because other names might have ticked those same boxes.

  • No false negatives, some false positives. Very little memory: about 10 bits per item gives a roughly 1% false-positive rate.
  • Here: when using hashing or custom aliases, check "is this code already taken?" in memory before touching the DB.
  • Also used by LSM-tree databases (lecture 9's notes), CDNs, and to skip already-seen items in feeds.

What production shorteners worry about

  • Read-heavy traffic: reads can outnumber writes 100:1. Cache the hottest codes, since a small share of links gets most clicks.
  • Abuse: shorteners hide phishing and malware links. Scan destinations (for example Google Safe Browsing), rate-limit creation, and allow takedowns.
  • Expiry and custom aliases: store expires_at, and clean up in the background. Custom aliases need a uniqueness check.
  • Analytics pipeline: with 302 redirects, write click events to a queue (lecture 5's message queue) and aggregate them asynchronously. Never slow the redirect itself.
  • Storage choice at scale: one simple table works in SQL, but a key-value store (lecture 9) shards short → long lookups naturally.
Check yourself

Revision questions

Try answering out loud before opening each one.

How do you decide the short code length?

Estimate the total URLs (10 M/day × 365 × 100 years ≈ 365 billion) and count the allowed characters (62). 62⁶ ≈ 56 billion is too few, and 62⁷ ≈ 3.5 trillion is enough, so 7 characters.

Why not use MD5 or SHA-1?

They produce 32 or 40 hex characters. Trimming to 7 causes frequent collisions between different long URLs.

Convert 1000 to base 62.

1000 = 16 × 62 + 8, so the digits are 16 and 8, which is "g8".

Why is a ticket server a poor ID generator?

It's centralised: a single point of failure and a bottleneck for every write.

What are the parts of a Snowflake ID?

Timestamp (41 bits), machine ID (10 bits) and sequence number (12 bits), plus 1 unused bit.

How does the ZooKeeper approach guarantee uniqueness?

ZooKeeper allots each server a non-overlapping range of IDs. Servers generate only within their range, and ask for a new unused range when theirs runs out.

Can a base-62 code be longer than 7 characters?

No. IDs are kept below 62⁷ (ZZZZZZZ). Shorter codes are padded.
