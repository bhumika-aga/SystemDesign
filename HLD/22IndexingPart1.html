Step 1 · how data is really stored ★ follow-up questions live here

A table is only a logical picture

The neat grid of rows and columns (employee ID, name, address) is a logical view for you. The database doesn't store it that way. The DBMS packs rows into fixed-size chunks called data pages, typically 8 KB each (it varies by database).

Three things to understand before indexing makes sense: (1) how rows are actually stored, (2) what kinds of index exist, (3) the data structure behind an index.

Inside the box

Anatomy of a data page

Part Size Holds
Header 96 bytes Page number, free space left, checksum, etc.
Data records 8,060 bytes The actual rows, in the order they were inserted
Offset array 36 bytes An array where each slot points to one row in the data records area

How many rows fit? If one row is 64 bytes (e.g. ID 16 + name 16 + address 32), then 8,060 ÷ 64 ≈ 125 rows per page.

Rows R1–R5 are stored as they arrived, but the offset array might read R2, R4, R5, R3, R1. Why that order? It comes from indexing, covered in Part 2.

Down to the disk

Data pages live in data blocks

  • A table usually needs many pages. A 10,000-row table can't fit in page 1, so the DBMS creates pages 2, 3 … 100 as needed. The DBMS creates and manages pages.
  • Pages are finally written into data blocks: real physical storage on a disk or SSD. A block is the smallest amount of data one I/O operation reads or writes.
  • Blocks are managed by the underlying storage system, not the DBMS, and can be scattered anywhere on the disk.
  • Block sizes range from 4 KB to 32 KB (8 KB most common). An 8 KB block holds one 8 KB page. A 32 KB block can hold several.
  • So the DBMS keeps a mapping: page 1 → block 1, page 2 → block 1, page 3 → block 2…
The motivation

Without an index: check every row

Indexing makes database queries faster. Without it, the DBMS has no idea which page holds employee 35. It must load every page from disk and check every row: O(N). With millions of rows, that's slow.

The fix is a data structure that finds things in O(log N) for search, insert and delete: the B+ tree. First, its simpler cousin.

The data structure

How a B-tree works

  • Keeps data sorted, and all leaves are at the same level (balanced).
  • Order M: each node has at most M children and M − 1 keys. In an order-3 tree, each node holds 2 keys and 3 pointers.
  • The pointer left of a key leads to values less than it. The pointer right of it leads to values greater than or equal to it.
  • When a node overflows, it splits: the middle key moves up to the parent. If the parent overflows too, it splits as well, and a split at the top creates a new root.
  1. 9, 33 fit in one node.
  2. 75 → [9, 33, 75] is too many, so the middle key 33 moves up as a new root: [9] ← 33 → [75].
  3. 41 → ≥ 33, goes right: [41, 75]. 98 → [41, 75, 98] overflows, so 75 moves up: root [33, 75].
  4. 214 → goes right of 75: [98, 214].
  5. 126 → [98, 126, 214] overflows, so 126 moves up → root [33, 75, 126] overflows too, so 75 moves up into a new root.
  6. Later, 55 joins [41, 55]. 72 overflows it, so 55 moves up beside 33.
The real one

B+ tree: a B-tree with linked leaves

A B+ tree is the same as a B-tree, with an extra feature: the leaf nodes are linked to each other. DBMSs use a B+ tree to manage data pages and the rows inside them.

  • Leaf nodes hold the actual indexed column values, each with a pointer to the data page holding that row.
  • Root and internal nodes only hold signposts for faster searching ("go left / go right"). A signpost value may even belong to a row that was since deleted. It still works for steering.
  • That's why, when a leaf splits, the middle key is copied up (it must stay in the leaf as real data). When an internal node splits, the key just moves up.
Worked example

Building an index on EmpID

Table rows in insert order: 19·e1, 25·e2, 30·e3, 17·e4, 6·e5, 1·e6, 5·e7. There's an index on EmpID, the tree is order 3, and each data page holds at most 3 rows.

  • 19, 25 fill one leaf. 30 overflows it, so 25 is copied up: [19] ← 25 → [25, 30].
  • 17 joins [17, 19]. 6 overflows it, so 17 is copied up: root [17, 25].
  • 1 joins [1, 6]. 5 overflows it, so 5 is copied up → [5, 17, 25] overflows → 17 moves up as the new root (not copied, because that node is internal).
  • Read the leaves left to right: 1, 5, 6, 17, 19, 25, 30. Sorted.
Choosing a page

Which page does a new row go into? And page splitting.

  1. Find the new key's correct logical position in the B+ tree.
  2. Look at its nearest neighbour key: which data page is that row in?
  3. Look up that page's block in the mapping, load the page from disk, and try to insert the row.
  4. If it fits, store the row and record "this key → this page" in the leaf.
  5. If the page is full, page splitting happens: create a new page, divide the rows between the old and new page, then update the pointers for every key that moved and add the new page → block mapping.

Continuing the example: 6 fits in page 1 (17, 19, 6). Then 1 finds page 1 full, so it splits again: page 1 keeps 17 and 19, and new page 3 gets 1 and 6, whose pointers are updated. By the same rule, 5 lands in page 3 beside its neighbour 6.

Recap

How it all connects

Layer Managed by Job
Table (your view) Logical rows and columns, not how it's stored
B+ tree index DBMS Keeps keys sorted; each leaf key points to a data page
Data pages (≈ 8 KB) DBMS Hold the rows, plus a header and an offset array
Page → block mapping DBMS Remembers where each page was written
Data blocks (4–32 KB) Storage system Physical disk units; the smallest unit of one I/O operation

Beyond the course good to know as an engineer

Good to know as an engineer

Real page sizes differ by database

  • SQL Server: 8 KB pages, exactly the lecture's layout: a 96-byte header, up to 8,060 bytes of row data, and a row offset array at the end.
  • PostgreSQL: 8 KB pages with a 24-byte header. Line pointers (its offset array) grow from the front and rows grow from the back.
  • MySQL InnoDB: 16 KB pages by default.

Real B+ trees are wide and shallow

The order-3 tree is for teaching. A real index node is a whole page, so it holds hundreds of keys. With a fanout of ~500, three levels cover 500³ ≈ 125 million keys. That's why finding one row among millions takes only 3–4 page reads, and the top levels usually sit in memory (the buffer pool) anyway.

Why B+ and not plain B?

  • Internal nodes store only keys (no row pointers), so more keys fit per page. That means higher fanout and a shallower tree.
  • Linked leaves make range queries cheap: BETWEEN, >, ORDER BY. Find the start, then walk the leaf chain sideways.
  • Fun fact: the inventors never said what the "B" stands for. "Balanced", "Bayer" and "Boeing" are all popular guesses.

Page splits cost real performance

  • Splits mean extra writes and half-empty pages. Random keys (e.g. UUID v4) cause splits all over the tree. Increasing keys (auto-increment IDs, time-ordered UUID v7) mostly append at the right edge.
  • Databases leave room on purpose: InnoDB leaves about 1/16 of a page free, and SQL Server/PostgreSQL have a fill factor setting.
  • In InnoDB, the B+ tree's leaf pages are the data pages: rows sit inside the leaves, sorted by primary key. That's the "clustered index" idea Part 2 covers.

Indexes aren't free

Every index is another B+ tree to update on each insert, update and delete, and it uses disk space. Index the columns you filter, join and sort on, not every column.

A small precision on "blocks"

In practice, the DBMS maps a page number to a position in a file, and the operating system's file system maps that to physical blocks on the device. The lecture's point still holds: the database controls pages, not where they physically land.

Check yourself

Revision questions

Try answering out loud before opening each one.

Is a table stored as rows and columns on disk?

No, that's a logical view. The DBMS stores rows inside data pages (~8 KB), which are written into disk blocks.

What are the three parts of a data page?

A header (page number, free space, checksum; 96 bytes), data records (the rows; 8,060 bytes), and an offset array of pointers to each row (36 bytes).

About how many 64-byte rows fit in an 8 KB page?

8,060 ÷ 64 ≈ 125.

Data page vs data block?

The DBMS creates and manages pages. Blocks are physical storage units managed by the storage system: the smallest unit one I/O can read or write. The DBMS keeps a page → block mapping.

Why is a query without an index O(N)?

The DBMS doesn't know which page holds the row, so it must load every page and check every row.

In an order-M B-tree, how many keys and children does a node have?

At most M − 1 keys and M children. Left pointers lead to smaller values, right pointers to values greater than or equal.

B-tree vs B+ tree?

A B+ tree links its leaf nodes together. The leaves hold the real indexed values (with page pointers), while the internal nodes only hold signposts for searching.

How does the DBMS choose a page for a new row?

It places the key in the B+ tree, checks its neighbour key's page, loads that page and inserts the row there. If the page is full, it splits the page and updates the pointers and mapping.

What happens in a page split?

A new page is created, the rows are divided between the old and new page, the leaf pointers of moved rows are updated, and the new page's block mapping is recorded.
