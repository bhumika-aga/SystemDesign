Clustered & Non-clustered Indexes

Part 1 showed how a B+ tree indexes a column. A table can have many indexes, but only one of them decides the order of the rows themselves: the clustered index. All the others are separate lookup trees: non-clustered indexes. This part explains the difference, why only one clustered index is allowed, and what every extra index costs.

The map

From the DBMS's view, there are only two types

You've heard of primary indexes, secondary indexes, composite indexes… Internally, the DBMS sorts them all into two kinds: clustered and non-clustered. The primary key's index is usually clustered. Secondary and composite indexes are non-clustered.

Type 1

Clustered index: row order matches index order

A clustered index means the order of rows inside the data pages matches the order of the index.

  • Make EmpID the primary key and insert rows 1, 4, 5, 2. The DBMS builds a B+ tree on EmpID, which is sorted: 1, 2, 4, 5.
  • But the rows were written into the page as 1, 4, 5, 2. How can the page "match" the index?
  • This is what the offset array from Part 1 is for. Slot 0 points to EmpID 1, slot 1 to EmpID 2, slot 2 to 4, slot 3 to 5.
  • The rows themselves don't move. The offset array is kept in index order, so whenever the DBMS walks a page, it walks it slot by slot and sees the rows sorted.
Picture it

Books are shelved wherever there's a gap, but the shelf has a numbered list on the end: "1st alphabetically: 3rd book; 2nd: 1st book…". Follow the list and you read them in order without moving a single book.

The rule

Only one clustered index per table

Rows can be put in order by one thing at a time. If EmpID decides the order of the rows and pages, they can't also be ordered by Name. So a table has at most one clustered index.

Choosing it

Which column becomes the clustered index?

  1. If you manually specify a clustered index, that's used.
  2. Otherwise, the DBMS uses the primary key, which is unique and not null.
  3. If the table has no primary key, the DBMS creates a hidden column you can't see. It just increases (1, 2, 3, …) with every row, so it's guaranteed unique and not null, and it becomes the clustered key.

What if you add a primary key later to a 1-million-row table? The primary key now takes priority, so the DBMS has to rebuild the B+ tree, update all its pointers, load many pages from their blocks and reshuffle the rows. That's a lot of work.

Type 2

Non-clustered (secondary) indexes

  • Queries often filter on other columns, like WHERE name = 'A'. You can index those too. These are secondary (or composite) indexes, and internally they're non-clustered.
  • Each one gets its own B+ tree, sorted by its column (A, B, C, D), and each leaf points to the data page holding that row.
  • But they don't change the row order or the offset array. That's why they're "non-clustered": they don't cluster the rows.
  • A table can have many non-clustered indexes: Name, Address, …
Don't index everything

What every extra index costs

"Why not put a secondary index on all 10 columns, so every query is fast?" Because each index carries real overhead:

  • Memory and disk: each index is a whole B+ tree. With 1 million rows, that's about 1 million leaf entries per index, stored in index pages that live in data blocks on disk. The DBMS also tracks which block each index page is in.
  • Slower writes: every insert, update or delete must update the clustered index and every secondary index, removing leaf entries, fixing pointers, and possibly splitting pages.

So: create indexes carefully, for the columns your queries actually use.

Everything together

How a search for ID 35 actually runs

  1. Load the index pages (the B+ tree) from their data blocks into memory.
  2. Traverse the B+ tree to find which data page holds 35, e.g. data page 5.
  3. Look up the block for data page 5 in the page → block mapping, e.g. block 2.
  4. Load that data block into memory.
  5. Read the row. There's no need to touch the other thousands of blocks.

Beyond the course good to know as an engineer

Good to know as an engineer

In real engines, a secondary index usually points to the primary key

The lecture draws every index pointing straight at a data page. In practice it depends on the engine:

Engine Clustered index Secondary index leaf holds
MySQL InnoDB The table is the clustered B+ tree: full rows live in its leaves, sorted by primary key Indexed column + primary key value. A lookup walks the secondary tree, then the clustered tree.
SQL Server Optional. Leaves hold the rows. A table without one is a heap. Indexed column + clustered key (or a row ID, file : page : slot, for a heap)
PostgreSQL None that's kept up to date. Tables are heaps (CLUSTER reorders only once). Indexed column + tuple ID (page, slot), much like the lecture's picture

That's why a short primary key matters in MySQL and SQL Server: it's copied into every secondary index.

The "hidden column" is an InnoDB detail

InnoDB first falls back to the first UNIQUE NOT NULL index. Only if there's none does it create a hidden 6-byte row ID (GEN_CLUST_INDEX). SQL Server doesn't add a hidden column; the table just stays a heap. Also, the clustered key doesn't have to be the primary key. SQL Server lets you cluster on any column. Primary key is just the default.

Key lookups and covering indexes

  • If a query needs columns the secondary index doesn't contain, the database makes a second trip per row to fetch them (a key lookup or bookmark lookup). Thousands of matching rows means thousands of extra trips.
  • A covering index contains every column the query needs (as key columns, or as INCLUDE columns in SQL Server/PostgreSQL), so the second trip disappears.

Composite indexes: the leftmost-prefix rule

An index on (last_name, first_name) is sorted by last name, then first name. It helps WHERE last_name = … and WHERE last_name = … AND first_name = …, but not WHERE first_name = … alone. Put the most commonly filtered (and most selective) column first.

When an index won't help

  • Low-selectivity columns (e.g. a true/false flag): scanning is often cheaper than jumping in and out of the index.
  • Functions on the column (WHERE LOWER(email) = …) skip a plain index unless you create an expression index.
  • Check with EXPLAIN: it shows whether the database chose an index seek, a scan, or a lookup.
Check yourself

Revision questions

Try answering out loud before opening each one.

What does "clustered index" mean?

The order of rows inside the data pages matches the order of the index.

Rows were inserted 1, 4, 5, 2. How does the page appear sorted?

The rows stay where they are. The offset array's slots point to them in index order (1, 2, 4, 5), and the DBMS reads the page slot by slot.

Why only one clustered index per table?

Rows can be physically ordered by only one thing at a time.

How does the DBMS pick the clustered key?

A manually specified clustered index first, then the primary key (unique, not null). With no primary key, a hidden auto-increment column.

What's expensive about adding a primary key to a big table later?

It becomes the new clustered key, so the DBMS must rebuild the B+ tree, update pointers and reshuffle rows across many pages.

What is a non-clustered index?

A separate B+ tree on another column (secondary or composite). Its leaves point to data pages, but it doesn't change the row order. A table can have many.

Why not index every column?

Each index is another B+ tree stored in index pages on disk, and every write must update all of them, so it costs space and slows writes.

Walk through finding ID 35 with an index.

Load the index pages, traverse the B+ tree to find the data page, map that page to its block, load the block, read the row.
