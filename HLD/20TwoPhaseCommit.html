Distributed Transactions · 2PC

A transaction inside one database is easy: it either all happens or none of it does. But "place order" may need to update an order database and an inventory database. This lecture covers why one database's transaction can't cover both, and how two-phase commit (2PC) makes them agree, including what breaks when machines fail.

The basics ★ asked at every experience level

What is a transaction?

A transaction is a set of operations, a group of tasks, performed against the database as one unit.

The four properties

ACID

Property Means In the A → B example
Atomicity All operations succeed, or all fail. If "credit B" fails, "debit A" is rolled back too.
Consistency The database is in a consistent state before and after. Before: A = 100, B = 50. After: A = 0, B = 150. Never A = 0 with B still 50.
Isolation Concurrent transactions appear to run one after another (serialised). T1 (A → B) and T2 (B → C) running together behave as if all of T1 ran, then all of T2 (or vice versa), never interleaved. Row locks make this happen.
Durability Once committed, data survives even if the database fails. After commit, A = 0 and B = 150 stay that way even after a crash.
The easy case

A transaction in one database

BEGIN_TRANSACTION (on database T) withdraw ₹100 from A → lock row A, 200 → 100 deposit ₹100 to B → lock row B, 100 → 200 IF all succeeded → COMMIT (locks released, changes saved) ELSE → ROLLBACK (every change undone) CLOSE_TRANSACTION

This works because everything happens in one database, whose transaction manager can lock, commit or undo every step.

The problem

Two databases: one transaction can't cover both

The interview question: "How do you handle a transaction when the operations span multiple databases?" or "A transaction is local to one database, so how do you keep ACID in a distributed system?"

  • An e-commerce purchase touches the order DB (count 100 → 101) and the inventory DB (500 → 400).
  • Each database has its own transaction manager. The order update commits. Then the inventory update fails and rolls back only its own changes.
  • The order DB says "ordered" while inventory says "never shipped". Atomicity is broken.

Three ways to solve it

Approach Status Covered in
Two-phase commit (2PC) Very popular, widely used This lecture
Three-phase commit (3PC) Improves on 2PC, but rarely used (complex) Lecture 21
SAGA pattern Used a lot; solves a different set of problems Lecture 21 (and lecture 4)
2PC · the happy path

Phase 1: vote. Phase 2: decide.

2PC adds a transaction coordinator that talks to every participant (here, the order and inventory microservices). It must support all of them.

  1. The application gives the coordinator the set of operations. The coordinator starts the transaction and sends each participant its update. Each participant applies it and locks the rows, but doesn't commit.
  2. Phase 1, voting / prepare: the coordinator asks each participant "are you prepared to commit?". Each answers OK (yes) or NO.
  3. Phase 2, decision / commit: if every participant said OK, the coordinator sends COMMIT to all. Each commits, releases its locks and replies DONE.
  4. The coordinator closes the transaction and returns to the application.
Picture it

A wedding. The officiant (coordinator) asks each partner "do you?" (phase 1). Only if both say "I do" does the officiant declare them married (phase 2). If either says no, nobody gets married.

2PC · the abort path

One "NO" aborts everyone

The order update succeeded (it votes OK), but the inventory update failed (it votes NO). The coordinator commits only if all say OK. One NO means it decides ABORT and sends it to everyone. The order service rolls back the change it made but never committed. The transaction closes with nothing changed.

Recovery tool

Everyone keeps a log file

  • The coordinator and every participant keep their own log file on permanent storage.
  • Before sending each message, they write it to the log: "sent PREPARE", "sent OK", "decision: COMMIT", "got COMMIT".
  • If any of them crashes and comes back, it reads its log to see what happened last. That's what makes the failure cases below recoverable.
The real interview questions

What if a message is lost?

Two things fail: the coordinator or a participant. Either way, one of three messages goes missing.

Lost message Who's waiting What happens Safe?
1 · PREPARE never arrives (e.g. coordinator down) The participant, holding locks After a timeout, the participant aborts by itself. If PREPARE arrives late, it just answers NO, and the coordinator aborts everyone. safe
2 · OK never arrives (e.g. participant down) The coordinator After a timeout, the coordinator aborts the transaction. When the participant comes back, it asks "what happened?". The coordinator checks its log and says ABORT. safe
3 · COMMIT / ABORT never arrives (e.g. coordinator down) The participant, which already said OK The participant can't decide on its own. Others may have committed already. It must wait for the coordinator to come back and read the decision from its log. blocked
2PC's big weakness

Why 2PC is a blocking protocol

  • Once a participant has voted OK, it has promised it can commit. It may no longer abort on its own, because the coordinator might have told the others to commit.
  • If the coordinator dies between phase 1 and phase 2, the participant is blocked: its rows stay locked, and other transactions touching them wait too.
  • It ends only when the coordinator recovers, reads its log and resends the decision.

Fixing this blocking is exactly why three-phase commit exists. That's the next lecture.

Beyond the course good to know as an engineer

Good to know as an engineer

Where 2PC really runs

  • XA transactions: the standard interface that lets a transaction manager drive 2PC across databases and message brokers (e.g. Java's JTA with Atomikos or Narayana).
  • PostgreSQL: PREPARE TRANSACTION, COMMIT PREPARED and ROLLBACK PREPARED are exactly phase 1 and phase 2. A prepared transaction is written to disk and survives a crash. The docs warn not to leave transactions prepared for long, because they hold their locks. That's the blocking problem in practice.
  • Inside distributed databases: Google Spanner, CockroachDB and others use 2PC across shards, but make the coordinator itself a replicated group (via Paxos/Raft). If one coordinator machine dies, another replica already knows the decision. That's the practical cure for blocking.
  • Kafka's exactly-once transactions (lecture 15) use a 2PC-like protocol with a transaction coordinator and markers written to each partition.

Why microservices usually avoid 2PC

  • Locks held across network round trips slow everything and reduce throughput.
  • Availability: the transaction succeeds only if every participant and the coordinator are up. More services means more chances to fail or block.
  • Many datastores (most NoSQL databases, Redis, third-party APIs like a payment gateway) can't take part in XA at all.

That's why the SAGA pattern (lecture 21) is the usual choice between microservices. It gives up strict atomicity in exchange for availability, using compensating actions.

Two details interviewers like

  • Participants can sometimes help each other. A blocked participant can ask the others: if anyone already got COMMIT or ABORT, it can follow. If every participant voted OK and none heard the decision, they're all stuck until the coordinator returns.
  • "Consistency" in ACID ≠ "consistency" in CAP (lecture 2). ACID's C means "rules and invariants hold" (e.g. money isn't created). CAP's C means "every read sees the latest write".
  • "Isolation = serialised" describes the strongest level, serializable. Most databases default to weaker levels such as read committed for speed.
Check yourself

Revision questions

Try answering out loud before opening each one.

What do the letters of ACID mean?

Atomicity (all or nothing), Consistency (valid state before and after), Isolation (concurrent transactions appear serialised), Durability (committed data survives failures).

Why can't one database transaction cover the order DB and the inventory DB?

A transaction is local to one database. Each database has its own transaction manager, so a failure in one can't roll back what's already committed in the other.

Name the three ways to handle distributed transactions.

Two-phase commit, three-phase commit, and the SAGA pattern.

What happens in each phase of 2PC?

Phase 1 (voting/prepare): the coordinator asks every participant if it's prepared to commit, and each votes OK or NO. Phase 2 (decision/commit): if all said OK, send COMMIT to everyone. Otherwise send ABORT to everyone.

Why does everyone keep a log file?

Each writes every step to durable storage before sending a message, so after a crash it can read the log and know what it had decided or promised.

The PREPARE message is lost. What happens?

The participant times out and aborts on its own, which is safe. If PREPARE arrives later, it answers NO.

A participant's OK is lost. What happens?

The coordinator times out and aborts. When the participant recovers, it asks the coordinator, which reads its log and says ABORT.

Why is 2PC called blocking?

A participant that voted OK can't decide alone. If the coordinator dies before sending COMMIT or ABORT, the participant waits, holding its locks, until the coordinator recovers.
