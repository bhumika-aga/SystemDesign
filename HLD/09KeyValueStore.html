Design a Key-Value Store

How Amazon's Dynamo keeps a shopping cart working for millions of people, even while servers crash and networks split. The lecture builds it in six steps, and each step earns one of three goals: scalability, decentralisation and eventual consistency.

The question ★★ very important

Why a key-value store, and what it must achieve

Amazon built Dynamo (which led to DynamoDB) for features like "Add to cart". Every cart is looked up by one key (the user or cart ID), and the store must never refuse a write. A customer who can't add to their cart is lost revenue.

Picture it

A giant coat-check with thousands of attendants spread across many rooms. Any ticket number tells you exactly which room holds the coat. Every coat is also kept in two other rooms in case one room floods. The attendants chat constantly so everyone knows who's still at work.

Three goals

  1. Scalability: millions or billions of users across regions. One machine and one hash table can't hold that.
  2. Decentralisation: no single node whose failure takes the system down. Every node is equal.
  3. Eventual consistency: a read might briefly return stale data, but replicas converge on the latest value.
Step 1 · achieves scalability

Partition with consistent hashing

The first idea in an interview is "a hash table", but one machine won't scale. So split the key space across many servers using consistent hashing (lecture 6).

  • Servers sit on a virtual ring, and each owns a range: S1 1–50, S2 51–100, S3 101–150, S4 151–200.
  • To store a value, generate its key: car → 45. 45 falls in 1–50, so S1 stores it. India → 175 goes to S4.
  • Hot ranges: if lots of popular keys fall in 1–50, S1 gets bombarded. The fix is virtual nodes: each server appears at several points on the ring, so traffic spreads across S1, S3, S4 and others.
Step 2 · achieves decentralisation

Replication: coordinator, replicas and the preference list

If S1 is the only server holding "car" and S1 dies, get(K1) fails. So every key is stored on N servers. N is configurable and defaults to 3.

  • Coordinator: the server whose range the key falls in (S1 for key 45).
  • Replicas: the coordinator walks clockwise and copies the key to N − 1 more servers.
  • Replica choice isn't strictly the next server. It skips virtual nodes of a server already chosen (S1 appearing again doesn't count), and can prefer servers in different data centres. If one data centre catches fire, the copies survive.

The preference list ★ key idea

For each key range, every server knows the list of servers responsible for it. The coordinator comes first, then the replicas.

Key range 1st (coordinator) Replica Replica
1 – 50 S1 S2 S3
51 – 100 S2 S3 S4
101 – 150 S3 S4 S1
151 – 200 S4 S1 S2

If the coordinator is down, the next server in the preference list takes the request. This is what makes the system decentralised: there's no master.

Step 3

Put and get operations

Put

  1. put(K1, car). Find the key (45), which goes to coordinator S1. S1 writes it locally.
  2. S1 checks its preference list and sends the copy to S2 and S3 asynchronously (in parallel, without waiting in line).
  3. S1 replies success once W replicas have acknowledged. With W = 1, the first ack is enough.

There is no separate "update" call. In DynamoDB, creating a new key and changing an existing one are both a put. That matters in step 4, where several puts to the same key create competing versions.

Get

  1. get(K1) reaches coordinator S1.
  2. S1 asks the replicas (S2, S3…) for their copy of K1.
  3. It waits for R responses (say R = 2), not all of them, then returns to the client.

The quorum rule: R + W > N

Symbol Meaning
N Number of copies of each key (replication factor, default 3)
W Acks the coordinator waits for before a write counts as successful
R Responses the coordinator waits for before a read counts as successful

If R + W > N, the set of nodes you read from always overlaps the set that took the latest write, so at least one response has the newest version. Lower R or W means faster responses but a higher chance of stale data.

Who receives the request? Two kinds of load balancer

  • Generic LB: the request lands on any node (say S4). S4 checks the preference list, sees it isn't the coordinator, and hops the request to S1, or to the next in the list if S1 is down. Simple to build, but higher latency.
  • Partition-aware LB: knows the ring, so it sends the request straight to the coordinator. Low latency, but you must build ring logic into the LB.
Step 4 · achieves eventual consistency ★ trickiest part

Data versioning with vector clocks

Why does get ask several replicas instead of just the coordinator? Because failures can leave replicas holding different versions of the same key, and the system has to detect that.

Picture it

Each version carries a list of signatures: "S1 edited this twice, S2 once". If one version's signatures include everything the other's has, it's clearly newer. If each has a signature the other lacks, two people edited in parallel and a human (the app) must merge them.

A vector clock is a list of [server, counter] pairs kept with each version of a value.

The lecture's example: K1 in the range 1–50, preference list S1, S2, S3

# What happens Resulting version
1 put(K1, car) handled by S1 car [S1,1]
2 put(K1, cart) handled by S1. It knows [S1,2] replaces [S1,1], so the old one is discarded. cart [S1,2]
3 S1 goes down. put(K1, carm) goes to the next in the list, S2. The S2–S3 link is also broken. carm [S1,2][S2,1]
4 At the same time, put(K1, carr) is handled by S3 carr [S1,2][S3,1]
5 S1 comes back. get(K1): S1 collects cart [S1,2], carm [S1,2][S2,1] and carr [S1,2][S3,1] cart is older than both. carm and carr are a conflict.
6 S1 can't decide, so it returns both versions. The client (the Add-to-cart service) reconciles them and writes back. merged [S1,3][S2,1][S3,1]
  • Reconciliation is done by the client, using an algorithm such as last-write-wins or a semantic merge. A cart can take the union of items.
  • This is eventual consistency: the first read may return stale or conflicting data, but after reconciliation every replica converges.
  • In CAP terms, Dynamo is AP. It gives up strict consistency for high availability, so writes are never refused.
Beyond the lecture: sloppy quorum and hinted handoff

When a replica in the preference list is temporarily down, Dynamo writes the copy to the next healthy node instead, with a hint saying who it's really for. When the original node returns, the stand-in hands the data back and deletes its copy. Writes keep succeeding through short outages. Merkle trees (step 6) handle longer, permanent divergence.

Step 5

Gossip protocol: who's alive and who owns what

Every node has to know every other node's range and whether it's up. There's no central registry, so nodes gossip.

  • Each node keeps a membership list: every server, its heartbeat counter and when it was last updated.
  • Every second (or other set interval), a node increments its heartbeat and sends it, with extra info like "I own 151–200", to random nodes. They pass it on, and soon everyone knows.
  • If S2's counter stops rising for a long time, nodes suspect it's down. When more than one node reports the same, S2 is marked down and taken out.
Node Heartbeat counter Last updated Status
S1 1042 12:00:05 up
S2 712 10:00:00 suspected down
S3 998 12:00:04 up
S4 1017 12:00:05 up

Step 6

Merkle tree: finding stale replicas cheaply

Say S1 (coordinator for 1–1000) and its replica S2 have drifted, and keys 500–700 on S2 are out of date. Comparing a million keys one by one is too slow. A Merkle tree finds the differing keys by comparing only a few hashes.

  1. Each server builds a tree over its key range. Leaves hash individual keys, and each parent hashes its children.
  2. Compare the roots. If they're equal, every key matches and you're done, even for a million keys.
  3. If they differ, go down one level and compare children. Only descend into subtrees whose hashes differ.
  4. You end at exactly the keys that are out of date and sync only those. It's like a binary search, O(log n) comparisons.
Beyond the lecture
  • Dynamo runs this anti-entropy check in the background. Cassandra, Riak and Git use the same idea, and so do blockchains.
  • DynamoDB, the AWS product, has since moved away from some of these designs (for example it offers strongly consistent reads and doesn't expose vector clocks), but the Dynamo paper is still the classic interview reference.
Beyond the course good to know as an engineer

Good to know as an engineer

The lecture covers how data moves between nodes. This is how each node actually stores it, plus a few failure details that bite in production.

Inside one node: the LSM tree

Picture it

A busy office writes every new note on a sticky pad (fast), and also jots it in a diary in case of a fire. When the pad fills up, it's filed as a sorted folder. Every so often, old folders are merged into bigger ones and outdated notes are thrown away.

  • WAL (write-ahead log): every write is appended to a log on disk first, so a crash loses nothing.
  • Memtable: a sorted in-memory structure. Writes land here, which is very fast.
  • SSTables: when the memtable fills up, it's written to disk as an immutable, sorted file.
  • Compaction: a background process merges SSTables and drops overwritten and deleted values.
  • Reads: check the memtable, then SSTables from newest to oldest. A Bloom filter per file skips files that definitely don't have the key.
  • Used by Cassandra, RocksDB, LevelDB and HBase. (DynamoDB, the AWS product, instead keeps a write-ahead log plus a B-tree on each replica.) Contrast with the B+ tree (HLD lecture 22), used by most SQL databases: LSM favours writes, B+ trees favour reads.

Deletes are writes: tombstones

  • Files are immutable, so a delete writes a tombstone marker ("K1 is deleted as of time T"). Compaction eventually removes the data.
  • Gotcha: if a replica was down when the tombstone was written, and the tombstone is purged before that replica catches up, the deleted data can come back ("zombie data"). Cassandra waits a grace period (gc_grace_seconds, 10 days by default) before purging for this reason.
  • Lots of tombstones make reads slow. Queue-like "insert then delete" workloads are a known anti-pattern in these stores.

Read repair

During a get, the coordinator already collects R responses. If one replica returns an older version, the coordinator writes the newest version back to it on the spot. Frequently read keys heal quickly, and Merkle-tree anti-entropy catches the rest.

CRDTs: conflicts that merge themselves

  • Conflict-free Replicated Data Types are data structures designed so that any two replicas can merge in any order and always reach the same result, with no client reconciliation needed.
  • Examples: G-Counter (each node counts its own increments, merge = take the max per node, value = sum), and OR-Set (add and remove items, where concurrent add and remove resolve predictably).
  • A shopping cart as an OR-Set would have merged carm and carr automatically. Used by Riak, Redis active-active, and collaborative editors.

Clock skew and "last write wins"

  • LWW picks the version with the latest timestamp, but server clocks drift apart by milliseconds or more.
  • If S2's clock runs 2 s fast, its older write can "win" over a genuinely newer write on S3, and the newer data is silently lost.
  • That's why Dynamo used vector clocks (causality, not wall time). Other systems use hybrid logical clocks, or Google Spanner's TrueTime (GPS and atomic clocks with bounded uncertainty).
Check yourself

Revision questions

Try answering out loud before opening each one.

Three goals of the key-value store and which step achieves each?

Scalability comes from partitioning with consistent hashing. Decentralisation comes from replication, the preference list and gossip. Eventual consistency comes from vector clocks and Merkle trees.

What is the coordinator, and where do replicas go?

The coordinator is the server whose range the key falls in. It copies the key to the next N − 1 servers clockwise, skipping repeat virtual nodes and preferring other data centres.

What is the preference list for?

For each key range, it lists the coordinator first and then the replicas. Any node can forward a request to the right place, or fall back to a replica when the coordinator is down.

What do N, R and W mean, and why R + W > N?

N is the number of copies, W the acks needed for a write, and R the responses needed for a read. If R + W > N, read and write sets overlap, so a read sees the latest write.

Generic vs partition-aware load balancer?

Generic sends the request to any node, which hops it to the coordinator. That's simple but slower. Partition-aware sends it straight to the coordinator, which is fast but needs ring logic in the LB.

How do vector clocks detect a conflict?

Each version carries [server, counter] pairs. If one clock contains all of the other's entries, it's newer. If each has an entry the other lacks (for example [S2,1] vs [S3,1]), they're concurrent, so both are returned for the client to merge.

How does gossip detect a failed node?

Nodes exchange heartbeat counters with random peers. If a node's counter stops rising and more than one peer notices, it's marked down.

What does a Merkle tree save?

You compare a few hashes from root to leaves instead of every key, and sync only the ranges whose hashes differ.
