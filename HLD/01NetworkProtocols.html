Network Protocols

Two computers can only talk if they follow the same rules: who speaks first, what a message looks like, what happens when one goes missing. Those rules are protocols. This lecture covers the ones you'll name in almost every system design: HTTP, FTP, SMTP, WebSockets, WebRTC, TCP and UDP.

What is a network protocol?

When two computers communicate over a network, a protocol is the agreed set of rules for that conversation: how to start it, what format each message uses, and how to end it.

Picture it

Two people who speak different languages can't chat. If both agree to speak English, take turns, and say "over" at the end of each sentence (like a walkie-talkie), they can. A protocol is that agreement, written down so every computer follows it exactly.

The layers

Networking is split into 7 layers (the OSI model): Application, Presentation, Session, Transport, Network, Data link, Physical. Each layer relies on the one below it. Your chat message is built at the top, handed down, sent across the wire as signals, and rebuilt layer by layer on the other side.

For system design, two layers matter most, and they're all this lecture covers:

  • Application layer: what the apps say to each other (HTTP, FTP, SMTP, WebSockets, WebRTC).
  • Transport layer: how the bytes get delivered (TCP or UDP).
Beyond the lecture

In practice the internet runs on a simpler 4-layer TCP/IP model: Application (OSI 5–7 merged), Transport, Internet (IP), Link. When people say "TCP/IP" they mean TCP at the transport layer running on top of IP at the network layer. IP handles addressing (getting a packet to the right machine); TCP or UDP handles delivery (getting it to the right app, reliably or fast).

Application layer · part 1

Client–server vs peer-to-peer

The lecture splits application-layer protocols into two families, based on who is allowed to talk to whom.

Picture it

Client–server is a shop: customers ask, the shopkeeper answers, and customers never serve each other. Peer-to-peer is friends swapping books directly: everyone can both give and receive, and there's no shop in the middle.

Client–server model

  • The client always starts the conversation. The server waits and responds.
  • Protocols in this family: HTTP, FTP, SMTP (with IMAP / POP3), WebSockets.
  • WebSockets is the odd one out: it's still client–server, but once connected the server can also send messages on its own (step 6).

Peer-to-peer (P2P) model

  • There's no server in the middle for the actual data, so data goes directly from peer to peer. That makes it fast.
  • The lecture's P2P protocol is WebRTC (step 7).
Client–server · 1

HTTP and HTTPS

HyperText Transfer Protocol is the language of the web. The browser asks for a page or an API response, and the server replies. It's the default choice for most APIs you'll design.

Picture it

Ordering at a counter: you ask for one thing, get it, and the conversation is over. Want something else? You queue up and ask again. The counter doesn't remember what you ordered last time unless you show your receipt (a cookie or token).

  • Connection-oriented: HTTP runs over TCP, so a connection is set up before any data is sent (the lecture marks HTTP as "1 connection").
  • Hypertext: pages contain links, so you can jump from one page to another.
  • Request → response: methods like GET, POST, PUT and DELETE, answered with status codes like 200 OK or 404 Not Found.
  • HTTPS = HTTP + encryption (TLS). This is what everyone uses now, because plain HTTP can be read by anyone on the network path.
Beyond the lecture
  • Stateless: each HTTP request stands alone, and the server doesn't remember the previous one. Logins work by sending a cookie or token with every request.
  • Versions: HTTP/1.1 (one request at a time per connection), HTTP/2 (many requests share one connection), HTTP/3 (runs over QUIC, which is built on UDP, for faster setup on mobile networks).
  • HTTP can't push to the client on its own. That's why chat apps need WebSockets, or workarounds such as long polling.
Client–server · 2

FTP: File Transfer Protocol

Built to move files between machines. What makes it different is that it uses two connections, compared with HTTP's one.

Picture it

A phone call with a manager, plus a delivery truck. The phone line (control) stays open the whole time so you can say "send file A… now file B". A truck (data) is sent for each file and comes back empty.

  • Control connection: carries commands (login, list files, "get report.pdf"). It stays up for the whole session.
  • Data connection: carries the file itself. It's created for a transfer and disconnected after.
  • Why it's rarely used today: FTP is not encrypted. Usernames, passwords and files travel as plain text, so it isn't secure. Files are now usually moved over HTTPS, or with SFTP / FTPS (secure variants).
Client–server · 3

Email: SMTP, IMAP and POP3

Email uses different protocols for sending and reading. SMTP sends mail. IMAP or POP3 read it. SMTP is always paired with one of the other two, most commonly IMAP.

Picture it

SMTP is the postal service carrying your letter to the other person's post office. IMAP is reading your letters at the post office, so they stay there and you can read them from any branch. POP3 is taking the letters home. They're off the post office shelf, so only that one home has them.

  • User agent: the app you use (Gmail, Outlook).
  • MTA client → MTA server: the mail servers that pass the message across the internet using SMTP.
  • POP3: reads the mail, downloads it, and deletes it from the server. Only the device that downloaded it has it.
  • IMAP: reads the mail from the server and keeps it there, so you can read the same mail on your phone, laptop and tablet. That's why SMTP + IMAP is the widely used combination.

The lecture doesn't go deep into SMTP. The point is that this is another client–server example.

Client–server · 4 ★ key for chat apps

WebSockets

A WebSocket is a client–server connection that stays open and works in both directions. The client can send to the server, and the server can send to the client without being asked. That's the only difference from HTTP, and it's the reason every chat app uses it.

Picture it

HTTP is sending letters: the server can only reply to a letter you sent. A WebSocket is a phone call that stays connected, so either side can speak at any moment. When your friend sends you a message, the server just says it down the line.

A common mistake: WebSocket is not peer-to-peer

People often assume WebSockets are P2P because messages seem to go from user to user. They don't. Client 1 talks to the server, and the server talks to Client 2. There's no direct Client 1 ↔ Client 2 link. It's client–server with two-way talking.

Why messaging apps need it

With plain HTTP, Client 2 would have to keep asking "any new messages?" every second. That's called polling, and it's inefficient: millions of requests, mostly with nothing new. With a WebSocket, the server pushes the message the instant it arrives. This is why a WhatsApp or Telegram design uses WebSockets.

Beyond the lecture
  • A WebSocket starts life as an HTTP request with an Upgrade: websocket header. The server answers 101 Switching Protocols, and from then on the same TCP connection carries two-way messages (ws://, or wss:// when encrypted).
  • Each open connection uses server memory. A chat system with millions of online users needs many servers just to hold connections, plus a way to find which server a user is connected to.
Peer-to-peer ★ key for video calls

WebRTC

Web Real-Time Communication is a peer-to-peer protocol. Browsers send audio and video directly to each other, and it uses UDP underneath to be fast. Think Google Meet, video calls, live streams and games.

Picture it

A friend introduces you to someone at a party, then walks away. You two chat directly from then on. The friend (signalling server) only helps you find each other. The conversation itself doesn't go through them.

  • Fast because data doesn't go through a server. It goes straight from peer to peer.
  • Uses UDP because in a live call, speed matters more than perfection. A lost video frame is better than a frozen call waiting for it to be re-sent.
Beyond the lecture
  • Signalling (exchanging "here's how to reach me" offers) isn't part of WebRTC. Apps usually do it over a WebSocket.
  • Most devices sit behind home routers (NAT) and don't know their public address. A STUN server tells a peer its public IP. If a direct path still can't be made (strict firewalls), a TURN server relays the media. That's slower, but it works.
  • Big group calls usually add a media server (SFU) that forwards streams, because a pure mesh of 20 peers would need each peer to upload 19 streams.
Transport layer ★ always asked

TCP vs UDP

Both carry data between machines (on top of IP). TCP is careful and reliable. UDP is quick and doesn't check.

Picture it

TCP is registered post. You call ahead, number every parcel, and the receiver signs for each one. Anything that goes missing gets sent again, and parcels are unpacked in the right order. UDP is throwing flyers over a fence. It's very fast, but you don't know whether they all landed, or in what order.

TCP/IP

  • Connection maintained: a virtual connection is set up before data flows.
  • Ordering maintained: each packet carries a sequence number. Packets 1, 2, 3 are put back in order even if they arrive as 2, 1, 3.
  • Acknowledgement: the receiver sends "ACK 1", "ACK 2". A packet with no ACK is sent again.
  • The result is reliable but slower. Use it where every byte matters: web pages, APIs, payments, file transfer, email.

UDP/IP

  • No connection, no acknowledgement, no ordering. The lecture calls it a best-effort mechanism for sending data.
  • The result is fast. Use it where fresh data matters more than complete data: live streaming, video and voice calls, online games.
  • The lecture's example: on a video call, if you miss half a second of what I said, you'd rather hear what I'm saying now than wait for the missed part.

Connection Yes, set up first No

Beyond the lecture
  • The TCP connection set-up is the three-way handshake: SYN → SYN-ACK → ACK. That's one extra round trip before any data moves. It's one reason UDP feels faster.
  • TCP also does flow control (don't overwhelm a slow receiver) and congestion control (slow down when the network is busy).
Putting it together

Which protocol, when?

The lecture ends with the question interviewers actually ask: "for this system, which protocol would you use, and why?"

You're designing… Use Why
A messaging app (WhatsApp, Telegram) WebSocket Two-way. The server must push new messages to the receiver without being asked.
Video calling, live streaming (Google Meet) WebRTC over UDP Speed over perfection. A lost frame is fine, a delay isn't. P2P avoids a server hop.
Normal websites and REST APIs HTTPS over TCP Simple request–response, reliable, encrypted.
Payments, anything where data must be exact TCP-based (HTTPS) Ordering and guaranteed delivery. A lost packet can't be tolerated.
Moving files HTTPS / SFTP (not FTP) FTP is not encrypted, so it isn't secure.
Email SMTP + IMAP SMTP sends. IMAP keeps mail on the server for every device.

Good to know as an engineer

These aren't in the lecture, but you'll meet them on the job almost immediately, usually while debugging.

How HTTPS proves who it is: the TLS handshake

Picture it

Before telling a stranger a secret, you check their government ID and agree on a code language only the two of you know. The ID is the certificate, the government is the certificate authority, and the code language is the session key.

  1. The client says hello and sends its supported ciphers plus a key share.
  2. The server replies with its key share and its certificate, which a trusted certificate authority (CA) has signed.
  3. The client checks the certificate chain up to a CA it trusts, and that the name matches the domain.
  4. Both sides derive the same session key and encrypt everything after that. TLS 1.3 does this in one round trip.

Why you care: "certificate expired" is a surprisingly common cause of real outages. Automate renewal (for example Let's Encrypt). Handshakes cost a round trip, which is one reason connection reuse matters (below).

Server push without WebSockets

Technique How it works Use when
Short polling The client asks "anything new?" every few seconds. Almost never. Wasteful.
Long polling The client asks, and the server holds the request open until there's data or a timeout. Then the client asks again. A fallback where WebSockets are blocked.
Server-Sent Events (SSE) One long HTTP response the server keeps writing events into. One-way (server → client), with auto-reconnect built in. Notifications, live scores, stock tickers, streaming AI responses.
WebSocket A full two-way persistent connection. Chat, multiplayer games, collaborative editing.

REST vs gRPC vs GraphQL

REST gRPC GraphQL
Shape Resources + HTTP verbs (GET /users/1) Remote function calls defined in a .proto file One endpoint. The client writes a query for exactly the fields it wants.
Format Usually JSON Protobuf (binary, compact) over HTTP/2 JSON
Strength Simple, cacheable, universal Fast, typed, streaming. Great between internal services. Avoids over- and under-fetching. Great for mobile and complex UIs.
Weakness Many round trips for nested data Not browser-native, harder to debug by eye Caching and rate limiting are harder. Clients can write costly queries.

The settings that decide real-world latency

  • Timeouts on every network call. Without one, a slow dependency ties up your threads forever. It's the most common cause of cascading failures.
  • Retries with exponential backoff + jitter (wait 100 ms, 200 ms, 400 ms… plus randomness), and only for idempotent operations. Retrying instantly in sync with everyone else turns a blip into an outage.
  • Connection pooling and keep-alive: reuse open TCP/TLS connections instead of paying the handshake cost on every request. Database drivers and HTTP clients both do this.
  • HTTP status code families: 2xx success, 3xx redirect, 4xx your fault (bad request, unauthorised, not found, 429 too many requests), 5xx server's fault. Retry 5xx and 429, but not most 4xx.
Check yourself

Revision questions

Try answering out loud before opening each one.

What's the difference between client–server and peer-to-peer?

In client–server, the client always starts and the server responds; clients never talk directly. In peer-to-peer, every node can talk directly to every other, and each is both client and server.

Is WebSocket a peer-to-peer protocol?

No. It's client–server, but bi-directional: once connected, the server can push to the client. Two clients chatting over WebSockets still go through the server.

Why does FTP use two connections?

A control connection stays open for commands for the whole session. A separate data connection is opened for each file transfer and closed after.

Why is FTP avoided today?

It isn't encrypted. Credentials and files travel as plain text. HTTPS or SFTP are used instead.

SMTP vs IMAP vs POP3?

SMTP sends mail. IMAP reads mail and keeps it on the server, so multiple devices can access it. POP3 downloads mail and deletes it from the server.

Three things TCP guarantees that UDP doesn't?

A maintained connection, ordering (sequence numbers), and delivery through acknowledgements and re-sends.

Why does WebRTC use UDP?

For live audio and video, getting the newest data fast matters more than getting every packet. Waiting for re-sends (as TCP does) would cause lag and freezes.

Which protocol for a WhatsApp design? For Google Meet?

WhatsApp: WebSockets, because the server pushes messages to receivers. Google Meet: WebRTC over UDP, because it's low latency and P2P.
