CAP Theorem

When your data lives on several machines, you want three things: every read is up to date, every node always answers, and the system survives the network breaking. CAP says you can't have all three at once. This lecture shows why with one small example, and which trade-off you actually get to make.

Start here asked directly in interviews

The setup: a distributed system with replicated data

The lecture's one-line definition: CAP describes the desirable properties of a distributed system with replicated data. All three words in that phrase matter.

Picture it

Two shops of the same bakery chain, one in India and one in the US, each with a copy of the same price list. Whenever head office changes a price in one shop, that shop phones the other to update its copy. Customers don't care which shop they call. They just want the right price, and they want someone to pick up.

  • Distributed: the data is on more than one machine, here node B in India and node C in the US.
  • Replicated: both nodes hold the same data. A write on B is copied to C.
  • The user (application A) doesn't know or care which node answers. To them it's one system.

Why it's asked early

CAP decides trade-offs at the very start of a design. If you pick the wrong side and discover it later, you may have to redesign the whole system. So know which property you're willing to give up before you draw anything.

The C

Consistency

Every read, from any node, at any moment, returns the latest written value.

The lecture's example: node B holds a = 4. Application A writes a = 5. B saves it and replicates it to C, so C changes from 4 to 5. Now whether A reads from B or C, it gets 5. That's consistency.

The A

Availability

Every node responds to every request. The response can be a success or a failure, but it must be a response, never silence or a timeout.

Picture it

Available means the shop always picks up the phone. It might say "sorry, out of stock", which still counts. What doesn't count is the phone ringing forever.

Beyond the lecture

The formal definition says every request to a non-failing node gets a non-error response. That response is not guaranteed to be the latest data, and that's exactly where it clashes with consistency.

The P the confusing one

Partition tolerance

A partition is a break in communication between nodes: B and C can no longer talk to each other. Partition tolerance means that even when that happens, the system stays up, and A can still send requests and get them handled.

Picture it

The phone line between the India shop and the US shop is cut. Partition tolerant means both shops stay open for customers anyway. Not partition tolerant means the whole chain closes until the line is fixed.

The lecture's simple way to say it: after the partition breaks, is the system still up, accepting and fulfilling requests? If yes, it's partition tolerant.

The theorem

Why you can't have all three

Possible: CA, CP, AP. Not possible: CAP. Here's the example that proves it.

  1. B and C both hold a = 5.
  2. The B–C link breaks (a partition) for, say, 5 minutes. We want the system to stay up (P).
  3. A writes a = 6. It lands on B. B tries to replicate to C, but the update can't get through.
  4. Now A reads a from C. C has two choices:
    • Answer 5. It's available, but that's old data, so consistency is lost.
    • Refuse to answer until it's back in sync. That keeps things consistent, but C isn't responding, so availability is lost.

There is no third option. During a partition you have to give up C or A. So all three together is impossible.

The three possible combos

CA, CP and AP

CP: consistent + partition tolerant (give up availability)

When the link breaks, the lecture says to bring node C down, so it stops accepting requests. All reads and writes go to B, and everyone gets a = 6. The system is up (P ✓) and consistent (C ✓), but C isn't responding, so availability is given up (A ✗).

AP: available + partition tolerant (give up consistency)

Keep both nodes answering during the partition. B says 6, C says 5. Both respond (A ✓) and the system is up (P ✓), but readers can get different answers (C ✗). When the link comes back, C catches up. This is called eventual consistency.

CA: consistent + available (give up partition tolerance)

You can only have both C and A if there's never a partition. The lecture's example: the moment B and C lose contact, you stop the whole system (A shouldn't query at all), so no one ever sees inconsistent data. While the network is healthy you're fully consistent and available, but you are not partition tolerant. A 10-minute network blip means 10 minutes of downtime.

Choice During a partition… Gives up
CP Nodes that can't sync stop answering. Everyone who gets an answer gets the latest data. Availability
AP All nodes keep answering. Some answers may be stale until the link heals. Consistency
CA The whole system stops. Partition tolerance
What to say in the interview ★ remember this

In the real world, P is not optional

Networks between machines and data centres will break sometimes. Stopping the entire system every time that happens isn't acceptable. So in a real distributed system you always keep P, and the real choice is between C and A, which means CP or AP.

Picture it

Phone lines between shops do go down. "Close every shop when the line drops" isn't a real plan. The only real question is: while the line is down, do shops refuse to sell (CP), or sell at possibly outdated prices (AP)?

The line to use in an interview: "We never trade off partition tolerance. We trade off between consistency and availability, based on the use case."

Choose CP when wrong data is worse than no data

  • Bank balances, payments, wallet deductions
  • Booking the last seat or ticket
  • Inventory for flash sales

Choose AP when a slightly old answer is fine

  • Social feeds, like counts, view counts
  • Product catalogue, recommendations
  • Chat "last seen", presence status
Beyond the lecture
  • Real databases: MongoDB (default settings) and HBase lean CP. The original Dynamo design, Cassandra and CouchDB lean AP. DynamoDB, the AWS product, replicates through a leader and offers both eventually and strongly consistent reads. Many let you tune this per query (for example Cassandra's consistency levels, MongoDB's read and write concerns).
  • A single-node relational database (one PostgreSQL server) is often called "CA". It's consistent and available, but only because there's no network between nodes to partition.
  • PACELC extends CAP: if there's a Partition, choose A or C; Else (normal operation), choose Latency or Consistency. Even without failures, waiting for every replica to confirm a write makes things slower.
Beyond the course good to know as an engineer

Good to know as an engineer

CAP is the headline. These are the details engineers actually argue about when choosing and running databases.

Consistency is a spectrum, not a switch

Model Guarantee Example
Linearizable (strong) Behaves like a single copy. Once a write finishes, every later read anywhere sees it. etcd, ZooKeeper, Spanner
Sequential Everyone sees operations in the same order, though not necessarily in real time. Some replicated logs
Causal If B depends on A (a reply to a comment), everyone sees A before B. Unrelated writes may appear in any order. Some geo-replicated stores (for example COPS)
Read-your-writes You always see your own updates, even if others don't yet. Session guarantees
Monotonic reads You never see data go backwards in time. Sticky reads to one replica
Eventual If writes stop, all replicas converge eventually. DNS, Cassandra (default levels)

Strongest at the top, weakest at the bottom. Each step down is cheaper and more available. Many products let you pick per request.

CAP's C is not ACID's C

  • CAP consistency = all replicas agree, so a read returns the latest write (linearizability).
  • ACID consistency = a transaction leaves the database obeying its rules (constraints, foreign keys, balance ≥ 0).

Same word, different ideas. Mixing them up is a classic interview trap.

How CP systems stay consistent: consensus

Picture it

A committee only acts when a majority votes yes. If the room splits into two groups, only the bigger group can reach a majority, so the two halves can never make conflicting decisions.

  • Raft and Paxos are the standard algorithms. The nodes elect a leader, and a write is committed once a majority (a quorum) has stored it.
  • With 2f + 1 nodes you survive f failures: 3 nodes survive 1, and 5 survive 2. That's why clusters are odd-sized.
  • This prevents split-brain, where two halves of a partitioned cluster each think they're in charge and accept conflicting writes.
  • You rarely implement it yourself. You use it through etcd (Kubernetes), ZooKeeper, Consul, or Kafka's KRaft.

Availability in "nines"

Availability Downtime per year Per month
99% (two nines) 3.65 days ~7.3 hours
99.9% 8.76 hours ~43.8 min
99.99% 52.6 min ~4.4 min
99.999% 5.26 min ~26 s

Availabilities multiply when dependencies are in series. Three services at 99.9% each give roughly 99.7% for the whole request. Every hop you add costs a little availability.

Check yourself

Revision questions

Try answering out loud before opening each one.

Define the CAP theorem in one line.

For a distributed system with replicated data, you can guarantee at most two of consistency, availability and partition tolerance at the same time.

What does availability mean in CAP?

Every node responds to every request, with success or failure, never silence. The response isn't guaranteed to be the latest data.

What is partition tolerance, in simple words?

If communication between nodes breaks, the system stays up and keeps accepting and fulfilling requests.

Walk through why CAP (all three) is impossible.

The link between B and C breaks and a write goes to B. C now has old data. If C answers, it's inconsistent. If C refuses, it's unavailable. It can't do both.

How does a CP system behave during a partition?

Nodes that can't stay in sync stop serving requests (in the lecture, node C is taken down). Answers from the remaining nodes are consistent.

Why is CA not a realistic choice for distributed systems?

It means shutting the whole system down whenever the network between nodes breaks, and network breaks are common. So P is always kept, and you choose between C and A.

CP or AP for a payment wallet? For an Instagram like-count?

Wallet: CP, because a wrong balance is unacceptable. Like-count: AP, because a slightly stale number is fine and the page must always load.
