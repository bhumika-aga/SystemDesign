Monolith to Micro­services

Most companies start with one big application that does everything. As it grows, it gets slow to build, hard to scale and risky to change, so teams break it into small services. This lecture covers why you'd do that, what it costs you, and the first pattern you need: how to decide where to cut.

Architecture 1

Monolithic application

A monolith is one application that does everything: orders, products and inventory, login, billing, payments. It's one codebase, deployed as one unit, usually on one database. In companies you'll often hear it called the legacy application, the thing everyone is planning to migrate to microservices.

Picture it

A giant department store run as one building with one set of keys, one electricity meter and one front door. To repaint the shoe section, you close the whole store. To make the toy section bigger for Christmas, you have to build a whole second copy of the store.

Why teams leave

Disadvantages of a monolith

  • Overloaded IDE. The codebase can run to gigabytes. IntelliJ or Eclipse struggles to even open it, and when it does, it's slow. That hurts every developer every day.
  • Scaling is hard, in two senses.
    • Growing the team and codebase: CI (continuous integration) jobs, regression runs, pushes and monitoring all get slow, so every operation drags.
    • Growing traffic: if only the order feature is getting heavy traffic, you can't scale just order. You have to run another copy of the entire application, say another 10 GB server with login, billing and payments you didn't need more of. That's costly.
  • Tightly coupled. Order, product and payment code share pieces. A one-line change for order can break payment. So every change means re-testing and redeploying the whole application, which takes a long time.
  • Debugging is hard. Finding a bug in a huge codebase, then running all CI jobs and regression and deploying everything, is slow and painful.
Architecture 2

Microservices

Break the big application into small, independent services: Product, Order, Billing, Login, Account, Payment. Each has its own code and can be deployed and scaled on its own. The lecture's summary: every disadvantage of the monolith is an advantage of microservices.

Picture it

The department store becomes a street of small shops. Each shop has its own door, keys and staff. The toy shop can open a second branch for Christmas without touching the shoe shop. Repainting one shop doesn't close the others.

  • Easy to manage: a bug in Order? Debug, fix and deploy only the Order service. That's far easier than going through the whole codebase.
  • Easy, cheap scaling: lots of order traffic? Add more instances of Order only. The lecture calls it "pocket friendly". Why pay to scale Login if it isn't busy?
  • Loosely coupled: change or scale one service without impacting the others.
  • Smaller, faster everything: smaller codebase, faster CI jobs, faster deployments.

Interview tip: "What are the advantages and disadvantages of microservices?" is a very common question. The advantages are easy: reverse the monolith's problems. The disadvantages are next.

Nothing is free ★ common interview question

Disadvantages of microservices

1. The split must be done properly

If you break the monolith in the wrong places, you get services that look separate but still depend on each other heavily. Scaling one forces you to scale the other, so they're tightly coupled in disguise. And every call between services is now a network call, so a request that took 5 ms inside one app might now take 10 ms as it hops between services. Latency goes up, especially with a bad split.

2. Monitoring and debugging get harder

Say S3 goes live with new code and its response changes shape (a becomes a′). S2 depends on S3, so S2 breaks, and S1 depends on S2, so S1 breaks too. The error surfaces at S1. S1's team debugs and says "S2 failed". S2's team says "S3 changed". It takes a chain of teams to find the real culprit, and when S3 shipped, it had to watch clients it doesn't own.

3. Transaction management is hard

With one database, a transaction is simple: 10 table inserts, and if 2 fail you roll back all 10 (ACID). With microservices, each service has its own database. If the order is saved in the Order DB but the payment fails in the Payment DB, there's no single transaction spanning both to roll back. You need a pattern for this: SAGA, in lecture 4.

Each of these problems has a known solution, and those solutions are the microservice design patterns.

The map

Phases of microservices and their patterns

Building microservices happens in phases, and each phase has its own set of design patterns. microservices.io lists 50+ of them. The lecture covers only the ones that matter for interviews.

1 · Decomposition

how to split into services

Decompose by business capability, decompose by subdomain. Covered in this lecture.

2 · Database

where each service keeps data

Database per service, or shared database. Then SAGA and CQRS to deal with the fallout. Lecture 4.

3 · Communication

how services talk

Synchronous API calls (REST, gRPC) or asynchronous events and messages (queues).

4 · Integration

how clients reach many services

API gateway, aggregation, UI composition, so the app or website doesn't call 20 services itself.

After those come cross-cutting concerns (config, logging), deployment, testing and observability (monitoring, tracing). A common interview question: "How would you divide this system into microservices, and why?" Decomposition patterns answer it.

Decomposition pattern

How small is "micro"?

There's no fixed size. "Micro" is relative to the project. One company's microservice is another company's whole application. Order management can be a huge system, but if it's one slice of a bigger product, it's still a microservice there.

Because there's no size rule, you need a pattern to guide where to cut. Two decomposition patterns do that.

Decomposition 1

Decompose by business capability

Make one service per business capability: something the business does that creates value.

Picture it

Split a company by department: Sales, Accounts, HR, Warehouse. Each department is a service with a clear job.

  • Example (online order app): Order management, Product management, Account management, Login, Billing, each its own microservice.
  • Everything related to orders goes in the Order service. Everything related to payments goes in the Payment service.
  • Challenge: you need good knowledge of the business. Without clarity about the business functions, it's hard to draw the right boundaries.
Decomposition 2

Decompose by subdomain (DDD)

Based on Domain-Driven Design. Treat each big area as a domain, split it into subdomains, and give each subdomain its own service. One domain can have several microservices.

Picture it

Instead of one "Accounts department", you split it into its real jobs: "paying suppliers" and "handling refunds". Each job gets its own small team.

  • Order management domain → order placing and order tracking subdomains, each a separate service.
  • Payment domain → forward payment (user 1 pays user 2) and reverse payment (refunds), each a separate service.

Unit of split A business function (Order, Payment) A subdomain inside a domain (Order placing, Order tracking)

Beyond the lecture
  • DDD classifies subdomains as core (what makes the business special, like pricing or matching), supporting (needed but not special) and generic (solved problems like auth or email, often bought rather than built).
  • Each service owns a bounded context: a boundary inside which words have one meaning. "Order" in the shipping context is not the same model as "Order" in the billing context.
  • microservices.io also lists "self-contained service" and "service per team" as decomposition patterns.

Beyond the course good to know as an engineer

Good to know as an engineer

Splitting into services is the easy part. These ideas decide whether microservices actually help your team.

Conway's law

"Organisations design systems that mirror their own communication structure." Four teams tend to produce four services. In practice, draw service boundaries along team boundaries: one team owns one service end to end, including its database, deployment and on-call.

The distributed monolith (the anti-pattern to avoid)

Picture it

You split a house into separate flats, but every flat still shares one boiler and one fuse box. Now you have the rent of many flats and the single point of failure of one house.

Warning signs: services that must be deployed together, services that share a database, or one request that needs a long chain of synchronous calls to succeed. You pay the network and operations cost of microservices with none of the independence.

How services find each other: service discovery

  • Instances come and go (autoscaling, crashes), so their IPs change. A service registry tracks where each service is currently running.
  • Common implementations: Kubernetes Services and DNS, Consul, Eureka.
  • Client-side discovery: the caller asks the registry and picks an instance itself. Server-side: the caller hits a load balancer that does the lookup.

API gateway and Backend-for-Frontend (BFF)

  • API gateway: one front door for all clients. It handles routing, authentication, rate limiting and TLS termination, so every service doesn't reimplement them.
  • BFF: a separate small gateway per client type (web, iOS, Android), each shaping responses for its screen. It stops one client's needs from bloating everyone's API.

Finding the culprit: distributed tracing

This is the practical fix for the S1 → S2 → S3 debugging problem in this lecture. Each request gets a trace ID that every service passes along in a header (the W3C traceparent header). Each service records a span: its own start and end times. A tracing tool stitches them into a waterfall.

Tools: OpenTelemetry (the standard for instrumenting), with Jaeger, Zipkin, Datadog or Honeycomb to view traces. Also add the trace ID to every log line, a correlation ID, so you can grep one request across all services.

Check yourself

Revision questions

Try answering out loud before opening each one.

List four disadvantages of a monolith.

Overloaded IDE (a huge codebase), hard to scale (you must copy the whole app, and CI and deployments are slow), tight coupling (one change can break other domains, so you redeploy everything), and hard debugging.

Why is scaling a monolith expensive?

You can't scale one feature. To give Order more capacity, you must run another copy of the entire application, paying for components that didn't need it.

Three disadvantages of microservices?

The split must be right (a bad split gives tightly coupled services and higher latency from network calls), monitoring and debugging across a chain of services is hard, and transactions that span several databases are hard.

How small should a microservice be?

There's no fixed size, because "micro" is relative to the project. Use decomposition patterns (by business capability or by subdomain) to decide the boundaries.

Decompose by business capability vs by subdomain?

Business capability: one service per business function (Order, Payment). Subdomain (DDD): each domain splits into subdomains, and each gets a service (Payment → forward payment, reverse payment).

Name the four main phases of microservices.

Decomposition, database, communication and integration. Then cross-cutting concerns, deployment, testing and observability.
