Strangler, SAGA & CQRS

Part 1 showed how to split a system into services. This part covers the three patterns you need once you actually do it: how to move off a live monolith safely, how to keep data correct when one action spans several databases, and how to join data that now lives in different places.

Refactoring to microservices ★★ very important

Strangler pattern

You already have a monolith running in production and want to move it to microservices without a risky big-bang switch. Put a controller in front that decides what share of the traffic goes to the new microservices and what share stays on the monolith. Then shift traffic over gradually.

Picture it

A strangler fig is a vine that grows around an old tree. Bit by bit it takes over, until the old tree is gone and only the fig is standing. The new system grows around the old one the same way, until the old one can be removed.

  1. Build the new microservices for a flow (using decomposition patterns from part 1).
  2. Route a small share of traffic to them, say 10% of API calls (10 out of every 100). The other 90% still go to the monolith.
  3. Something breaks? Instantly set microservices back to 0%, so all traffic returns to the monolith. Users barely notice. Fix the bug, then start again at 10%.
  4. As confidence grows: 20% → 50% → 100%.
  5. At 100%, the monolith gets zero traffic for that flow. Once everything has moved, delete the monolith.

You can split by percentage of traffic, or by flow (for example, move only the "order tracking" APIs first).

Beyond the lecture
  • Martin Fowler named this the Strangler Fig pattern in 2004, after the plant.
  • The controller is usually an API gateway, a reverse proxy or a feature flag. Gradual percentage rollouts are the same idea as canary releases.
  • The hard part is usually data: during migration both old and new code may need the same records, so teams sync data between them until the cut-over.
Data management in microservices

Database per service vs shared database

Once you have services S1, S2 and S3, where does their data live? Either each service has its own database, or all services share one. The lecture explains why the shared option doesn't hold up, and why the preferred option creates the two problems SAGA and CQRS exist to solve.

Why a shared database doesn't work well

Example: an e-commerce app. S1 is Order, S2 is Inventory, S3 is Payment.

  • Scaling: orders run into millions while inventory is a handful of products. With one shared database, you have to scale the whole thing (more capacity, more memory) even though only order data is growing.
  • Schema changes become dangerous: say there are 10 shared tables and S3 wants to delete a column. It can't, because S1 and S2 might use that table. Every change needs coordination, and services are coupled through the database.
  • For a small application a shared DB can be fine, but it doesn't scale.

In fairness, a shared DB has two real advantages: joins are easy (all tables are in one place) and transactions are easy (ACID works across all tables).

Database per service (the preferred approach)

  • The rule: no service queries another service's database. If S2 needs data from D3, it calls S3's API.
  • Each service picks the right database: relational SQL, NoSQL like MongoDB, PostgreSQL.
  • Each service's database scales on its own, with more capacity only where traffic needs it.
  • Teams own and change their schema without breaking anyone.

But now you lose exactly what a shared DB made easy:

Problem 1: transactions (ACID)

One action like "place order" touches Order DB, Inventory DB and Payment DB. There's no single transaction across three databases. → SAGA solves this.

Problem 2: query joins

Tables 1–5 live in D1, tables 6–8 in D2, tables 9–10 in D3. How do you join table 6 with table 10? → CQRS solves this.

Distributed transactions ★★ very important

SAGA pattern

A SAGA is a sequence of local transactions. Each service does its own small ACID transaction in its own database, then publishes an event that triggers the next service. If a step fails, the SAGA runs compensating transactions backwards to undo what the earlier steps did.

Picture it

Planning a trip: book the flight, then the hotel, then the car. If the car booking fails, you don't pretend the whole thing never happened. You cancel the hotel, then cancel the flight. Each booking is its own deal, and each has a matching "undo".

The problem

"Place an order" touches three databases: Order DB (T1, T2), Inventory DB (T3, T4), Payment DB (T5, T6). The order row is created ✓, the inventory is updated ✓, then the payment record fails ✕. ACID says all or nothing, so the first two must be undone. But each database only knows its own local transaction. Nobody can roll back all three at once.

The SAGA solution

  1. Order service creates the order in its DB (local transaction) and publishes OrderCreated.
  2. Inventory service receives it, reserves stock in its DB, and publishes StockReserved.
  3. Payment service tries to record the payment and fails. It publishes a failure / compensation event: PaymentFailed.
  4. Inventory hears it, reverses its change (adds the stock back), and publishes StockReleased.
  5. Order hears that and rolls back (marks the order cancelled).

The one big transaction has been turned into a sequence of local transactions with an undo for each.

Beyond the lecture
  • A SAGA gives eventual consistency, not strict ACID. For a moment, the order exists while payment hasn't failed yet. Design the UI for it ("order pending…").
  • Compensation is a new action, not an erase: "refund" or "cancel", recorded in history.
  • Events can be delivered twice, so each step and each compensation must be idempotent (safe to repeat).
  • The alternative is two-phase commit (2PC), which locks all databases until everyone agrees. It's strongly consistent but slow and fragile. That's HLD lectures 20–21.
Two ways to run a SAGA

Choreography vs orchestration

Picture it

Choreography is a flash mob. Nobody's in charge; each dancer watches for a cue and does their move. Orchestration is an orchestra with a conductor who points at each section and says when to play, or when to stop.

Choreography (event-based)

  • Each service does its work, publishes an event, and listens for others' events (success or failure) to decide its next move, including its own rollback.
  • No central component, so it's simple to start with.
  • Drawback: cyclic dependency. S1 listens to S2, S2 listens to S3, S3's failure goes back to S2 and S1… As services grow, it gets hard to see or reason about the whole flow.

Orchestration (a central coordinator)

  • The orchestrator calls S1, then S2, then S3 in order.
  • If S3 fails, the orchestrator tells S2 and S1 to roll back.
  • The whole flow lives in one place, so it's easier to understand and debug. The orchestrator is one more component to build and keep running.
Choreography Orchestration
Who drives Nobody. Services react to events A central orchestrator
Communication Events through a message broker Orchestrator commands each service
Best for Few services, simple flows Many services, complex flows
Main drawback Cyclic dependencies, hard to follow Extra component, central point to manage
The lecture's interview question

SAGA example: paying from a wallet

Person A pays Person B ₹10 from their wallet balance (instead of a UPI app like PhonePe or GPay). Two microservices are involved: Balance (holds the wallet amount, ₹100) and Payment (records every payment: who, to whom, how much, when).

  1. Balance checks that A has at least ₹10, then deducts it: ₹100 → ₹90.
  2. Payment tries to insert the record "A paid B ₹10 on this date" and fails.
  3. The problem: A's balance went down, but there's no payment in history. The money has disappeared.
  4. SAGA fix: Payment publishes a failure event with the details (transaction 1 failed, ₹10).
  5. Balance is listening (choreography). It runs a compensating transaction, adding ₹10 back: ₹90 → ₹100.

The answer interviewers want: "Use SAGA. Each service keeps its local transaction, and on failure publishes an event so earlier steps compensate."

Querying across services

CQRS: Command Query Responsibility Segregation

Split the system into two sides. Commands change data (create, update, delete). Queries read data (select). Commands go to each service's own database. Queries go to a separate read database (a view) that already holds the data combined.

Picture it

A school keeps attendance in one office and marks in another. Parents keep asking "show me attendance and marks together". So a clerk keeps a combined report card folder, updated whenever either office changes something. Parents read the folder and never bother the two offices.

The problem it solves

With database per service, S1 owns table T1 (orders) and S2 owns T2. You need a query that joins T1 and T2, for example an order history showing items and stock. S1 isn't allowed to query S2's database directly, so a normal SQL join is impossible.

How CQRS fixes it

  • Command side: create, update and delete go to each service's own database (T1, T2).
  • Query side: a separate DB (the view) holds the joined data, for example an order-history table with fields from both T1 and T2. All reads (select) go here.
  • Keeping the view up to date: whenever T1 or T2 has a create, update or delete, publish an event. A listener applies the same change to the view. Alternatively, use DB triggers or stored procedures that run on every change.
Beyond the lecture
  • The read view is eventually consistent: it lags a little behind the writes.
  • Reads and writes can now be scaled separately, which suits read-heavy systems. The read store can even be a different technology (a search index, a cache) shaped for the exact query.
  • CQRS is often paired with event sourcing, where the write side stores the list of events itself and the read side is built from them.
  • It adds real complexity (two models, sync logic). Use it when cross-service reads or read load actually demand it.

Beyond the course good to know as an engineer

Good to know as an engineer

SAGA and CQRS both depend on events actually being published. These patterns make that reliable, and stop one sick service from taking down the rest.

The transactional outbox ★ the gap in most SAGA explanations

The hidden bug: the Order service saves the order to its DB, then publishes OrderCreated to the broker. If it crashes between the two, the order exists but no event is ever sent, and the SAGA silently stalls. You can't wrap a DB write and a broker publish in one transaction.

  1. In one local transaction, insert the order row and an event row into an outbox table. Either both commit or neither does.
  2. A relay process reads new outbox rows and publishes them to the broker. It either polls the table, or uses change data capture (CDC), for example Debezium reading the DB log.
  3. After publishing, it marks the row as sent.

The relay may publish the same event twice (a crash after publishing but before marking it), so consumers must be idempotent. HLD lecture 13 covers that.

Resilience patterns: stop failures spreading

  • Circuit breaker: like a fuse. When calls to a dependency keep failing, stop calling it for a while and fail fast (or return a fallback) instead of piling up waiting threads. Closed = normal. Open = reject immediately. Half-open = allow a few test calls. If they succeed, close again.
  • Timeouts on every call, shorter than the caller's own timeout.
  • Retries with exponential backoff and jitter, and only for idempotent operations.
  • Bulkhead: give each dependency its own thread or connection pool, like watertight compartments in a ship. If one floods, the others keep working.
  • Libraries: Resilience4j (Java), Polly (.NET), or a service mesh such as Istio or Linkerd, which does this at the network layer without code changes.

Migration and release hygiene

  • Feature flags: the Strangler controller is often just a flag with a percentage rollout (LaunchDarkly, Unleash or home-grown).
  • Expand–contract schema changes: add the new column, write to both, backfill, switch reads, then drop the old one. Never break a running version.
  • Contract tests (for example Pact) catch "S3 changed its response and broke S2" before release.
Check yourself

Revision questions

Try answering out loud before opening each one.

How does the Strangler pattern migrate a monolith?

A controller in front routes a small share of traffic (for example 10%) to the new microservices. If there are issues, it drops to 0% and all traffic returns to the monolith. As confidence grows it goes to 50% and then 100%, and the monolith is finally deleted.

Why is a shared database a poor fit for microservices?

You must scale the whole DB even if one service needs it, and schema changes (like dropping a column) can break other services that use the same tables.

What two problems does database-per-service create?

Transactions spanning several databases (solved by SAGA) and joins across databases (solved by CQRS).

Define SAGA in one line.

A sequence of local transactions. Each publishes an event to trigger the next, and failures trigger compensating transactions that undo earlier steps.

Choreography vs orchestration?

Choreography: services publish and listen to events with no central controller. It's simple, but can lead to cyclic dependencies. Orchestration: a central orchestrator calls each service and tells them to roll back on failure.

Wallet balance deducted but the payment record failed. What do you do?

SAGA: the Payment service publishes a failure event, and the Balance service listens and runs a compensating transaction, adding the ₹10 back (₹90 → ₹100).

What do C and Q stand for in CQRS, and how is the read side kept updated?

Command (create, update, delete) and Query (select). Every write publishes an event, or fires a DB trigger or procedure, that applies the same change to the read view.
