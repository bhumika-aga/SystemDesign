OAuth 2.0

"Sign in with Gmail" on another site works because of OAuth: an open authorization framework that lets a third-party app use some of your protected data without ever seeing your password. This lecture covers the four roles, the authorization code flow step by step (with its real requests), how the state value blocks a CSRF attack, and the other ways to get a token.

The idea

What OAuth is

  • OAuth = Open Authorization. It's an authorization framework.
  • It enables secure third-party access to a user's protected data.
  • Example: you're already signed into Gmail, which holds your profile (name, date of birth, email). On some other website you click "Sign in using Gmail". You're authorising that third-party site to use part of your Gmail data. Gmail hands over just what's needed, and the site greets you: "Welcome, user".
Picture it

A hotel gives a valet a valet key: it starts the car, but can't open the boot or glovebox, and it stops working when you check out. OAuth gives apps a valet key (an access token) to just the data you approve, instead of your real key (your password).

The cast

Four roles

Role Who Job
Resource owner You Owns the protected data and grants access
Client Instagram (or Facebook, or XYZ site) The app that initiates the request and wants your data
Authorization server Gmail's auth server Authenticates you, collects consent, issues codes and tokens
Resource (hosting) server Gmail Hosts your protected data: name, date of birth, email…

Sometimes one service plays both the authorization and resource roles, but usually (and in this lecture) they're two separate components.

Ways to get a token

Five authorization grant types

Authorization code is the important, widely used one. Refresh token is used alongside it. Implicit, password and client credentials exist but aren't generally encouraged for user logins (see "Good to know").

The main flow ★ learn this one

Authorization code grant, end to end

  1. Registration (once): Instagram registers with Gmail's authorization server and gets a client ID and client secret. Only the client and the authorization server know the secret.
  2. You click "Sign in using Gmail" on Instagram.
  3. Instagram redirects you to the authorization server.
  4. You authenticate there (log in to Gmail if needed) and give consent: "Instagram wants your email, profile and address. Allow?"
  5. The authorization server sends Instagram an authorization code.
  6. Instagram sends the code back to the authorization server and asks for a token.
  7. It receives two tokens: an access token (short-lived, e.g. 10–15 minutes or 1 hour) and a refresh token (long-lived, used to get new access tokens).
  8. Instagram calls the resource server with the access token.
  9. The resource server asks the authorization server: "is this token valid?"
  10. If it's valid, your requested data (name, age, email) is returned and you're signed in. If not, the request is rejected, e.g. 401 Unauthorized.
Under the hood

The requests and responses

As the lecturer stresses, the endpoint names are illustrative. Check the official RFCs and your provider's docs for exact names and parameters.

① Register the client

POST /register { "client_name": "my app name", "redirect_uris": ["https://mysamplewebsite.com/callback", …] } ← up to 3 in the lecture → { "client_name": "…", "client_id": "unique id", "client_secret": "confidential" }

② Fetch the authorization code (browser redirect)

GET /authorize?response_type=code ← required: "I want a code back" &client_id=… ← required &redirect_uri=…/callback ← optional; must match a registered URI &scope=email profile address ← space-separated: what data is wanted &state=sj111 ← random, hard-to-guess (CSRF protection) → redirect: https://mysamplewebsite.com/callback?code=AUTH_CODE&state=sj111

If redirect_uri is left out, the server uses one registered earlier. An authorization code can be used only once.

③ Exchange the code for tokens

POST /token grant_type=authorization_code code=AUTH_CODE redirect_uri=… ← optional client_id=… client_secret=… ← the client proves who it is → { "access_token": "…", ← plain string or a JWT "token_type": "Bearer", ← send it in the Authorization header "expires_in": 3600, ← seconds (1 hour) "refresh_token": "…" }

Then call the resource server with Authorization: Bearer <access_token> to fetch the data for the granted scopes.

Security ★ interview favourite

Why the state parameter matters: CSRF

The attack (without state)

  1. The attacker calls /authorize for their own Gmail account, gets an authorization code, and doesn't use it.
  2. You start "Sign in with Gmail" on Instagram, which waits for a code.
  3. The attacker injects their code into your callback.
  4. Instagram exchanges it for a token, which belongs to the attacker's account. You're now signed into Instagram as the attacker.
  5. Anything you then upload (say, to a linked Google Drive) goes to the attacker's Drive. This is cross-site request forgery (CSRF).

The fix

Instagram sends a random, hard-to-guess state (e.g. sj111) with /authorize. The real authorization server echoes it back with the code. Instagram compares the two. If the state is missing or doesn't match, it discards the code. state is recommended rather than mandatory, but you should always use it.

Staying logged in

Refresh token grant

POST /token grant_type=refresh_token refresh_token=… client_id=… client_secret=… → { "access_token": "new…", "token_type": "Bearer", "expires_in": 3600, "refresh_token": "new…" }
The rest

The other three grants

Implicit grant: the token straight from /authorize

GET /authorize?response_type=token&client_id=…&redirect_uri=…&scope=…&state=… → redirect: …/callback#access_token=…&token_type=Bearer&expires_in=3600

There's no refresh token, because there's no second step. When it expires, you authorize again. Generally not recommended.

Resource owner password credentials (ROPC)

POST /token grant_type=password username=owner's Gmail username password=owner's Gmail password client_id=… client_secret=… scope=… → access_token + refresh_token (refreshing later doesn't need the password again)

Client credentials: when the client is the resource owner

POST /token grant_type=client_credentials client_id=… client_secret=… scope=… → access_token (no refresh token: just ask again with the same credentials)

Beyond the course good to know as an engineer

Good to know as an engineer

OAuth is authorization. "Sign in with…" needs OpenID Connect

OAuth answers "may this app access this data?", not "who is this user?". Using an access token as proof of identity is a classic bug. "Sign in with Google" actually uses OpenID Connect (OIDC), a thin layer on OAuth: add scope=openid, and alongside the access token you get an ID token (a signed JWT stating who logged in). The lecture says "authenticating" loosely. The precise picture is OAuth for access, OIDC for login.

PKCE: the modern must-have

  • Mobile apps and single-page web apps can't keep a client secret (anyone can read the app's code). PKCE ("pixie") protects them.
  • The client makes a random code_verifier and sends its hash, code_challenge, with /authorize. When swapping the code at /token, it must present the original verifier. A stolen or injected code is useless without it.
  • PKCE also blocks the code-injection attack above, and it's now recommended for every client, alongside state.

What's deprecated today

The OAuth 2.0 Security Best Current Practice (RFC 9700) and the upcoming OAuth 2.1 drop the implicit and password grants:

  • Implicit leaks tokens through the URL (browser history, logs). It's replaced by authorization code + PKCE.
  • Password (ROPC) hands your real password to the client, defeating OAuth's whole point, and breaks multi-factor login.
  • OAuth 2.1 also requires PKCE, exact redirect-URI matching, and no tokens in URL query strings.

A few precisions on the lecture's samples

  • The token endpoint is always POST (the password slide shows GET).
  • The implicit grant returns the token in the URL fragment (#access_token=…), not after a ?.
  • "Up to 3 redirect URIs" is a lecture example, not a spec limit. Registration usually happens in a developer console, or via Dynamic Client Registration (RFC 7591).

How resource servers check tokens

  • Opaque token (random string): the resource server asks the authorization server via token introspection (RFC 7662), as the lecture describes.
  • JWT token: the resource server verifies the signature itself using the auth server's published public keys (JWKS). That's faster, but revoking a token early is harder.

Other practical bits

  • Refresh token rotation: every refresh returns a new refresh token and invalidates the old one, so a reused old token signals theft.
  • Device authorization grant (RFC 8628): for TVs and consoles. "Go to example.com/device and enter code ABCD-1234."
  • Keep scopes minimal, store tokens securely (not in localStorage for sensitive apps), and always use HTTPS.
Check yourself

Revision questions

Try answering out loud before opening each one.

What does OAuth stand for, and what does it do?

Open Authorization: a framework that gives third-party apps secure, limited access to a user's protected data without sharing the password.

Name the four roles in the Instagram + Gmail example.

Resource owner: you. Client: Instagram. Authorization server: Gmail's auth server. Resource server: Gmail, which hosts your data.

What does registration give the client?

A client ID and a client secret. The secret is known only to the client and the authorization server.

Walk through the authorization code flow.

Redirect the user to the auth server, the user logs in and consents, the auth server returns a code, the client swaps the code plus its secret for access and refresh tokens, and the client calls the resource server with the access token (which the resource server validates).

Access token vs refresh token?

The access token is short-lived and used to call APIs (sent as a Bearer token). The refresh token is long-lived and used only to get new access tokens.

What attack does "state" prevent, and how?

CSRF and code injection. The client sends a random state and checks the same value comes back. A missing or mismatched state means the response isn't for its request, so the code is discarded.

How does the implicit grant differ, and what's its drawback?

The token comes straight back from /authorize with no code step and no refresh token. It's now deprecated because tokens leak through URLs.

When is client credentials the right grant?

When there's no user and the client is itself the resource owner, e.g. one backend service calling another.

Is OAuth an authentication protocol?

No. It's authorization. Logins use OpenID Connect on top of OAuth, which adds an ID token describing the user.
