Two-Phase Locking · Part 1

Two-phase locking (2PL) is the most common way to build pessimistic concurrency control. Its one rule: a transaction first only takes locks, then only gives them back, and never takes another once it has released one. This part covers that rule, basic 2PL, and its biggest problem: deadlock.

Context

2PL is a kind of pessimistic locking

Lecture 25 compared optimistic (check versions at the end) and pessimistic (lock up front) concurrency control. Two-phase locking is the classic way to do pessimistic control, and it's widely used in industry. It builds on the shared (S) and exclusive (X) locks from lecture 24.

The rule

Phase 1 grows, phase 2 shrinks

Phase 1 · Growing

  • The transaction requests locks from the lock manager.
  • The lock manager grants a lock, or denies it if another transaction already holds a conflicting lock.
  • Locks can only be acquired. None are released.

Phase 2 · Shrinking

  • The transaction can't acquire any new lock.
  • It may only release locks it took earlier.
  • The very first unlock marks the start of this phase.
Variants

Three types of 2PL

Type One-line idea Covered
Basic 2PL Grow then shrink. Locks may be released before commit. This part
Conservative 2PL Take all needed locks at the very start, or none. Next part
Strong strict 2PL (rigorous) Hold every lock until commit or abort. Mostly used in industry. Next part

Whichever type, the two-phase shape always holds: a growing phase, then a shrinking phase.

Basic 2PL

Basic 2PL, step by step

Time Transaction 1 Transaction 2
t0 BEGIN
t1 X(A) growing
t2 X(B) growing
t3 process some work
t4 unlock(A) shrinking starts BEGIN
t5 unlock(B) X(B)
t6 COMMIT X(A)
t7 COMMIT (releases A and B)
  • T1 shows the textbook shape: lock, lock, work, unlock, unlock.
  • T2 never unlocks explicitly. COMMIT ends the transaction and releases all its locks, and that's still two-phase.
  • The defining feature of basic 2PL: locks may be released before the transaction ends, as T1 does.
Problem · case 1 ★ frequently asked

Deadlock: two rows, opposite order

  • t0: both transactions begin.
  • t1: T1 takes X(A), T2 takes X(B).
  • t2: T1 asks for X(B). That's allowed in the growing phase, but B is held by T2, so T1 waits. T2 asks for X(A), held by T1, so T2 waits.
  • Neither can finish its growing phase, so neither ever releases. Deadlock.
Problem · case 2

Deadlock with just one row: lock upgrades

  • t1: T1 and T2 both take S(A). Many shared locks are allowed, so both can read.
  • t2: T1 wants to write, so it asks to convert its S(A) to X(A). That only works once T2's shared lock is released, so T1 waits.
  • At the same moment T2 asks to upgrade too, and waits for T1's shared lock.
  • Neither releases its shared lock, so they wait forever, even though there's only one data item. Deadlock.
Up next

So how do we prevent it?

Basic 2PL is correct but can deadlock. The next lecture covers deadlock prevention strategies, starting with a simple one shown at the end of this video:

  • Timeout: if a transaction has been waiting too long for a lock, the scheduler assumes it's deadlocked and aborts it.
  • The catch: the scheduler can be wrong. T1 might just be waiting for T2, which is slow but not stuck.
Beyond the course good to know as an engineer

Good to know as an engineer

Why the two-phase rule matters: serializability

If every transaction follows 2PL, the final result is always equivalent to running them one after another in some order. This property is called conflict serializability. Why? The lock point (the moment a transaction holds all its locks) gives every transaction a place in line, and every conflict between two transactions resolves in that same direction.

The standard test: draw a precedence graph with one node per transaction and an arrow T1 → T2 whenever T1 touched an item before T2 in a conflicting way (at least one of the two wrote). No cycle means the schedule is serializable. A cycle means it isn't.

Basic 2PL's other big problem: cascading aborts

In the table above, T1 releases its write lock on A before committing. T2 can then read T1's uncommitted value of A, which is a dirty read. If T1 later aborts, T2 must abort too, and anything that read T2's data, and so on: a cascading abort. Holding write locks until commit removes this, which is why databases use the stricter variants.

The variants in one table

Variant Write (X) locks Read (S) locks Deadlock? Cascading aborts?
Basic Any time after the lock point Any time after the lock point possible possible
Conservative All taken up front All taken up front none possible
Strict Held until commit/abort Released any time after the lock point possible none
Rigorous (strong strict) Held until commit/abort Held until commit/abort possible none

Databases' "hold locks until commit" behaviour is essentially rigorous 2PL. That's what SELECT … FOR UPDATE and the serializable level do in lock-based engines.

Not to be confused with two-phase commit

2PL (two-phase locking) controls concurrency inside a database. 2PC (two-phase commit, lecture 20) makes several databases agree to commit. Different problems, similar names. Distributed databases often use both together.

How real databases handle the deadlocks

Besides timeouts, databases keep a wait-for graph and check it for cycles. When one appears, they pick a victim to abort (often the transaction that's done the least work), and the application retries (lecture 25). Lock upgrades (case 2) are common enough that some databases offer an update lock (SQL Server's U lock): only one transaction can hold "I intend to write this" at a time, which prevents the upgrade deadlock.

Check yourself

Revision questions

Try answering out loud before opening each one.

What are the two phases of 2PL?

Growing: the transaction only acquires locks. Shrinking: it only releases them, with no new locks once the first is released.

Who grants or denies locks?

The lock manager. It denies a request if another transaction already holds a conflicting lock.

Is "lock A, unlock A, lock B" two-phase?

No. Once you release a lock you're in the shrinking phase and may not acquire another.

Name the three types of 2PL.

Basic, conservative, and strong strict (rigorous), the last being the one mostly used in industry.

Is it still 2PL if a transaction never unlocks and just commits?

Yes. Commit ends the transaction and releases all its locks at once, which is a valid shrinking phase.

Describe the two-row deadlock.

T1 holds X(A) and wants X(B). T2 holds X(B) and wants X(A). Each waits for the other forever.

How can one row cause a deadlock?

Both transactions hold S(A), and both try to upgrade to X(A). Each upgrade needs the other's shared lock released, so both wait.

What's the timeout strategy, and its weakness?

Abort a transaction that has waited too long, assuming a deadlock. It can be wrong if the other transaction is just slow.
