Optimistic vs Pessimistic

Back to the double-booked seat. There are two attitudes. Optimistic: assume clashes are rare, let everyone read freely, and check a version number just before writing. Pessimistic: assume clashes will happen, so lock first and make everyone else wait. This lecture shows how each works, and why only the pessimistic one can deadlock.

The connection to lecture 24 ★ the interview answer

Each approach pairs with an isolation level

  • Optimistic concurrency control (OCC): isolation below repeatable read, in practice read committed. More concurrency.
  • Pessimistic concurrency control (PCC): repeatable read or serializable. Locks are held to the end.
  • Read uncommitted is for read-only use. If you're writing, dirty reads are never acceptable.

Strictly these are "concurrency control" approaches. People commonly say "optimistic/pessimistic locking", which is fine in conversation.

Optimistic · worked example

Optimistic: read freely, compare versions before writing

Each row carries a version number, increased by one on every update. Some databases provide one; otherwise you add a version column.

  1. T1: both transactions begin. The row is ID 1 · FREE · version 1.
  2. T2: both read the row. Under read committed, each shared lock is released right after reading, so both read at once and remember version 1.
  3. T3: A wants to book. It runs SELECT … FOR UPDATE (an exclusive lock), then validates the version: "I read version 1, and the database still says 1." ✓
  4. T4–T5: A updates the row to BOOKED · version 2 and commits, releasing the lock.
  5. T6: B also wants to book. It takes the exclusive lock and validates: "I read version 1, but the database now says 2." Someone changed it, so validation fails. B rolls back and must try again (and will now see BOOKED).
The general recipe

The optimistic flow

Best when conflicts are rare: lots of reads, few writers to the same row. It gives a high level of concurrency.

Pessimistic

Pessimistic: keep every lock until the end

  • Under repeatable read / serializable, locks aren't released after the read. They're held until commit or abort.
  • Other transactions can still read row A (shared + shared is allowed), but no one can update it until T1 finishes. If T1 updates row B, its exclusive lock blocks even readers of B.
  • The effect is close to serialization: transactions that touch the same rows effectively run one after another (T1 then T2, or T2 then T1).
Pessimistic's big problem

Deadlock

  • T1: read A, then write B. T2: read B, then write A. They start together.
  • Step 1: T1 reads A and holds a shared lock on A. T2 reads B and holds a shared lock on B.
  • Step 2: T1 wants an exclusive lock on B, but T2's shared lock is there, so it waits for T2. T2 wants an exclusive lock on A, but T1's lock is there, so it waits for T1.
  • Neither can finish, so neither releases. That's a deadlock. The database detects it (or times out), aborts the stuck transaction(s), releases their locks, and they retry.
The contrast

The same two transactions, optimistically

Read A and read B each release their shared locks immediately. So T1 can take the exclusive lock on B and T2 the one on A, and both commit. No waiting cycle, no deadlock. (If they had updated the same row, the version check would catch it instead.)

Side by side

Optimistic vs pessimistic

Optimistic (OCC) Pessimistic (PCC)
Isolation level Below repeatable read (read committed) Repeatable read or serializable
Concurrency Much higher Lower
Detects conflicts At write time, by comparing versions Up front, by blocking
Deadlock No chance (per the lecture) Possible: stuck transactions are forced to roll back
Cost of a conflict Roll back and retry Waiting. Long locks can time out and roll back.
Best when Conflicts are rare Conflicts are frequent or very costly
Common technique Version column + check Two-phase locking (2PL), next lecture

Don't say "optimistic is always better". Start from the problem: decide the isolation level it needs, and that largely decides optimistic vs pessimistic.

Beyond the course good to know as an engineer

Good to know as an engineer

How optimistic locking is usually written

UPDATE seats SET status = 'BOOKED', version = version + 1 WHERE id = 10 AND version = 1; -- the version you read -- 1 row updated → you won -- 0 rows updated → someone changed it first: re-read and retry (or tell the user)
  • A single conditional UPDATE does the lock, check and write in one atomic step. No separate SELECT … FOR UPDATE is needed.
  • JPA/Hibernate does this automatically with a @Version field and throws OptimisticLockException on a mismatch. Retry in a new transaction with fresh data, cap the attempts, and add a little backoff. For an HTTP API, returning 409 Conflict is common.
  • Correction: MySQL does not keep a usable version per row automatically. You add the column yourself. SQL Server offers a rowversion type, and PostgreSQL has a hidden xmin column that some tools use.

How pessimistic locking is usually written

  • Usually you lock just the rows you need with SELECT … FOR UPDATE, rather than raising the whole transaction's isolation level. That works even at read committed.
  • Variants: FOR UPDATE NOWAIT (fail immediately if locked) and SKIP LOCKED (skip locked rows, which is great for job queues).

Living with deadlocks

  • Databases detect deadlock cycles and roll back one victim (MySQL error 1213, "try restarting transaction"). InnoDB also gives up after innodb_lock_wait_timeout, 50 seconds by default.
  • Prevention: lock rows in a consistent order (e.g. always lower ID first), keep transactions short, and index the columns in your WHERE clauses so fewer rows are locked.
  • "Optimistic never deadlocks" is mostly true because locks are held only briefly. But the final writes still take exclusive locks, so two transactions updating the same rows in opposite orders can still deadlock. It's just much rarer.

Picking one in practice

  • Optimistic: editing a profile or document, low-traffic records, long user "think time" between read and write.
  • Pessimistic: hot rows with many simultaneous writers (a flash-sale stock counter, the last seats of a popular show). Under heavy contention, optimistic transactions mostly retry, wasting work.
  • Often simplest of all: an atomic update like UPDATE stock SET qty = qty - 1 WHERE id = 7 AND qty > 0.
  • When the shared thing isn't a single database row (e.g. a file, or a call to an external API), teams use a distributed lock (Redis, ZooKeeper, etcd). It needs lease timeouts and fencing tokens to be safe.
Check yourself

Revision questions

Try answering out loud before opening each one.

Which isolation levels go with optimistic and with pessimistic?

Optimistic: below repeatable read, usually read committed. Pessimistic: repeatable read or serializable.

How does optimistic concurrency detect a conflict?

Each row has a version. Before updating, you lock the row and compare its current version with the one you read. If it changed, roll back and retry. If not, update and increment the version.

Two transactions read version 1, and A commits first. What happens to B?

B's validation sees version 2 instead of 1, so it rolls back and retries.

Why does pessimistic locking reduce concurrency?

Locks (even read locks) are held until the transaction ends, so anyone who wants to update those rows has to wait.

Describe the classic pessimistic deadlock.

T1 locks A and wants B. T2 locks B and wants A. Each waits for the other forever. The database aborts them so they can retry.

Why doesn't the same pair deadlock under optimistic control?

Read locks are released immediately, so each transaction can take the exclusive lock it needs and commit.

When is optimistic the wrong choice?

Under heavy contention on the same rows. Most transactions would fail validation and retry, wasting work, so pessimistic locking is better there.
