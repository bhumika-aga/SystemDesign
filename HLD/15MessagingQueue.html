Messaging Queues

A messaging queue sits between a service that produces work and a service that does it. The producer drops a message in and moves on. The consumer picks it up when it's ready. This lecture covers how Kafka and RabbitMQ do this, and the interview follow-ups: what if the queue fills up, goes down, or the consumer fails?

The basics ★ a favourite interview topic

What a messaging queue is, and why we need one

A producer puts a message into a queue. A consumer reads it from the queue and processes it. The producer and consumer never call each other directly. That simple gap brings three big advantages.

1 · Asynchronous work, with retries built in

  • The user doesn't have to wait for the email or SMS. Those are slow, heavy tasks, so doing them synchronously would add latency to every purchase.
  • "Why not just call the notification service asynchronously, without a queue?" Because of retries. If the notification service is down, the message stays in the queue and can be tried again. A direct call would simply be lost.

2 · Pace matching

Producers often create messages faster than a consumer can handle them. Without a queue, the consumer would be overwhelmed. With one, producers drop messages in at their speed, and the consumer takes them out at its own.

The same idea, at scale: a cab company

Picture it

A restaurant's order spike. Waiters (producers) clip order tickets onto the rail as fast as customers order. The chef (consumer) takes the next ticket when ready. Nobody stands at the stove waiting, and no order is forgotten.

Two messaging types

Point-to-point vs publish/subscribe

Point-to-point

Many consumers may read the queue, but each message is processed once, by one of them. If Consumer 1 takes message A, Consumer 2 never sees it. Use it for jobs that must happen once, like charging a card.

Publish/subscribe

The publisher sends to an exchange, which broadcasts the message to every queue bound to it. The same message is processed by many consumers. Use it when several services care about one event, like "order placed" going to email, analytics and inventory.

Pick based on the business need: should one worker handle this, or should everyone hear about it?

How it works · Kafka ★ most asked

Kafka's nine moving parts

Part What it is
Producer (publisher) Sends messages to a topic.
Broker A Kafka server. Start Kafka on a machine and you have a broker.
Cluster A group of brokers, each usually on its own machine (node).
Topic A named category of messages, like "orders" or "cab-locations". A broker can hold many topics. A topic is really a container for partitions.
Partition Where the messages actually live: an append-only list, like a queue. A topic can have many, and they can sit on different brokers.
Offset A message's position in its partition: 0, 1, 2, 3… Each partition counts on its own.
Consumer Reads messages from partitions and processes them.
Consumer group A team of consumers sharing the work. Every consumer belongs to one group.
ZooKeeper The coordinator. Brokers talk to it to know which broker holds which topic and partition, and (in the lecture's model) it tracks consumer offsets. Newer Kafka replaced it; see "Good to know".
Picture it

A library. The cluster is the whole library, each broker is a building, a topic is a subject ("History"), and the partitions are the shelves for that subject, possibly in different buildings. The offset is a book's number on its shelf.

Inside a message

A message, and which partition it lands in

Field Required? What it holds
Topic yes Which topic to publish to.
Value yes The actual message, e.g. "car 42 is at (19.07, 72.87)".
Key optional A string or ID that identifies the thing, e.g. the car ID.
Partition optional A specific partition to write to.
  • Key present: Kafka hashes the key to pick the partition. The same key always lands in the same partition, so all of car 42's updates stay together and in order.
  • Partition given: the message goes straight there.
  • Neither: messages are spread out, roughly round robin: message 1 to P0, message 2 to P1, message 3 to P2, and so on.

The lecture checks the key first and then the partition. In real Kafka, an explicitly set partition wins over the key. You'd rarely set both anyway.

Sharing the work

Consumer groups

  • Within one group: each partition is read by only one consumer. Consumer 1 and Consumer 2 of group A never read the same partition. That's how a group shares work without double-processing.
  • Across groups: anything goes. Group B's consumers read the same partitions as group A's, because each group gets its own full copy of the stream.
  • So Kafka gives you both messaging types: one group = point-to-point-style work sharing, several groups = pub/sub.
The key to recovery ★ very important

Offsets, and what happens when a consumer dies

For every group, topic and partition, Kafka remembers a committed offset: how far that group has successfully processed. In the lecture's model it's stored in ZooKeeper, like "group A · topic A · partition 0 · committed offset 3". That means offsets 0–3 are done and 4 onwards are unread.

  1. Consumer 1 is reading partition 0 and goes down.
  2. Kafka picks another free consumer from the same group, Consumer 2.
  3. It looks up the last committed offset (3) and has Consumer 2 continue from offset 4.

That's why both pieces exist. Consumer groups give you a spare consumer, and committed offsets tell it exactly where to pick up.

Distributed for real

Cluster, leaders and followers

  • Partitions of one topic can sit on different brokers: here broker 1 holds P0 and broker 2 holds P1.
  • Each partition has a replica on another broker. The original is the leader, the copy is the follower.
  • All reads and writes go to the leader. The follower keeps copying every new message from it, staying in sync.
  • If the leader's broker dies, the follower takes over as the new leader, with all the messages.
Interview follow-ups

"But what if…?"

Question Answer (Kafka)
The queue size limit is reached? One machine has a limit, so add brokers and spread partitions across them. Capacity grows with the cluster.
The queue goes down. What happens to its messages? Nothing is lost. The follower replica on another broker becomes the leader, and it already has every message.
A consumer goes down? Another consumer in the same group takes its partitions and resumes from the committed offset.
A consumer can't process a message? Retry a set number of times, then move it to a dead letter queue. Next section.
How is it distributed? Brokers form a cluster, partitions are spread and replicated across them, and a coordinator (ZooKeeper) keeps track.
When a message is bad

Retries and the dead letter queue

  1. The committed offset is 6. The consumer reads offset 7, a buggy message, and fails.
  2. It doesn't commit 7, so on the next pull it gets 7 again and bumps a retry count (you configure the limit: 3, 4, 5 tries).
  3. When retries run out, the message goes to a failure queue / dead letter queue (DLQ).
  4. Now the consumer commits 7 and carries on with new messages.
  5. Later, someone inspects the DLQ, fixes the problem and puts the message back into a working partition.
Picture it

A postman with a letter that has a smudged address. They try a few times, then drop it at the "undeliverable" desk instead of blocking the whole round. Someone sorts that desk later.

One key difference

Kafka pulls, RabbitMQ pushes

Kafka: pull

The consumer polls: "any new messages?" It takes data when it's ready, which is how pace matching falls out naturally.

RabbitMQ: push

The queue pushes each message to a consumer as soon as it arrives.

Near the end of the video the lecturer says "Kafka works on push". That's a slip of the tongue. Kafka is pull, as stated earlier in the lecture.

How it works · RabbitMQ

RabbitMQ: exchanges and bindings

Very similar to Kafka, with one extra hop. The producer talks to an exchange, not a queue. The exchange is bound to queues by routing keys: "routing key 1 → queue 1, routing key 2 → queue 2". There can be many exchanges, and several can feed the same queue.

Exchange types

Exchange Routing rule
Fanout Broadcast to every queue bound to the exchange. Keys are ignored.
Direct The message's key must exactly match a binding's routing key. No wildcards.
Topic Bindings can use wildcards, so one binding matches many keys. (Exact syntax in "Good to know".)

Retries without offsets

RabbitMQ has no offsets. If a consumer can't process a message, it's requeued to the back of the queue and retried. After the retry limit it goes to a dead letter queue, just like Kafka.

Side by side

Kafka vs RabbitMQ

Kafka RabbitMQ

Tracking progress Committed offset per group and partition Acknowledge each message; no offsets
Failed message Don't commit, retry, then dead letter queue Requeue, retry, then dead letter queue

Beyond the course good to know as an engineer

Good to know as an engineer

ZooKeeper is gone from modern Kafka

  • Kafka now manages its own metadata with a built-in consensus protocol called KRaft. Kafka 4.0 (March 2025) removed ZooKeeper completely. The lecture's ZooKeeper picture is right for older clusters, and good for understanding the coordinator's role.
  • Committed offsets haven't lived in ZooKeeper for years either. Kafka stores them in an internal topic, __consumer_offsets.
  • Small detail: Kafka's committed offset is the next message to read. "Done up to 3" is stored as 4. The idea is the same as the lecture's.

Kafka keeps messages after they're read

Unlike a classic queue, Kafka doesn't delete a message when it's consumed. It keeps the log for a retention period (7 days by default) or up to a size limit. That's why many groups can read the same data, and why you can replay by resetting an offset. RabbitMQ removes a message once it's acknowledged.

When a RabbitMQ queue is full

You can cap a queue's length. The overflow setting decides what happens: drop-head (the default: drop the oldest message), reject-publish (refuse new ones and tell the publisher), or reject-publish-dlx (refuse and send them to a dead letter exchange).

Partitioning details that bite in production

  • Ordering is only guaranteed within one partition. Need per-user or per-order ordering? Use that ID as the key.
  • With no key, modern producers (Kafka 2.4+) use a sticky partitioner: fill a batch for one partition, then switch. It's more efficient than strict round robin.
  • A skewed key (one celebrity user) creates a hot partition that one consumer can't keep up with.
  • Partitions cap parallelism. A group can't have more busy consumers than partitions. Extra consumers sit idle. Plan the partition count ahead.

Durability knobs

Typical production settings: replication factor 3, producer acks=all (wait for the in-sync replicas) and min.insync.replicas=2. Together they mean a write survives any single broker failing.

Delivery guarantees, and why consumers must be idempotent

Guarantee How Risk
At most once Commit, then process A crash loses the message
At least once (the usual) Process, then commit A crash re-delivers, so duplicates happen
Exactly once Kafka's idempotent producer + transactions Only within Kafka; external side effects still need care

Because of at-least-once delivery, the same message can arrive twice. Consumers should be idempotent, using the same idea as lecture 13's idempotency keys.

Retries in practice

  • The Kafka broker has no built-in retry counter or DLQ. Client frameworks (e.g. Spring Kafka's retry topics, Kafka Connect's error handling) implement the lecture's pattern.
  • Retrying in place blocks the whole partition behind one bad message. Larger systems move failures to separate retry topics with growing delays (backoff), then to the DLQ.

RabbitMQ details

  • Topic exchange syntax: routing keys are dot-separated words. * matches exactly one word and # matches zero or more. So the binding *.123 matches india.123. A key like India_123 (an underscore, not a dot) would not match the lecture's *123 example.
  • There's a fourth type, the headers exchange, which routes on message headers instead of the key.
  • Push needs flow control: a consumer's prefetch limit caps how many unacknowledged messages RabbitMQ pushes to it.

The lines are blurring

RabbitMQ now offers Streams (a Kafka-like log), and Kafka 4.0 added early access to share groups ("Queues for Kafka"), where consumers share a partition's messages queue-style. The choice is still about the main use: Kafka for high-volume event streams and replay, RabbitMQ for flexible routing of task messages.

Check yourself

Revision questions

Try answering out loud before opening each one.

Give three reasons to put a queue between two services.

Asynchronous work (the user doesn't wait), retries if the consumer is down, and pace matching when producers are faster than the consumer.

Point-to-point vs pub/sub?

Point-to-point: each message is processed once, by one consumer. Pub/sub: an exchange broadcasts it to every bound queue, so many consumers process the same message.

Broker, topic, partition, offset: one line each.

Broker: a Kafka server. Topic: a named container of partitions. Partition: the append-only list where messages live. Offset: a message's position in its partition.

How is a message's partition chosen?

An explicit partition is used if given. Otherwise the key is hashed, so the same key always goes to the same partition. Otherwise messages are spread across partitions (round robin or sticky batches).

Can two consumers in one group read the same partition?

No. Within a group, each partition has one reader. Consumers in different groups can read the same partition.

A consumer dies. Walk through the recovery.

Kafka assigns its partitions to another consumer in the same group, which looks up the committed offset and resumes from the next message.

A broker dies. Are its messages lost?

No. Each partition has a follower replica on another broker. The follower becomes the leader and already has the messages.

How do retries and the dead letter queue work in Kafka?

Don't commit the failed offset, so it's read again and the retry count goes up. After the limit, move it to a DLQ, commit, and continue. Someone fixes and replays the DLQ later.

Fanout, direct and topic exchanges?

Fanout: all bound queues. Direct: exact routing-key match. Topic: wildcard patterns (* one word, # zero or more).

Which is push and which is pull?

Kafka is pull (the consumer polls). RabbitMQ is push (the queue sends to the consumer).
