Load Balancers

A load balancer stands in front of many servers and decides which one handles each request, so no single server is overloaded. This lecture covers the two kinds (L4 and L7) and six algorithms for choosing a server: three static, three dynamic. Each comes with a catch.

The idea

What a load balancer does

Many clients send requests, and there are many servers (server 1 … server n). If every request landed on one server, it would be overwhelmed. A load balancer sits in between and spreads the traffic so no single server is overburdened.

Modern load balancers do much more (logging, health checks, TLS…), but distributing traffic is their original and main job.

Picture it

A supermarket with one person at the entrance pointing each shopper to a checkout: "you, counter 2; you, counter 3". Each algorithm below is a different rule for how that person points.

Two kinds

L4 (network) vs L7 (application) load balancers

L4 · network load balancer

Works at the transport layer. It sees source and destination IP addresses and TCP/UDP ports, and decides on those alone. Less information, so it's faster.

L7 · application load balancer

Works at the application layer. It can read headers, session, cookies, even the data, and the response too, so it can also cache. Much more advanced, but slower.

The lecturer's view is that the algorithms below belong to network (L4) load balancers. In practice both kinds use them; see "Good to know".

The map

Six algorithms, in two families

Static

The rule is fixed in advance and ignores how busy each server is right now. Cheap and simple.

Dynamic

The load balancer computes something live (connections, response times) for each request. Smarter, but more work.

Static · 1

Round robin

Take turns: request 1 → server 1, request 2 → server 2, request 3 → server 1, and so on, cycling forever.

Advantages

  • Very easy to implement.
  • Equal load: 10 requests, 5 each.

Disadvantage

  • A high-capacity and a low-capacity server are treated the same. If server 1 has 10× the resources, both still get 5. The weak server may go down from overload.
Static · 2

Weighted round robin

It fixes round robin's flaw by giving each server a weight that represents its capacity. Server 1 is 3× as strong as server 2, so it takes three requests for every one server 2 takes: 1, 2, 3 → S1, 4 → S2, 5, 6, 7 → S1, 8 → S2…

Advantages

  • The low-capacity server is saved from getting a big share of requests.
  • Still easy: weights are static, set when a server is added. No live computation, so it's a static algorithm.

Disadvantage

  • Requests take different amounts of time. If the weak server happens to get the heavy ones (request 4 takes 10 s, request 8 takes 20 s) while the strong one gets millisecond requests, the weak server still gets overburdened.
Static · 3

IP hash

Every client has a source IP address. The load balancer runs it through a hash function, and the result picks the server. Static, because nothing about server load is checked.

Advantages

  • Good when the same client must keep reaching the same server. Client 1's IP always hashes to server 1, however many times it connects.
  • Easy to implement.

Disadvantages

  • Clients behind a proxy all share the proxy's IP, so they all hash to one server and overload it.
  • No guarantee of equal distribution: even without a proxy, the hash might send requests 1, 3, 4 to one server and only 2 to the other.
Dynamic · 1

Least connections

For each new request, the load balancer checks which server has the fewest active connections right now and sends it there.

Advantage

  • Dynamic: it looks at each server's current load, so overload is unlikely when the servers have equal capacity.

Disadvantages

  • A TCP connection can be open but idle. Server 1's two connections might send one request each, while server 2's single connection (client 2) floods it with requests. Counting connections misjudges the real load.
  • It doesn't consider capacity: a weak server with few connections can still be overburdened.
Dynamic · 2

Weighted least connections

Add weights to least connections, just as weighted round robin added them to round robin. For each request, compute active connections ÷ weight for every server. The lowest ratio gets the request.

Server 1 has two connections but is 10× stronger, so its ratio is 0.2. Server 2 has just one connection, but its ratio is 1. Server 1 wins, even though it has more connections.

Dynamic · 3 ★ worth walking through

Least response time

First, TTFB (time to first byte): the time between sending a request and receiving the first byte (first packet) of the response. The load balancer measures it per server by sending requests and timing the replies.

Rule: score = active connections × TTFB. Send to the lowest score. If scores tie, fall back to round robin. Walking through the lecture's example:

Request Server 1 (TTFB 3) Server 2 (TTFB 1) Server 3 (TTFB 2) Goes to
Req 4 2 × 3 = 6 4 × 1 = 4 0 × 2 = 0 Server 3 (now 1 active)
Req 3 6 4 1 × 2 = 2 Server 3 (now 2 active)
Req 2 6 4 2 × 2 = 4 Tie → round robin → Server 2 (now 5 active)

It combines how busy a server is with how fast it is actually responding. A slow server, even one with few connections, gets fewer new requests.

Beyond the course good to know as an engineer

Good to know as an engineer

Health checks: the feature that matters most

Every algorithm assumes the servers are alive. Real load balancers run health checks. Active checks probe each server regularly (e.g. GET /health every few seconds). Passive checks watch real traffic for errors and timeouts. A failing server is pulled out of rotation and added back when it recovers. That's what makes a load balancer a high-availability tool, not just a traffic splitter.

The load balancer must not be a single point of failure

One load balancer in front of ten servers is itself a single point of failure. Run them in pairs (active–passive with a floating IP, as in lecture 14), or use a managed cloud load balancer, which is redundant internally. Across regions, DNS-based or anycast load balancing spreads users between data centres before any request reaches a regional load balancer.

The algorithms aren't only for L4

L7 load balancers (Nginx, HAProxy, Envoy, AWS's application load balancer) offer round robin, least connections, hashing and more. What L7 adds is content-based routing: by URL path (/api vs /images), header, cookie or hostname. This is the reverse-proxy role from lecture 16.

Better ways to keep a client on one server

  • Cookie-based sticky sessions (L7): the load balancer sets a cookie naming the server, so it isn't fooled by shared proxy IPs or by phones switching networks and changing IP.
  • Plain hash % N reshuffles almost every client when you add or remove a server. Consistent hashing (lecture 6) moves only a small share.
  • The cleanest fix is often stateless servers, with session data in a shared store like Redis, so any server can handle any request and no stickiness is needed.

Fixing the "idle connection" problem

With HTTP/2 and gRPC, one connection carries many requests, so counting connections is misleading. Modern proxies balance on active requests instead. Envoy's default "least request" uses power of two choices: pick two servers at random and send to the less busy one. That's nearly as good as checking every server, and much cheaper. NGINX offers the same idea.

Other algorithms you'll hear about

  • Random: surprisingly decent at large scale.
  • Ring hash / Maglev: consistent-hashing variants used by Envoy and Google.
  • Slow start: a newly added server gets a gradually increasing share, so a cold cache isn't flooded.
Check yourself

Revision questions

Try answering out loud before opening each one.

What's a load balancer's main job?

Distribute incoming traffic across servers so none is overburdened.

L4 vs L7?

L4 (network, transport layer) decides on IPs and TCP/UDP ports only: faster. L7 (application layer) can read headers, cookies, session and data, and can cache: more advanced.

Which algorithms are static, and which dynamic?

Static: round robin, weighted round robin, IP hash. Dynamic: least connections, weighted least connections, least response time.

Round robin's weakness, and the fix?

It treats strong and weak servers equally, so the weak one can crash. Weighted round robin gives each server a share in proportion to its capacity.

Weighted round robin's remaining weakness?

It ignores how long requests take. If the weak server gets the slow requests, it still overloads.

Why can IP hash overload one server?

Clients behind a proxy share its IP, so they all hash to one server. Hashing also doesn't guarantee an even spread.

Why can least connections misjudge load?

An open connection may be idle while another is very busy, and it ignores server capacity.

Server A: weight 10, 2 connections. Server B: weight 1, 1 connection. Which gets the next request under weighted least connections?

A: 2/10 = 0.2 vs B: 1/1 = 1. The lowest ratio wins, so A.

What's TTFB, and how does least response time use it?

Time to first byte: the delay between sending a request and receiving the first byte of the response. Score = active connections × TTFB. Lowest score wins, and ties go round robin.
