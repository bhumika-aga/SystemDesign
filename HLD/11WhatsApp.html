Design WhatsApp

WhatsApp, Discord, Telegram, Slack and Messenger all solve the same problem: get a message from one phone to another in real time, to millions of people at once, even when the other person is offline. This lecture builds that system one piece at a time.

Step 1 · requirement gathering ★ very common interview question

What must the chat app do?

Split requirements into functional (the minimum product: without these it isn't a chat app) and non-functional (the qualities that make it good at scale).

Functional (must have)

  • 1-to-1 send and receive. Start with text. Images, videos and files are an extension once the text flow works.
  • Group messaging: create a group, add people, send to everyone.
  • Online / offline and last seen.
  • User login and authentication.

Non-functional (qualities)

  • Scalability: billions of messages a day.
  • Low latency: real time. You send, they see it almost instantly.
  • Availability: never "service not available" when you try to send.
Step 2 · back-of-the-envelope

How big is it?

The lecturer spends only a minute here. Interviewers skip this step about 80% of the time. Lecture 8 has the full method.

total users = 2 billion
daily active (DAU) = 50 million
per user per day = 10 messages to each of 4 people = 40 messages
messages per day = 50 M × 40 = 2,000 M = 2 billion / day
message size = 100 characters ≈ 100 bytes (the lecture assumes 1 byte per character here)
storage per day = 2 B × 100 bytes = 200 GB / day
10 years of history = 200 GB × 365 × 10 ≈ 730 TB

Chat history is a choice. WhatsApp keeps history on your phone, not on its servers. Discord, Telegram, Slack and Messenger store history on their servers, so they need storage like this.

The core concept

Why not just connect the two phones?

  • If User A knows User B's IP address, they could talk directly, peer-to-peer.
  • That doesn't work at 50 million daily users. There's nowhere to keep chat history, nothing to handle groups, and nothing to hold a message when B is offline.
  • So users never talk directly. A chat server sits in the middle (client–server). It is responsible for scalability, groups, history and availability.
The connection ★ core of the design

HTTP can send, but it can't receive

HTTP is request–response: the client always starts, and the server only answers. User A sending a message is a normal request, so that's fine. But to deliver the message, the server would have to start talking to User B unprompted, and HTTP doesn't allow that. There are three ways around it.

1 · Polling

The client asks "any message for me?" over and over. Each ask opens a TCP connection, gets "no", and closes. It's a huge waste of connections and server load for mostly empty answers. Not scalable.

2 · Long polling ("pushing")

The client asks once, and the server holds the request open for up to a threshold (say 1 minute). If a message arrives it replies immediately. Otherwise it says "no" at the end and the client asks again. It's better than polling (one ask per minute instead of hundreds), but the server still blocks a thread per waiting user. With millions of users that's still not scalable.

3 · WebSocket the answer

  • Bi-directional: after a handshake, the client can send to the server and the server can send to the client.
  • Persistent: the connection stays open. It only closes if one side shuts it down or the internet breaks. Ten messages each way all travel on the same connection.
  • Since WebSocket is needed for receiving anyway, use it for sending too. Every user holds a WebSocket connection to a chat server.
Step 3 · design · 1-to-1 messaging

Many chat servers, and a map of who's where

There are thousands of chat servers. User 1 is connected to chat server 100, and User 2 to chat server 500. When User 1 says "send hello to User 2", how does server 100 know where User 2 is? A user mapping service (also called user discovery) keeps that answer.

Picture it

A big hotel with many floors, each with its own receptionist. Guests only talk to their floor's receptionist. The front desk keeps a register of which guest is on which floor, so a receptionist can look up the floor and pass a note along.

User Connected to
User 1 chat server 100
User 2 chat server 500
  • The mapping service is built on ZooKeeper, which coordinates distributed applications (see lecture 7). Here it coordinates the chat servers.
  • Assigning a server: when a user comes online, the mapping service picks a chat server (usually the nearest by geography), records user → server, and the user opens a WebSocket to it.
  • The send call: sendMsg(from, to, message, type), where type is 1-to-1 or group.

The happy path (both users online)

  1. User 1 sends sendMsg(U1, U2, "hello", 1-to-1) over its WebSocket to chat server 100.
  2. Server 100 asks the mapping service: "which server has User 2?" The answer is server 500.
  3. Server 100 passes the message to server 500 internally.
  4. Server 500 pushes it down User 2's open WebSocket.
Storage

Where the messages live: NoSQL

To keep chat history, every sendMsg also writes to a database. Choosing SQL or NoSQL follows lecture 10: look at the reads and writes.

Reads

  • A chat's history with one user
  • A group's chat history
  • Group member details
  • User profile

Writes

  • Send message
  • Update profile picture
  • Group changes
  • Hint 1: no complex queries or joins. None of these reads need multi-table joins.
  • Hint 2: low-latency search over huge data. Billions of messages a day, years of history, and users searching all their chats for a word.
  • Plus the non-functional needs: highly scalable and available. That points to NoSQL.
  • The lecture's example: Discord uses Cassandra, a wide-column NoSQL database.

The message table

message_id from to message timestamp
1001 SJ Hardik hello 10:41:02
1002 Hardik SJ hi! 10:41:09
  • Partition key = (from, to): every message between the same two people lands on the same node, so one chat's history is a single fast lookup. The data is spread horizontally across nodes (lectures 6 and 9).
  • message_id gives ordering inside a partition. NoSQL has no auto-increment, so generate it from a timestamp or a local ID generator.
  • You don't need a global ID generator like Snowflake. Ordering only matters within one chat, so two different chats can both have a message 100.
When things go wrong

Delivering to an offline user

  1. User 2 loses internet, or its chat server goes down. The mapping service removes User 2's entry.
  2. User 1 sends "hello". Chat server 1 asks the mapping service, which has no entry for User 2.
  3. The message can't be delivered, so it's just saved in the DB.
  4. Later User 2 logs in through the login service over HTTP. The login service talks to the mapping service, which assigns a chat server (say CS3) by location.
  5. User 2 opens a WebSocket to CS3. CS3 checks the DB for unread messages for User 2 and delivers them.
Groups

Group messaging

Group messages go into their own table, keyed by group. Group management (create, delete, join, add members) is a separate HTTP service.

group_id (partition key) message_id user message timestamp
G1 1 U1 hello 10:50:00
  • group_id is the partition key, so one group's messages sit together. message_id keeps them in order, as before.
  • Group service (HTTP, behind the load balancer) creates and deletes groups, adds members, and handles joins and updates. It keeps its own DB, SQL or NoSQL.
  1. U1 sends "hello" to group 1 over its WebSocket.
  2. The chat server asks the group service: "who's in group 1?" The answer is U1, U2, U3 and U4.
  3. It skips the sender and asks the mapping service which chat servers U2, U3 and U4 are on. They may be the same server or different ones.
  4. It forwards the message to each of those chat servers, which push it to their users.
Presence

Online, offline and last seen

A separate presence system tracks who's online, using heartbeats.

  • The client sends a heartbeat every ~3 seconds (over WebSocket). The presence system records user → last heartbeat time.
  • If no heartbeat arrives for a threshold (say 1 minute), the user is marked offline, and "last seen" is the last heartbeat time.
  • It stores this in something fast like Redis, and chat servers read it from there.

Why not use the mapping service's connection status?

Picture it

You're on a train going through tunnels. Your connection drops and returns every few seconds. If your status followed the raw connection, friends would see "online… offline… online… offline" flickering. The 1-minute threshold smooths that out: short drops don't count.

Putting it together

The full design

Component Job Talks over Storage
Chat servers Hold users' connections, route and store messages WebSocket NoSQL (Cassandra)
User mapping service Which user is on which chat server. Assigns servers. internal ZooKeeper / in-memory (Redis)
User login service Login, authentication, profile, phone number HTTP via load balancer SQL
Group service Create, delete and update groups, members HTTP via load balancer SQL or NoSQL
Presence system Online / offline, last seen WebSocket heartbeats Redis

How each requirement is met: 1-to-1 and group through chat servers plus the mapping and group services. Scalability, low-latency search and availability through NoSQL and many chat servers. Login through the login service. Last seen through the presence system.

Beyond the course good to know as an engineer

Good to know as an engineer

What production chat systems add on top of the lecture's design.

Delivery receipts: the ticks

  • One tick (sent): the server has stored the message. Two ticks (delivered): the recipient's device acknowledged it. Blue (read): the recipient opened the chat.
  • Each is an acknowledgement that flows back through the same chat servers. Until the server gets a delivery ack, it keeps the message marked "undelivered" and retries.

Message IDs from the client, for safe retries

Networks drop, so phones resend. If the client generates a unique message ID (a UUID) before sending, the server can recognise a retry and ignore the duplicate. That's idempotency (HLD lecture 13). Without it, a flaky connection shows "hello" twice.

Push notifications when the app is closed

An offline phone has no WebSocket. Instead of only waiting for the next login, the server sends a notification through Apple Push Notification service (APNs) or Firebase Cloud Messaging (FCM). The phone wakes, reconnects, and fetches unread messages.

Images, video and files

Never send big files through the chat servers. The client uploads the file to object storage (S3-style), often served through a CDN (lecture 5), then sends a normal small chat message containing the file's URL and a thumbnail.

A queue between chat servers

Instead of chat server 100 calling server 500 directly, many systems publish to a message queue or stream (for example Kafka, lecture 5) that the recipient's server consumes. That buffers spikes, survives a server restart, and makes retries easy.

Huge groups and channels

Fanning out every message to 100,000 members is expensive. Large groups and channels often switch to fan-out on read: store the message once and let members fetch it when they open the channel, instead of pushing to everyone.

End-to-end encryption

WhatsApp and Signal use the Signal Protocol. Messages are encrypted on the sender's phone and decrypted only on the recipient's. The servers route and store ciphertext they can't read. It's also why server-side search of message content isn't possible there.

Update on the lecture's example

Discord stored its messages in Cassandra from 2017, then migrated the whole cluster (trillions of messages) to ScyllaDB, a Cassandra-compatible database written in C++, in 2022–23. That cut the cluster from 177 nodes to 72 and made latencies steadier. The design lesson is the same: a wide-column store partitioned by channel.

Check yourself

Revision questions

Try answering out loud before opening each one.

Functional vs non-functional requirements for a chat app?

Functional: 1-to-1 send and receive, group messages, online and last seen, login and auth. Non-functional: scalability, low latency, availability.

Why can't plain HTTP deliver messages?

HTTP is request–response, and only the client can start a request. Delivering a message needs the server to start talking to the recipient.

Polling vs long polling vs WebSocket?

Polling asks repeatedly, opening and closing connections, so it's wasteful. Long polling holds each request open until a message arrives or a timeout, which blocks a server thread per user. WebSocket is one persistent, bi-directional connection where either side can send any time. That's the chosen option.

How does chat server 100 find the server User 2 is on?

It asks the user mapping service (built on ZooKeeper), which keeps a user → chat server table and assigns servers when users come online.

Why NoSQL for messages, and what's the partition key?

There are no complex joins, and it needs low-latency search over huge data plus scalability and availability. The partition key is (from, to) for 1-to-1 chats and group_id for groups.

How is message order kept without a global ID generator?

message_id comes from a timestamp or a local ID generator, and it only needs to be ordered within one partition (one chat), not globally.

What happens when the recipient is offline?

The mapping service has no entry for them, so the message is only saved in the DB. When they log in and get assigned a chat server, that server fetches their unread messages and delivers them.

Why a presence system instead of using connection status?

Connections flicker, for example in train tunnels. Heartbeats with a threshold (say 1 minute) stop "online / offline" flickering, and give a clean last-seen time.
