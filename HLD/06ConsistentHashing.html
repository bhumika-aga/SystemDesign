Consistent Hashing

Deciding which server should hold a piece of data is easy when the number of servers never changes. In real systems servers are added and removed all the time. Consistent hashing is the trick that keeps that from forcing you to move almost all of your data.

What is hashing?

A hash function takes an input of any length and turns it into a fixed-size number. The same input always gives the same number.

Picture it

A school sorts students into houses by a rule: add up the letters of your name and take the remainder when divided by 4. Anyone can run the rule and always lands in the same house, so nobody needs a list to look you up.

Mod hashing

To place a key in a table of fixed size N, take hash(key) mod N. With a 6-slot table, a hash of 20 goes to slot 20 mod 6 = 2. This works perfectly as long as N never changes. When N does change, it breaks.

Where it shows up

Two places systems use hashing to route data

1 · Load balancing app servers

The load balancer computes hash(key) mod 3 to decide which of 3 app servers gets a request. The same user keeps landing on the same server.

2 · Horizontal sharding of a DB

Rows are split across DB servers (for example names A–P on DB1, Q–Z on DB2). A hash decides which shard stores each key. This is where lecture 5 left off.

The problem ★ why consistent hashing exists

Mod N breaks when servers change

Servers aren't fixed. Traffic grows, so you add one. A machine crashes, so you lose one. The moment N changes, hash(key) mod N gives a different answer for most keys, so most of your data is now "on the wrong server".

Picture it

Split a class into 3 teams by roll number mod 3. A fourth team is added, so now it's mod 4. Almost every child has to change teams, not just enough to fill the new one.

Example with made-up hash values. Going from 3 nodes to 4 nodes:

Key hash mod 3 → node mod 4 → node
Shreyansh 21 0 → N1 1 → N2 moved
Rahul 13 1 → N2 1 → N2 stays
Shiva 11 2 → N3 3 → N4 moved
Aman 12 0 → N1 0 → N1 stays
Neha 22 1 → N2 2 → N3 moved
Ravi 17 2 → N3 1 → N2 moved

4 of 6 keys moved. In a real system that means rebalancing millions of DB entries: copying data between servers, or cache misses everywhere, just because one server was added. The same happens when a server is removed, since mod 3 becomes mod 2.

So normal mod hashing is a poor fit wherever the number of nodes is dynamic: app servers that scale up and down or crash, and database shards that get added as data grows.

The goal

When a node is added or removed, move as few keys as possible. With consistent hashing, only about 1/n of the keys (n = number of nodes) need to move on average, instead of almost all of them.

How it works

The hash ring

Imagine the hash output space bent into a circle. The lecture uses a ring of 12 positions, 0 to 11, that wraps back to 0. Both servers and keys are hashed onto the same ring.

Picture it

A circular running track with a few water stations. Every runner jogs clockwise and drinks at the first station they reach. Add a new station and only the runners just behind it change where they drink. Everyone else carries on as before.

  1. Place each server on the ring with a hash, for example hash(S1) mod 12. Here S1 lands at 3, S2 at 7 and S3 at 11.
  2. Place each key the same way: hash(key1) mod 12.
  3. From the key's position, move clockwise. The first server you reach owns that key.

Result: S1 → K1, K2 · S2 → K7, K5 · S3 → K6, K3, K4.

The key idea is that a key's server no longer depends on how many servers exist. It only depends on which server comes next on the ring.

Why it wins

Adding and removing servers

Adding a server

Only the keys between the new server and the server before it (counter-clockwise) move. Everything else stays where it was.

Removing a server

Only the keys that the removed server owned are moved, to the next server clockwise. That's the "limited rebalancing" consistent hashing promises: about 1/n of the keys.

The catch

Disadvantage: uneven load

The first diagram assumed servers land at equal distances around the ring. Hashes are random, so servers can end up bunched together. Then one server owns a huge arc of the ring and gets most of the keys.

The point of hashing across servers was to divide the load equally, and here it fails completely.

The fix ★ always mention this

Virtual nodes (virtual objects)

Place each physical server on the ring at several points, using several hash functions (or hashing S1#1, S1#2 and so on). Each point is a virtual node, a replica marker for the same real server.

Picture it

Instead of one big water station per sponsor, each sponsor gets several small stations scattered around the track. However the runners are spread out, each sponsor ends up serving roughly the same number.

  • More points per server means a more even spread of keys.
  • When a server is removed, its keys scatter to many other servers instead of all dumping onto one neighbour.
  • A stronger machine can be given more virtual nodes so it takes a bigger share.
Beyond the lecture
  • Real systems use hash spaces much bigger than 12, such as 0 to 2³²−1 or a 128-bit MD5 space, and often 100–200 virtual nodes per server.
  • Looking up "next server clockwise" is a binary search in a sorted list of ring positions, so it takes O(log n).
  • Used by Amazon Dynamo (lecture 9), Apache Cassandra, Discord's chat routing and many CDNs and caches.
  • Consistent hashing reduces movement but doesn't stop hot keys. One very popular key still lives on one server. Replication and caching handle that.
Beyond the course good to know as an engineer

Good to know as an engineer

The ring isn't the only way to get "minimal movement". These alternatives are simpler in some situations, and you'll see them in real libraries.

Rendezvous hashing (highest random weight)

Picture it

Every key holds a quick lottery among all servers. Each server gets a score from hash(key + server), and the highest score wins the key. Remove a server and only the keys it had won hold a new lottery. Everyone else's winner is unchanged.

  • No ring and no virtual nodes. Load spreads evenly by construction.
  • Cost: each lookup scores every server, which is O(n). That's fine for tens of servers, slow for thousands.
  • Easy to extend: take the top-k scores to pick k replicas.

Jump consistent hash

  • A tiny algorithm (published by Google engineers in 2014) that maps a key to one of n numbered buckets using no memory and about ln(n) steps.
  • It moves the minimum number of keys when n grows. The catch is that buckets can only be added or removed at the end (0…n−1), so it suits storage shards, not servers that fail at random.

Consistent hashing with bounded loads

  • Even with virtual nodes, one very hot key or unlucky placement can overload a server.
  • This variant gives every server a capacity cap, for example 1.25 × the average load. If a key's server is full, the key continues clockwise to the next server with room.
  • It's used in load balancers (it was added to HAProxy, and Vimeo and Google have written about it) to keep cache locality while preventing hotspots.
Method Lookup cost Balance Best for
Mod N O(1) Even A fixed number of nodes only
Ring + virtual nodes O(log n) Good with many vnodes Dynamic clusters (Dynamo, Cassandra)
Rendezvous O(n) Very even Small clusters, choosing replicas
Jump hash O(log n) Very even Numbered shards that only grow or shrink at the end
Bounded loads O(log n) Capped Load balancers with hot keys

Revision questions

Try answering out loud before opening each one.

What does a hash function do?

It turns an input of any length into a fixed-size value. The same input always produces the same output.

Why does hash(key) mod N fail when servers change?

Changing N changes the result for most keys, so most data suddenly maps to a different server. That forces huge rebalancing, possibly millions of DB entries moving.

Two use cases where the node count is dynamic?

Load balancing across app servers, which scale up and down or crash, and horizontal sharding of databases, which get more shards as data grows.

How does a key find its server on the ring?

Hash the key onto the ring and move clockwise. The first server you reach owns the key.

How many keys move when a node is added or removed?

Only the keys in the affected arc, about 1/n of all keys on average (n = number of nodes).

What's the disadvantage of basic consistent hashing, and the fix?

Servers can land close together, so one server owns a big arc and gets most keys. The fix is virtual nodes: place each server at several points on the ring so load spreads evenly.
