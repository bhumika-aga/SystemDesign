SQL vs NoSQL

"Which database will you use?" In an interview, "either works" is a weak answer, and so is a choice with no reason. This lecture compares the two families on four axes, then turns them into a checklist for choosing. It doesn't teach SQL or any NoSQL product in depth, only enough to pick the right one and explain why.

SQL · structure

SQL: tables, a fixed schema, relations

SQL (Structured Query Language) is how you query a relational database (RDBMS): MySQL, PostgreSQL, Oracle. Data lives in tables of rows and columns, and tables are linked by relations (parent → child).

Picture it

A government office with printed forms. Every form has the same boxes (the schema), decided before anyone fills one in. Forms reference each other by ID number. It's very orderly, but adding a new box means reprinting every form.

  • Predetermined schema: before inserting anything, you define the table name, the columns and their types. For example name VARCHAR(200), roll_no NUMBER(20).
  • You manage the data with SELECT, INSERT, UPDATE and DELETE.
SQL · nature and scaling

Centralised, and scales vertically

  • Nature: centralised. One employee's whole record (ID, department, salary, address across several related tables) sits on one server. It's not normally split with Table 1 on server 1 and Tables 2–3 on server 2.
  • Scaling: vertical. A users table grows from 10 million rows upward, so you add RAM and storage to the same machine.
  • Horizontal sharding (by rows or columns) is possible, but it isn't a natural fit: joins and transactions across shards get hard. Vertical scaling is how SQL scales most naturally.
SQL · property

ACID

Letter Means In plain words
A Atomicity A transaction happens completely or not at all.
C Consistency Every rule (constraints, keys) holds before and after.
I Isolation Concurrent transactions don't see each other's half-done work.
D Durability Once committed, it survives a crash.

The takeaway from the lecture: ACID guarantees data integrity and consistency. After every transaction the data is in a fully consistent state. Isolation levels are covered in HLD lecture 24.

NoSQL · structure

NoSQL: four ways to store data

"NoSQL" is also called non-relational, or best, "not only SQL". There's no single table format. There are four families.

1 · Key-value

key → opaque value

The simplest. The value can be a string, number or JSON, but the database treats it as a blob. You can only look up by key, never search inside the value. That makes it very fast. DynamoDB (lecture 9), Redis.

1001 → "…anything…"

2 · Document

key → JSON / XML document

Like key-value, but the database understands the value, so you can query fields inside it. That's the difference from key-value. MongoDB.

1001 → { "name": "Shreyansh", "dept": "IT" }

3 · Column-wise (wide-column)

key → list of column : value

Each key holds its own set of columns, and the number of columns can differ per key. Cassandra, HBase.

1001 → first_name: Shreyansh dept: IT interest: Basketball 1002 → first_name: Raj dept: Sales

4 · Graph

nodes + edges (relationships)

Data is stored as nodes, with edges for the relationships between them. Following a relationship is a direct jump, not a full table scan and join as in SQL, so it's very fast for social networks and recommendation engines. Neo4j.

NoSQL · nature and scaling

Distributed, and scales horizontally

  • Nature: distributed. There are no rigid relations tying rows together, so data can be spread over many nodes easily. Of 10 million users, 2 million can sit on each node.
  • Scaling: horizontal. Growing? Add node 4, node 5… and put the next million users there. See lecture 9 for exactly how Dynamo does it (consistent hashing, replication).
NoSQL · property

BASE instead of ACID

Letter Means In plain words
BA Basically Available Data is replicated across nodes, so if one is down another serves it. It's highly available and rarely loses data.
S Soft state Data can change without any user action. Replicas sync in the background, so a node holding a stale copy updates itself.
E Eventual consistency A read might return stale data, but if you retry after a while you'll get the latest once replicas have synced.
Picture it

ACID is a bank teller who won't let you leave until every ledger is updated. BASE is a group chat: your message shows up for most people instantly, some see it a few seconds later, and eventually everyone has the same history.

The part interviewers care about ★★ when to use which

When to use SQL, and when NoSQL

If you need… Choose Why
Flexible, changing queries SQL Today a 3-table join, tomorrow the business needs a 5-table join. SQL handles complex, changing queries. NoSQL supports only basic queries.
Only basic lookups, or you know the search columns in advance NoSQL If queries are simple and fixed (always search by these 5 columns), NoSQL does it fast.
Highly relational data SQL Lots of parent → child hierarchy and dependencies between entities.
Strict data integrity / consistency SQL You can't afford to lose or misread a single transaction, as in financial institutions. ACID is a must.
High availability + high performance, with some inconsistency OK NoSQL Distributed, so almost never down. Search is fast because data sits on small nodes you can jump to directly.
Big data, fast-growing and dynamic NoSQL Built for billions of records. Losing or delaying one or two out of millions has no real impact.

The decision factors in one line: query flexibility, relational data, consistency (ACID), availability and performance, data size. Always give your reason in the interview.

Beyond the lecture
  • The line has blurred. PostgreSQL has JSON columns, MongoDB supports multi-document ACID transactions, and "NewSQL" systems (CockroachDB, Spanner) scale SQL horizontally.
  • Real systems often use both: SQL for orders and payments, NoSQL for carts, sessions, feeds or search. Mention this "polyglot persistence" when a design has very different data needs.
  • Link it to CAP (lecture 2): SQL databases usually lean CP, and many NoSQL stores lean AP.
Beyond the course good to know as an engineer

Good to know as an engineer

Picking SQL or NoSQL is the first decision. These are the ones that follow, and the mistakes that show up in code review.

In NoSQL, design around your access patterns

In SQL you model the data, then write any query later. In NoSQL (especially key-value and wide-column) you do the reverse: list the queries first, then shape the tables so each query is a single key lookup.

  • Example: to show "a user's orders, newest first", use partition key user_id and sort key order_date. One lookup returns them in order.
  • DynamoDB takes this to single-table design: several entity types in one table, with composite keys like USER#42 / ORDER#2026-09-27.
  • The cost: a new query pattern later may need a new index or a data migration.

Normalisation vs denormalisation

Normalised Denormalised
Idea Store each fact once (customer name only in customers) Copy data where it's read (customer name also inside each order)
Writes One place to update, so no inconsistency Must update every copy
Reads Need joins One lookup, fast
Typical in SQL / OLTP NoSQL, read models (CQRS, lecture 4), analytics

OLTP vs OLAP

  • OLTP (online transaction processing): many small, fast reads and writes, such as "place this order". PostgreSQL, MySQL, DynamoDB.
  • OLAP (analytics): few huge queries over billions of rows, such as "revenue by country by month". Column-oriented warehouses like BigQuery, Snowflake, Redshift and ClickHouse.
  • Keep them separate. Copy data from OLTP to OLAP with ETL or CDC pipelines, so heavy reports never slow down checkout.

Specialised stores you'll meet

Need Use Why not a regular DB
Full-text search, fuzzy matching Elasticsearch, OpenSearch An inverted index maps word → documents. LIKE '%shoe%' scans every row.
Metrics, sensor data over time InfluxDB, TimescaleDB, Prometheus Built for append-heavy, time-ordered data, compression and downsampling.
Images, videos, backups Object storage (S3, GCS) Cheap and effectively unlimited. Store the URL in your DB, not the blob.
Cache, sessions, leaderboards Redis In-memory, sub-millisecond, with rich data types.

The N+1 query problem

orders = SELECT * FROM orders LIMIT 100 -- 1 query for each order: SELECT * FROM customers WHERE id = ? -- + 100 queries ✕

101 round trips where one would do. ORMs (Hibernate, Django, Rails) make this easy to write by accident through lazy loading. Fix it with a JOIN, a batched WHERE id IN (…), or the ORM's eager loading. Watch for it whenever a list page gets slow as the data grows.

Check yourself

Revision questions

Try answering out loud before opening each one.

Compare SQL and NoSQL on the four axes.

Structure: tables with a fixed schema vs key-value, document, column and graph. Nature: centralised vs distributed. Scaling: vertical vs horizontal. Property: ACID vs BASE.

What's a "predetermined schema"?

You must define tables, columns and types before inserting any data.

Key-value vs document database?

Both store key → value. In key-value the value is opaque, so you can query only by key. In a document database you can also query fields inside the JSON or XML value.

What makes a column-wise database different?

Each key holds its own list of column : value pairs, and different keys can have a different number of columns.

Why is a graph database fast for social networks?

Relationships are stored as direct edges between nodes, so finding friends is a jump along edges instead of a full table scan and join.

Expand BASE.

Basically Available, Soft state (data can change without user interaction as replicas sync), Eventual consistency.

Database for a bank's transactions? For a product catalogue search?

Bank: SQL, for ACID and strict integrity. Catalogue search: NoSQL, for high availability, fast simple lookups and a huge, growing dataset.
