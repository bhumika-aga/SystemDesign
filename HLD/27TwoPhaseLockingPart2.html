Two-Phase Locking · Deadlocks

Part 1 showed that basic 2PL can deadlock: transactions waiting on each other in a circle, forever. This part covers four ways out: give up after a timeout, draw a wait-for graph and look for circles, take every lock up front (conservative 2PL), or let a transaction's age decide who waits and who's aborted.

Strategy 1

Timeout: "you've waited too long, so you're probably stuck"

  • A scheduler tracks which transactions are running and which are waiting.
  • If a transaction has waited too long for a lock, the scheduler assumes a deadlock and aborts it.
  • Disadvantage: the scheduler can be wrong. T1 might be waiting for T2, which isn't stuck but just takes a long time. Then a perfectly valid transaction gets aborted. So on its own, a timeout isn't a correct deadlock detector.
Strategy 2 · better

Wait-for graph (WFG): look for a circle

  • The scheduler builds a directed graph. Each transaction is a node, and there's an edge Ti → Tj if Ti is waiting for Tj to release a lock.
  • When Tj releases that lock, the scheduler deletes the edge.
  • It periodically checks the graph for a cycle. T1 → T2 → T3 → T4 → T5 → T1 is a cycle, so those five transactions are deadlocked.
  • Unlike a timeout, it doesn't guess: a slow T2 with no cycle is left alone.
Breaking the cycle

Choosing a victim

Once a cycle is found, one transaction in it is aborted. It's called the victim. The scheduler doesn't pick blindly. It weighs:

Criterion Reasoning
Effort already spent A transaction that has done a lot of work is costly to throw away.
Effort still needed to finish One that's nearly done should probably be allowed to finish.
Cost of aborting How many updates must be rolled back to restore the previous state.
Number of cycles it's in A transaction in several cycles (like T3 here) breaks them all at once.
Strategy 3

Conservative (static) 2PL: take every lock before you start

  • Each transaction declares up front every item it will read and write.
  • The scheduler tries to grant all those locks at the start. If any one isn't available, none are granted, and the transaction waits until it can get all of them.
  • Once running, a transaction already holds everything it needs, so it never waits mid-way. Deadlock can't happen.

Pro

  • No deadlocks.

Cons

  • Much less concurrency: locks are held for the whole transaction, and work waits until everything is free.
  • Extra burden: the scheduler must know every read and write in advance. That's why it's rarely used.
Strategy 4

Timestamps: let age decide

Every transaction gets a timestamp when it starts. A smaller timestamp means it started earlier: it's older. Older means higher priority. When one transaction needs a lock another holds, their ages decide who waits and who's aborted, using one of two rules.

The two rules ★ easy to mix up

Wait-die vs wound-wait

Situation Wait-die Wound-wait
Older T1 wants a lock that younger T2 holds T1 waits T1 wounds T2: T2 is aborted and releases its lock, and T1 takes it
Younger T2 wants a lock that older T1 holds T2 dies (is aborted) T2 waits
  • Wait-die: "old waits for new; new doesn't wait for old, it dies". If ts(T1) < ts(T2), T1 waits for T2 to finish. Otherwise the requester is aborted.
  • Wound-wait: "old wounds new". If ts(T1) < ts(T2), T2 is aborted and releases its lock. Otherwise the requester waits.
  • Either way, waiting only ever goes in one direction of age, so a circle of waiting can't form. No deadlock.
  • Memory trick: the first word says what the older transaction does. Wait-die: older waits. Wound-wait: older wounds.

Deadlock was the first big issue with basic 2PL. The second, cascading aborts, is the next lecture.

Beyond the course good to know as an engineer

Good to know as an engineer

Prevention vs detection

The lecture calls them all "prevention strategies" and calls strategy 4 "timestamp-based deadlock detection". Strictly there are two families:

  • Detection: let deadlocks happen, then find and break them (wait-for graph; timeout as a rough version).
  • Prevention: make deadlocks impossible by design (conservative 2PL, wait-die, wound-wait, a fixed lock order). Timestamp schemes are prevention: nothing is detected, the rule just never allows a cycle.

What real databases do

  • MySQL InnoDB, PostgreSQL and SQL Server use wait-for-graph detection, plus a timeout as a safety net. PostgreSQL waits deadlock_timeout (1 s by default) before running the check. InnoDB's lock wait timeout is 50 s by default.
  • InnoDB tends to pick as victim the transaction that has changed the fewest rows. SQL Server lets you set DEADLOCK_PRIORITY.
  • Google Spanner uses wound-wait for its read-write transactions. In a globally distributed system, maintaining one global wait-for graph is too slow.

Starvation and fairness

An aborted transaction restarts with its original timestamp. It keeps getting older relative to newcomers, so eventually it has top priority and can't be aborted forever. Wait-die can restart the same young transaction many times, while wound-wait usually causes fewer restarts.

Distributed deadlocks

Across many machines, no single node sees the whole wait-for graph. Options: a central detector that collects every node's wait edges, edge-chasing probes forwarded along wait edges (a probe that comes back to its sender means there's a cycle), or simply using timestamp prevention instead.

The simplest prevention in your own code

Always lock rows in the same order, e.g. when transferring money, lock the lower account ID first. With a fixed order, a circle can't form, and no fancy scheduler rules are needed.

Check yourself

Revision questions

Try answering out loud before opening each one.

Why is a timeout alone a poor deadlock detector?

It can't tell a deadlock from a slow transaction, so it may abort a transaction that was only waiting for a long-running one.

What does an edge Ti → Tj mean in a wait-for graph?

Ti is waiting for Tj to release a lock. The edge is removed when Tj releases it.

How does the wait-for graph reveal a deadlock?

A cycle in the graph means every transaction in it is waiting on another in the same loop.

Four factors in choosing a victim?

Effort already spent, effort still needed, cost of aborting (updates to roll back), and the number of cycles the transaction is in.

How does conservative 2PL avoid deadlock, and why is it rare?

It grants all the locks a transaction needs at the start, all or nothing, so no one waits mid-transaction. It's rare because it cuts concurrency and needs every read/write declared in advance.

Older T1 wants a lock younger T2 holds. What happens under each rule?

Wait-die: T1 waits. Wound-wait: T2 is aborted and T1 takes the lock.

Younger T2 wants a lock older T1 holds. What happens under each rule?

Wait-die: T2 dies (is aborted). Wound-wait: T2 waits.

Why can't timestamp schemes deadlock?

Waiting is only ever allowed in one direction of age (old for young in wait-die, young for old in wound-wait), so a cycle can't form.
