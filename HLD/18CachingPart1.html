The idea

What is caching?

Caching stores frequently used data in fast-access memory (like RAM) instead of reading it every time from slow-access memory (a hard disk, a database).

  • It makes the system fast: reads come from fast memory.
  • It reduces latency.
  • It can help with fault tolerance. How depends on the strategy; the write-back strategy in Part 2 is the clearest example.
Picture it

You keep the books you read every day on your desk, and the rest on a shelf in the basement. Grabbing from the desk takes a second; the trip downstairs takes minutes. The desk is the cache.

Everywhere

Caches live at every layer

Layer What it caches
Client side (browser) Pages and files you load often, so they aren't fetched from the host again.
CDN Static data, close to users spread around the world (lecture 16).
Load balancer Responses. L7 load balancers can cache (lecture 17).
Server-side application cache ★ Data your app reads from the database. Redis is the classic example. This lecture's focus.
The focus

Where the server-side cache sits

Client → load balancer → one of many app servers → cache → database. The cache sits between the app and the database. The app asks the cache first: "do you have this?" If yes, it returns that. If not, it goes to the database. Exactly how depends on the caching strategy.

Scaling the cache

What is distributed caching?

With a single cache server:

  • Scalability: one machine has limited space and resources. Past a point, it can't grow.
  • Single point of failure: if it fails, all caching is gone.

A distributed cache uses a cache pool of many cache servers (CS1, CS2, CS3, CS4…). Each app server has a cache client, a library that connects it to the right cache server for each key.

How does the client pick a server? Consistent hashing

The cache servers are placed on a consistent hashing ring. To store or read a key, hash it to a point on the ring and move clockwise to the first cache server. That server owns the key. Lecture 6 covers this in depth. The lecture's summary: there's nothing magic about distributed caching. It's consistent hashing where the nodes happen to be cache servers.

Two words you'll see everywhere: a cache hit means the data was found in the cache, and a cache miss means it wasn't.

Strategy 1 ★ most common

Cache-aside

  1. The application first checks the cache.
  2. Found → cache hit → return the data to the client.
  3. Not found → cache miss → the application fetches from the database, stores it in the cache, and returns it.

Pros

  • Good for read-heavy applications: most reads never touch the database.
  • If the cache goes down, requests don't fail. Every read is treated as a miss and served from the database. You just lose the speed-up.
  • The cache's data shape can differ from the database's. The app writes the cache, so it can store it however it likes (see below).

Cons

  • New data always misses first. Fix: pre-heat (warm) the cache.
  • Writes go straight to the database and don't touch the cache. Unless you pair it with a write strategy, the cache and database can become inconsistent (next section).
The catch

How the cache goes stale

Step What happens Database Cache A read returns
1 Write: value = 10 (straight to DB) 10 —
2 Read: cache miss → load from DB into cache 10 10 10 ✓
3 Write: value = 11 (straight to DB, cache untouched) 11 10
4 Read: cache hit 11 10 10 ✕ stale

The database has the latest value, but the cache still holds the old one and happily serves it. That's why read strategies must be paired with a write strategy, which is what Part 2 is about.

Strategy 2

Read-through

Almost the same as cache-aside, with one change: on a cache miss, the cache library itself fetches the data from the database, stores it, and returns it to the application. The app no longer needs "if miss, then…" logic.

Pros

  • Good for read-heavy applications.
  • The logic of fetching from the database and updating the cache is separated from the application. It lives in the cache library.

Cons

  • New data always misses first (fix: pre-heat the cache).
  • Without a write strategy, the cache and database can become inconsistent.
  • The cache document must match the database table. If the employee table has 20 fields, the cached object has the same 20. No custom shape.
Picture it

Cache-aside: you check your desk, and if the book isn't there, you walk to the basement yourself. Read-through: you ask a librarian at the desk, and if the book isn't there, the librarian fetches it. Either way you get the book.

Beyond the course good to know as an engineer

Good to know as an engineer

Keeping cache-aside fresh: TTL and invalidation

  • Give every cached entry a TTL (time to live), so stale data expires on its own. That's a safety net even when your invalidation has bugs.
  • On a write, the usual move is to delete the cache key rather than update it. The next read reloads fresh data. Updating the cache from two concurrent writers can leave the older value in place.
  • Even delete-on-write has a small race. A slow reader can load the old value just after the delete and write it back. TTLs limit the damage, and some teams delete twice with a short delay.

"If the cache dies, requests still succeed"… if the database can cope

The cache often absorbs 90%+ of reads. If it disappears, the full read load hits the database at once, which may fall over too. Real systems replicate cache nodes, rate-limit or shed load when the cache is down, and size the database with this in mind.

Cache stampede (thundering herd)

When a very popular key expires, thousands of requests miss at the same moment and all query the database together. Fixes:

  • Request coalescing / single flight: only one request reloads the key, and the rest wait for its result.
  • A lock on the reload.
  • Probabilistic early refresh: occasionally refresh a key a little before it expires.
  • Jittered TTLs: add a random bit to each TTL so keys don't all expire at once.

Cache penetration

Requests for keys that don't exist (often from bots or attacks) always miss and always hit the database. Cache the "not found" result with a short TTL, or put a Bloom filter in front to reject keys that definitely don't exist.

How real distributed caches split keys

  • Memcached clients classically use consistent hashing, as in the lecture.
  • Redis Cluster uses 16,384 hash slots: slot = CRC16(key) mod 16384, and each primary node owns a range of slots. Moving slots between nodes rebalances the cluster. Each primary can have replicas, which also fixes the single-point-of-failure problem.
  • Watch out for hot keys: one celebrity key can overload the one node that owns it. Replicate it or add a small local cache in each app server.

Read-through in practice

Redis itself doesn't fetch from your database; using Redis is almost always cache-aside. Read-through comes from libraries and products that accept a "loader" function, e.g. Caffeine's LoadingCache, Hazelcast map loaders, or Amazon DAX in front of DynamoDB. The loader decides the shape, but it's usually a direct copy of one row or entity, which is why the lecture says the shape must match.

Measure it

Track the hit ratio (hits ÷ all lookups). A cache with a 30% hit ratio is mostly overhead. Common hot read paths often reach well above 90%.

Check yourself

Revision questions

Try answering out loud before opening each one.

Define caching and name three benefits.

Storing frequently used data in fast memory instead of reading it from slow storage every time. It makes the system faster, reduces latency, and can help fault tolerance.

Name four places a cache can live.

The browser (client side), a CDN, the load balancer, and server-side application caches like Redis.

Two problems with a single cache server?

Limited scalability (one machine's resources) and a single point of failure.

How does a distributed cache decide which server holds a key?

The app's cache client uses consistent hashing: hash the key onto the ring and take the first cache server clockwise.

Walk through cache-aside on a miss.

The app checks the cache and misses. The app reads from the database, writes the value into the cache, and returns it to the client.

Why doesn't a cache outage break cache-aside?

Every read is treated as a miss and served from the database. The speed-up is lost, but requests still succeed (as long as the database can take the load).

Show how cache-aside serves stale data.

DB = 10, a read caches 10, then a write sets DB = 11 without touching the cache. The next read hits the cache and gets 10.

The one real difference between cache-aside and read-through?

Who loads the data on a miss: the application (cache-aside) or the cache library (read-through).

Why can cache-aside use a custom data shape but read-through can't?

In cache-aside the app writes to the cache, so it can combine or reshape data. In read-through the library copies the database row as-is.
