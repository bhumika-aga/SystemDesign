Design a Rate Limiter

A rate limiter caps how many requests a user can make in a period of time, for example 3 tweets a minute. Anything over the limit is rejected before it reaches your servers. Almost every API needs one, and the interview hinges on knowing five algorithms and when each fits.

Why ★ very common interview question

The problem: too many requests

  • In a DDoS attack, attackers send thousands or even lakhs of requests in seconds.
  • Every server has limited resources (RAM, CPU, disk). The flood uses them up, and the server goes down.
  • Now genuine users get declined too.
  • A rate limiter stops this by capping requests per user or client. Every backend engineer builds APIs, so knowing how to limit their rate is basic.
Picture it

A theme park ride lets in a fixed number of people per run. A guard at the gate counts people. When the ride is full, the next person is told "please wait and come back". The ride never gets overloaded, and the people already on it have a good time.

The lecture covers five algorithms, then the design: token bucket, leaking bucket, fixed window counter, sliding window log and sliding window counter.

Algorithm 1

Token bucket

A bucket holds tokens, and every request must take one. A refiller adds tokens at a fixed rate. No token means the request is rejected.

  • Capacity: the most tokens the bucket can hold, say 4. Tokens added when it's full overflow and are discarded.
  • Refiller: adds tokens on a schedule, say 2 per minute.
  • Both numbers come from a config file, so they can be changed without code changes.
  • A rejected request gets HTTP 429 Too Many Requests.

Worked example

Rule: each user gets 3 tokens for the post-tweet API, and the refiller adds 2 tokens per minute (never above 3). Implemented as a simple counter per user.

Time Request Tokens before → after Result
10:01:00 post tweet 3 → 2 allowed
10:01:25 post tweet 2 → 1 allowed
10:01:35 post tweet 1 → 0 allowed
10:01:50 post tweet 0 → 0 429 denied
10:02 (refill +2) 0 → 2
10:03 (refill +2, capped at 3) 2 → 3 (1 overflows)
10:03 post tweet 3 → 2 allowed

Rules can be set per user, per API, or both.

Algorithm 2

Leaking bucket

Requests pour into a bucket with a hole in the bottom. They leak out at a constant rate to be processed. If they pour in faster than they leak, the bucket overflows and the extras are rejected.

  • Built with a queue of fixed capacity, first in first out.
  • Request arrives → queue full? Yes: 429. No: add to the queue.
  • Requests are taken from the queue and processed at a constant rate.

Disadvantage: bursty traffic

Some apps have legitimate bursts. Amazon Prime Video traffic is low during the day and spikes in the evening. A leaking bucket processes everything at the same steady rate, so during a spike, old requests sit in the queue and new ones get rejected. Ask the interviewer whether the app needs a constant processing rate before choosing this.

Algorithm 3

Fixed window counter

Chop time into fixed windows (8:00–8:05, 8:05–8:10, …) and give each window a counter, say 3. Each request uses one. When it hits 0, reject until the next window starts and the counter resets.

  • Window length and count come from config, for example 5 minutes and 3 requests.
  • It's very simple: one counter per window.

Disadvantage: bursts at the edges ★ always mention this

If 3 requests arrive at the very end of one window and 3 more at the very start of the next, each window sees only 3, so all 6 are allowed. But looking at any 5-minute stretch across that boundary, there were 6 requests: double the limit. Your system may not be ready for that.

Algorithm 4

Sliding window log

Instead of fixed windows, keep a log of timestamps. For each request, look back exactly one window (say 1 minute) from now. The window slides with time, so there are no edges to exploit.

Rule: 3 requests per minute. The log is kept sorted by time.

Request at Step Log after Result
10:00:10 log it · size 1 :10 allowed
10:00:20 within 1 min · size 2 :10 :20 allowed
10:00:40 within 1 min · size 3 :10 :20 :40 allowed
10:00:45 still within 1 min, size already 3 → but it's still logged :10 :20 :40 :45 429 denied
10:01:20 window is now 10:00:20–10:01:20 · remove timestamps from the top that fall outside :40 :45 1:20 count now under 3 → allowed
  • Fixes the fixed-window edge problem. The limit holds over any 1-minute span.
  • Disadvantage: memory. It stores a timestamp for every request, even the denied ones. For busy users that's a lot of storage.
Algorithm 5

Sliding window counter

The best of both: the cheap counters of the fixed window, plus the no-edge-burst behaviour of the sliding log. Keep a count per fixed window, and estimate how many requests fall in the sliding window using a weighted share of the previous window.

rule: 5 requests per minute
current window so far = 2 requests
previous window total = 6 requests
overlap with previous window = 10 s of 60 s
estimate = 2 + 6 × (10 / 60) = 2 + 1 = 3 → 3 ≤ 5 → allowed

It assumes the previous window's requests were spread evenly, so it's an approximation, but a very good one (see "Good to know").

Algorithm Memory Allows bursts? Weak spot
Token bucket 2 numbers per user Yes, up to capacity Tuning capacity and refill rate
Leaking bucket A queue per user No, smooths to a constant rate Bursty apps: old requests block new ones
Fixed window counter 1 counter per window Yes, double at window edges Edge bursts
Sliding window log 1 timestamp per request No, exact Memory (denied requests logged too)
Sliding window counter 2 counters Barely, approximate Assumes an even spread in the previous window
High-level design

Where the rate limiter lives

  • Placement: either inside the server, or as a separate layer between client and server. If you already have an API gateway (which handles authentication and so on), host the rate limiter there. Discuss with the interviewer, since it depends on the company's setup.
  • Counters and queues in Redis: every request reads and updates a counter. A normal database is far too slow for that, so use an in-memory store.
  • Rules in config files: "3 per minute", "5-minute windows" and so on are config. They live on disk but rarely change, so load them into a cache at startup, and the limiter reads from the cache.
  • Result: forward the request to the server, or return 429.

The lecturer's emphasis: the boxes are simple. The algorithms are what interviewers dig into.

Follow-up question

Many rate limiters, one Redis

  • At scale you run several rate limiter instances. A client's requests may hit any of them.
  • They all use one centralised Redis, so everyone sees the same counters.
  • Follow-up: atomicity. If two requests from the same user reach RL1 and RL2 at the same moment, both read "2 tokens left", both allow, and both write. That's a race condition.
  • Answer: make the read-check-update atomic in Redis. Existing solutions do this, so you don't build it yourself. The cost is a little extra latency. If the interviewer accepts that, use it. Otherwise it's a known limitation.
Beyond the course good to know as an engineer

Good to know as an engineer

How Redis makes it atomic in practice

  • Fixed window: INCR rate:user42:202610011005, then EXPIRE it after the window. INCR is atomic on its own, so two limiters can't both read the same old value.
  • Token bucket / sliding window: put the read-check-update logic in a small Lua script. Redis runs each script as one atomic step. This is what Stripe describes using with Redis for its limiters.

Tell clients what happened

  • Return 429 with a Retry-After header (seconds to wait).
  • Many APIs also send X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset on every response, so well-behaved clients slow down before hitting the wall. (An IETF draft standardises these as RateLimit-* headers.)
  • Clients should back off exponentially with jitter, and honour Retry-After.

What to limit by

User ID or API key for logged-in traffic, and IP address for anonymous traffic. Beware that many users can share one IP behind an office NAT or mobile carrier. Different endpoints usually get different limits: login attempts are far stricter than reads.

Layers of limiting

Real systems limit at several layers: a CDN or WAF at the edge stops floods before they reach you (lecture 5), the API gateway enforces per-user quotas, and individual services protect themselves with concurrency limits and load shedding. Stripe runs a request-rate limiter, a concurrent-requests limiter, and load shedders that keep capacity for critical traffic.

Real-world choices

  • Stripe and Amazon use the token bucket for API request rates.
  • Cloudflare uses the sliding window counter at its edge. Across 400 million requests it measured just 0.003% wrongly allowed or limited, using only two counters per key.

Hard vs soft limits, and failing open

A hard limit never lets traffic over. A soft limit lets a little over briefly. And decide what happens if Redis is down: fail open (allow everything, so availability wins) or fail closed (reject everything, so protection wins). Most public APIs fail open.

Check yourself

Revision questions

Try answering out loud before opening each one.

Why do we need a rate limiter?

To stop floods such as DDoS, or one abusive client, from using up a server's limited resources and taking it down for genuine users.

Explain the token bucket.

A bucket with a capacity holds tokens, and a refiller adds them at a fixed rate (extras overflow). Each request takes one token. With none left, it's rejected with 429.

Token bucket vs leaking bucket?

The token bucket allows bursts up to its capacity. The leaking bucket queues requests and processes them at a constant rate, which hurts legitimately bursty apps because old requests block new ones.

What's wrong with the fixed window counter?

Requests bunched at the end of one window and the start of the next both pass, so up to double the limit can get through around the boundary.

Sliding window log: advantage and disadvantage?

It's exact over any rolling window, with no edge bursts. But it stores a timestamp for every request, including denied ones, so it uses a lot of memory.

Compute: rule 5/min, current window 2, previous window 6, overlap 10 s.

2 + 6 × 10/60 = 2 + 1 = 3 ≤ 5, so the request is allowed.

Where do counters and rules live in the design?

Counters and queues live in Redis, which is in-memory and fast. Rules live in config files that are loaded into a cache at startup.

Multiple rate limiters share one Redis. What can go wrong?

A race condition: two limiters read the same counter at once and both allow. The fix is atomic operations (INCR, Lua scripts), at the cost of a little latency.
