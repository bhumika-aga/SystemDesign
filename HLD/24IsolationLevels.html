The problem ★ asked in both LLD and HLD

Many requests, one seat

  • A critical section is the piece of code that accesses a shared resource, here "read seat 10; if free, set it to booked".
  • Three requests enter it at the same time. All read free, all update to booked, and all return success. One seat, sold three times.
  • In HLD interviews this comes up as "explain distributed concurrency control". In LLD interviews (BookMyShow, parking lot) it's the follow-up: "how do you handle concurrency?"
The first instinct

Why synchronized only works on one machine

  • Wrapping the critical section in synchronized (a lock) lets one request in at a time. User 1 books, and users 2 and 3 then see "already booked". Correct.
  • But that lock only exists inside one process. It coordinates the threads of one process.
  • In a distributed system, the service runs on many machines behind a load balancer. Each process has its own lock, so all three requests still get in at once.
  • So we need distributed concurrency control: optimistic and pessimistic concurrency control (often loosely called optimistic and pessimistic locking). They're covered next lecture, after three foundations.
Foundation 1

Transactions protect integrity

A transaction keeps the database consistent. Moving ₹20 from A (₹100) to B (₹50): the debit works (A = 80), then the credit fails. Rollback undoes the successful debit too, so A is back to 100.

Only two states are consistent: both succeeded (A = 80, B = 70) or nothing happened (A = 100, B = 50). Without a transaction you'd be left with A = 80 and B = 50, so money vanishes.

Foundation 2

Database locks: shared (S) and exclusive (X)

Locking makes sure no other transaction updates a locked row.

A row already has… Can another take a shared lock? Can another take an exclusive lock?
Shared lock (S), a read lock yes many can read together no the writer waits
Exclusive lock (X), a write lock no can't even read no
Foundation 3 · the problems

Three things that go wrong with concurrent reads

Isolation (the I in ACID) means each transaction feels like it's running alone, even though many run in parallel. How strong that feeling is decides how much concurrency you get. Weak isolation allows these three problems.

1 · Dirty read: reading data that's later rolled back

2 · Non-repeatable read: same row, different value

3 · Phantom read: same query, different rows

The difference: a non-repeatable read changes a row you already read; a phantom read adds or removes rows in the set your query matches.

The answer

Four isolation levels

Level Dirty read Non-repeatable read Phantom read
0 · Read uncommitted possible possible possible
1 · Read committed prevented possible possible
2 · Repeatable read prevented prevented possible
3 · Serializable prevented prevented prevented

The whiteboard labels the top "consistency high" and the bottom "consistency low", and the narration once says isolation level 0 is "read committed". Both are slips. Read uncommitted (level 0) gives the most concurrency and the least consistency; serializable (level 3) gives the most consistency and the least concurrency.

Under the hood

How each level uses locks

Level Reads Writes So…
Read uncommitted No lock No lock (per the lecture) Readers can see uncommitted writes, so all three problems happen
Read committed Shared lock, released as soon as the read is done Exclusive lock, held to the end of the transaction You can't read an uncommitted write (the X lock blocks you). But between your two reads, someone can update and commit.
Repeatable read Shared lock, held to the end of the transaction Exclusive lock, held to the end Nobody can update a row you've read until you finish. But new rows can still be inserted into your range.
Serializable Same as repeatable read, plus a range lock Same, plus a range lock The range your query covers (including the gaps) is locked, so no new rows can appear

Setting it

SET TRANSACTION ISOLATION LEVEL REPEATABLE READ; BEGIN_TRANSACTION; SELECT …; UPDATE …; IF success → COMMIT ELSE → ROLLBACK END_TRANSACTION;

If you don't set one (e.g. a plain Spring @Transactional), the database's default is used. It varies by database.

In the interview

Pick the weakest level your problem can tolerate

  • Only reads, dirty reads acceptable → read uncommitted: no locking, maximum concurrency.
  • No dirty reads, but values may change between reads → read committed.
  • Re-reading a row must return the same value → repeatable read.
  • Even new rows appearing would be wrong → serializable.

Beyond the course good to know as an engineer

Good to know as an engineer

Writes always take locks

The lecture's table says read uncommitted takes no lock for writes. In real databases, every write takes an exclusive lock until commit, at every level. Otherwise two transactions could overwrite each other's uncommitted changes (a "dirty write"). Read uncommitted only skips the read locks.

Most databases use snapshots, not just locks (MVCC)

  • The lecture describes the classic lock-based implementation. PostgreSQL, Oracle and MySQL InnoDB mostly use multi-version concurrency control: each transaction reads from a snapshot, and writers create new row versions. So readers don't block writers and writers don't block readers.
  • Under MVCC, read committed takes a fresh snapshot per statement, and repeatable read keeps one snapshot for the whole transaction.
  • PostgreSQL's repeatable read already prevents phantoms. MySQL InnoDB prevents them for locking reads with gap / next-key locks, the real-world "range lock".

Defaults differ

Database Default level
PostgreSQL, Oracle, SQL Server Read committed
MySQL (InnoDB) Repeatable read
CockroachDB Serializable

Two more anomalies interviewers like

  • Lost update: two transactions read balance 100, both add 10, both write 110. One update vanishes. The usual fixes are SELECT … FOR UPDATE, an atomic UPDATE … SET x = x + 10, or optimistic version checks (next lecture).
  • Write skew: two doctors each check "is someone else on call?", see yes, and both go off duty. Snapshot-based repeatable read allows this. Only true serializable stops it.

The seat problem in practice

A one-line fix often beats a higher isolation level: UPDATE seats SET status='BOOKED' WHERE id=10 AND status='FREE', then check that exactly 1 row changed. The database's row lock makes the check-and-set atomic, so only one request wins.

Check yourself

Revision questions

Try answering out loud before opening each one.

What is a critical section?

The piece of code that accesses a shared resource, e.g. "read seat; if free, book it".

Why doesn't synchronized fix double-booking in a distributed system?

It locks only within one process. Copies of the service on other machines have their own locks, so concurrent requests still enter together.

How does a transaction protect integrity?

If any statement fails, rollback undoes all the successful ones, so the database ends in either the all-done or the nothing-done state.

Shared vs exclusive lock?

Shared (read): many holders at once, but no writer. Exclusive (write): one holder, and nobody else can read or write.

Dirty read vs non-repeatable read vs phantom read?

Dirty: reading another transaction's uncommitted change. Non-repeatable: re-reading a row gives a different committed value. Phantom: re-running a query returns a different set of rows.

Which problems does each level prevent?

Read uncommitted: none. Read committed: dirty reads. Repeatable read: dirty and non-repeatable reads. Serializable: all three.

How does read committed prevent dirty reads but not non-repeatable reads?

Writes hold an exclusive lock until commit, so you can't read uncommitted data. But a read releases its shared lock immediately, so someone can update and commit between your two reads.

How does serializable stop phantoms?

It adds a range lock over the query's range, including the gaps, so no new matching rows can be inserted until it finishes.
